# 关键概念

本页统一 Java 工作流栏目的术语口径。后续如果你在 [构建工作流](构建工作流.md)、`workflow` API 文档或 examples 中看到这些词，默认都以本页定义为准。

如果你还没读上一页，建议先看 [概述](概述.md)；如果你已经理解了术语，可以继续读 [构建工作流](构建工作流.md)。

## 核心术语总览

| 术语 | Java 对应类型 / 方法 | 含义 |
| --- | --- | --- |
| 工作流 | `Workflow` | 面向用户的主工作流类，表示一张由多个节点组成的有向图 |
| 工作流卡片 | `WorkflowCard` | 工作流的元信息卡片，描述 `id`、名称、版本、输入 schema 等 |
| 组件 / 节点 | `ComponentComposable`、`WorkflowComponent`、`Start`、`End`、`QuestionerComponent` 等 | 组成工作流图的执行单元 |
| 普通边 | `addConnection(...)` | 定义批处理依赖或顺序执行关系 |
| 条件边 | `addConditionalConnection(...)` | 根据路由结果决定后续节点 |
| 流式边 | `addStreamConnection(...)` | 在支持流式能力的节点之间传递增量数据 |
| 工作流会话 | `WorkflowSessions`、`WorkflowSessionApi` | 承载一次 workflow 执行过程中的状态、交互输入和环境变量 |
| 工作流输出 | `WorkflowOutput` | `invoke(...)` 的返回容器，封装 `result` 和 `state` |
| 执行状态 | `WorkflowExecutionState` | 标记执行是否完成、是否需要额外交互输入 |
| 流式输出块 | `WorkflowChunk`、`OutputSchema` | `stream(...)` 返回的增量数据块 |
| 交互输入 | `InteractiveInput` | 在 `INPUT_REQUIRED` 后恢复执行时提交给 workflow 的输入 |
| 子工作流 | `SubWorkflowComponentImpl` | 把另一条 `Workflow` 作为当前图中的一个节点来调用 |

## 1. `Workflow`

`Workflow` 是 Java 工作流的中心对象。

它同时承担三件事：

1. **构图**：注册节点、声明输入输出 schema、连边。
2. **执行**：通过 `invoke(...)` 批量执行，通过 `stream(...)` 增量执行。
3. **兼容封装**：提供多组重载，兼容不同参数顺序、不同 schema 写法和 legacy 组件接入方式。

你可以把它理解成“**一张可执行的图**”。它不是 workflow 列表，也不是意图路由器；这些应用层职责通常在 `WorkflowAgent` 中出现。

## 2. `WorkflowCard`

`WorkflowCard` 是工作流的身份卡片。

最常见的信息包括：

- `id`
- `name`
- `version`
- `description`
- `inputParams`

它的作用不只是“写给人看”。在 Java 侧：

- `Workflow` 自身会持有这张卡片。
- `WorkflowAgent.addWorkflows(...)` 注册 workflow 时，也会读取 `WorkflowCard` 中的描述信息。
- `inputParams` 可以作为这条 workflow 对外暴露的输入 schema。

因此，`WorkflowCard` 代表的是“这条 workflow 是谁、接收什么输入”，而不是执行过程中的动态状态。

## 3. 组件 / 节点

工作流图中的每个节点都可以理解为一个“组件”。Java 侧常见的节点分成三类：

### 起止节点

- `Start`：入口节点，按原样透传输入。
- `End`：结束节点，负责产出最终结果；可返回普通批结果，也可参与 `stream` / `transform` / `collect`。

### 业务节点

例如：

- `QuestionerComponent`
- `LLMComponent`
- `BranchComponent`
- `IntentDetectionComponent`
- `SubWorkflowComponentImpl`

这些节点负责真正的业务逻辑、追问、模型调用、路由或子图委派。

### 自定义节点

如果内置组件不够用，可以基于 `WorkflowComponent` 或 `ComponentComposable` 扩展自定义节点。后续组件页会单独展开这一层。

## 4. 边：普通边、条件边、流式边

“注册组件”只是在图里放了节点；真正让图跑起来，还要靠边定义执行关系。

### 普通边：`addConnection(...)`

普通边表示典型的先后依赖：前一个节点执行完，后一个节点再执行。

适合：

- 线性流程
- 并行分支后的汇聚
- 普通批处理输入输出传递

### 条件边：`addConditionalConnection(...)`

条件边表示“下一个节点不是固定的，而是运行时决定的”。

Java 当前支持两类常见路由输入：

- `BranchRouter`
- `Function<Object, Object>` 路由函数

适合：

- 条件分支
- 动态跳转
- 循环或回跳场景

### 流式边：`addStreamConnection(...)`

流式边用于在支持流能力的节点之间传递增量输出。

典型搭配是：

- 上游节点具备 `STREAM` 或 `TRANSFORM` 能力
- 下游节点具备 `TRANSFORM` 或 `COLLECT` 能力

最常见的入门场景是：

- `LLMComponent` 逐块产出内容
- `End` 以 `responseMode = "streaming"` 的方式向外输出

## 5. `WorkflowSessions` 与会话

`WorkflowSessions` 是 workflow 包级的会话创建门面。

最常用的入口有：

- `WorkflowSessions.createWorkflowSession()`
- `WorkflowSessions.createWorkflowSession(String sessionId)`

它背后返回的是 `WorkflowSessionApi`。这层会话在工作流里承担几个核心职责：

- 保存本次执行的状态
- 在节点之间共享中间结果
- 承接交互输入恢复
- 管理流式输出、trace 等执行期能力

一个很重要的实践点是：**如果 workflow 在一次执行中被中断，需要继续同一条流程，就要复用同一个 session**。

## 6. `WorkflowOutput`

`WorkflowOutput` 是 `invoke(...)` 的返回容器，包含两个字段：

- `result`
- `state`

你可以把它理解成“这次执行的结果包”。

### 常见读取方式

```java
WorkflowOutput output = workflow.invoke(inputs, session, null);
Object result = output.getResult();
WorkflowExecutionState state = output.getState();
```

### 典型返回形态

- `state == COMPLETED`：`result` 通常是 `End` 节点整理后的业务输出。
- `state == INPUT_REQUIRED`：`result` 通常是交互相关的输出块集合，调用方需要继续提交 `InteractiveInput`。

## 7. `WorkflowExecutionState`

`WorkflowExecutionState` 是对执行阶段结果的枚举化表达。

| 状态 | 含义 | 调用方通常怎么处理 |
| --- | --- | --- |
| `COMPLETED` | 正常完成 | 读取 `WorkflowOutput.getResult()` |
| `INPUT_REQUIRED` | 当前 workflow 需要更多用户输入 | 读取交互提示，构造 `InteractiveInput` 后继续调用 |
| `ERROR` | 执行失败 | 记录异常或向上抛出错误 |

对入门最重要的是前两个值：

- `COMPLETED` 表示流程收束。
- `INPUT_REQUIRED` 表示流程没有结束，而是进入“等待补充输入”的中间态。

## 8. 流式输出：`WorkflowChunk`、`OutputSchema`、`StreamMode`

Java 工作流的流式执行使用 **同步 `Iterator<WorkflowChunk>`**。

### `WorkflowChunk`

`WorkflowChunk` 是流式块的顶层别名接口。调用方最常见接收到的具体类型是 `OutputSchema`。

### `OutputSchema`

`OutputSchema` 是标准输出块，包含：

- `type`
- `index`
- `payload`

这意味着调用方可以一边遍历 iterator，一边按块刷新界面或日志。

### `StreamMode`

`workflow.stream(...)` 还可以通过 `List<StreamMode>` 指定订阅哪些流：

- `StreamMode.OUTPUT`
- `StreamMode.TRACE`
- `StreamMode.CUSTOM`

其中入门最常用的是 `StreamMode.OUTPUT`。

> 注意：`StreamMode` 表示“你想订阅哪类流”；而 `WorkflowChunkType` 更偏向对块类别的顶层命名。这两者相关，但不是同一个层面的概念。

## 9. `InteractiveInput`

当 `QuestionerComponent` 一类节点要求补充信息时，workflow 可能返回 `INPUT_REQUIRED`。

这时调用方一般会：

1. 读取本次交互提示。
2. 构造 `InteractiveInput`。
3. 用相同 session 再次调用 `workflow.invoke(...)`。

示意写法如下：

```java
InteractiveInput reply = new InteractiveInput();
reply.update("questioner", "2000元");
WorkflowOutput resumed = workflow.invoke(reply, session, null);
```

这里的 `"questioner"` 需要与 workflow 中实际注册的组件 id 保持一致。

## 10. 子工作流：`SubWorkflowComponentImpl`

当一条主流程已经太复杂，或者某段逻辑需要复用时，可以把另一条 `Workflow` 包装成 `SubWorkflowComponentImpl` 后注册到父 workflow 中。

这样做的好处是：

- 复杂流程可以分层组织
- 公共子流程可以复用
- 可视化和结构表达会更清晰

本页只统一概念，不展开嵌套写法细节；后续在组件编排页再深入。

## 这些概念如何串起来

把上面的术语按一次典型执行串起来，其实就是下面这条链路：

1. 用 `WorkflowCard` 描述 workflow 身份和输入。
2. 用 `Workflow` 注册 `Start`、业务节点、`End`。
3. 用普通边、条件边或流式边把节点连成图。
4. 用 `WorkflowSessions` 创建本次执行会话。
5. 调用 `invoke(...)` 得到 `WorkflowOutput`，或者调用 `stream(...)` 得到 `Iterator<WorkflowChunk>`。
6. 如果状态是 `INPUT_REQUIRED`，就用 `InteractiveInput` 在同一会话中恢复执行。

这正是下一页 [构建工作流](构建工作流.md) 的主线。

## 术语边界提醒

为了避免把概念混在一起，入门阶段尤其要记住下面三点：

- `Workflow` 不等于 `WorkflowAgent`：前者是单条图，后者是应用层入口。
- `WorkflowCard` 不等于 session：前者是静态描述，后者是运行时状态。
- `stream(...)` 的块输出不等于 `invoke(...)` 的最终结果：前者强调增量过程，后者强调执行收束后的返回包。
