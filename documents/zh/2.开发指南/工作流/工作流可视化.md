# 工作流可视化

本页只聚焦 Java 当前已经公开的 Mermaid / `DrawableGraph` 可视化路线：工作流搭建完成后，如何把节点和边导出成 Mermaid 文本或图片，用于开发联调、文档留档和问题排查。

如果你还没有搭好第一条 workflow，建议先读 [构建工作流](构建工作流.md)。如果你已经开始关心“图里有哪些现成节点可用”，可与 [使用组件](使用组件/README.md) 结合阅读。

## 可视化入口在哪里

Java 版的可视化入口直接挂在 `Workflow` 上。最常见的三个方法是：

- `workflow.draw()` / `workflow.draw(title)` / `workflow.draw(title, "mermaid", expandSubgraph, enableAnimation)`：返回 Mermaid 文本。
- `workflow.drawBytes(title, "png", expandSubgraph)`：返回 PNG 二进制。
- `workflow.drawBytes(title, "svg", expandSubgraph)`：返回 SVG 二进制。

如果你需要拿到底层图对象，而不是直接要文本或图片，可以继续使用 `workflow.getInternalDrawable()` 进入内部的 `HasDrawable` / `Drawable` 路线。

## 从工作流到 `DrawableGraph` 的路径

Java 当前这条链路可以概括成四层：

1. `Workflow` / `BaseWorkflow` 维护一份实现了 `HasDrawable` 的内部图表示。
2. `HasDrawable.getDrawable()` 返回 `Drawable`。
3. `Drawable` 把节点、边、分支和子图转换成 `DrawableGraph`。
4. `DrawableGraph` 再被导出为 Mermaid 文本，必要时继续渲染为 PNG 或 SVG。

也就是说，**Mermaid 文本和图片都只是同一份图结构的不同输出形式**；真正的“源数据”是 `DrawableGraph`。

## 先认识四个核心类型

| 类型 | 作用 | 你最应该关注什么 |
| --- | --- | --- |
| `Drawable` | 可视化总入口 | 负责收集节点和边，并导出 Mermaid / PNG / SVG。 |
| `DrawableGraph` | 可绘制图模型 | 保存全部 `nodes`、`edges`、开始节点、结束节点和 break 节点。 |
| `DrawableNode` | 节点数据模型 | 至少包含 `id`，也可以带展示名称和元数据。 |
| `DrawableEdge` | 边数据模型 | 除了 `source` / `target`，还会标记这条边是否是条件边、流式边。 |

把这四个类型放到一起理解，基本就能看清 Java 工作流的可视化数据是怎么组织的。

## 嵌套图是怎么表示的

当工作流里出现子工作流或循环时，Java 不会把它们压平处理，而是继续按“图包含图”的方式表示。

- `SubWorkflowComponentImpl` 通过 `getSubWorkflowInternal()` 暴露内部子工作流的可视化对象。
- `LoopComponentImpl` 和 `AdvancedLoopComponentImpl` 通过 `HasDrawable` 暴露循环体子图。
- `DrawableSubgraphNode` 用来保存带内部 `DrawableGraph` 的节点。

因此，可视化页看到的不是“最终执行引擎内部状态”，而是更接近开发者思维模型的图结构。

## Mermaid 文本、PNG、SVG 各自代表什么

### Mermaid 文本

Mermaid 文本是最基础的输出形式，也是最适合开发阶段排查问题的格式。

- 返回值类型是 `String`。
- 内容本质上是一段 `flowchart TD` 脚本。
- 最适合做代码评审、提交 diff、文档粘贴和 issue 复现。
- 如果图里有流式边，`enableAnimation = true` 时 Mermaid 文本会附带动画属性。

对大多数联调场景，先看 Mermaid 文本通常比先导图片更高效，因为你可以直接看出节点 ID、边方向和条件标签。

### PNG

PNG 适合做固定快照，常用于文档插图或即时消息发送。

- 返回值类型是 `byte[]`。
- 需要通过 `drawBytes(..., "png", ...)` 获取，而不是 `draw(...)`。
- Java 当前实现会先生成 Mermaid 文本，再调用 `mermaid.ink` 公共服务渲染成 PNG。
- 如果远端渲染失败，当前实现会返回空字节数组，因此调用方最好先判断长度再落盘或回传。

### SVG

SVG 适合需要缩放、嵌入网页或保留流式边视觉效果的场景。

- 返回值类型同样是 `byte[]`。
- 需要通过 `drawBytes(..., "svg", ...)` 获取。
- 渲染路径与 PNG 一样，都是先生成 Mermaid 文本，再交给 `mermaid.ink`。
- 当前实现会在生成 SVG 前启用流式边动画语义，因此如果图里有 streaming edge，SVG 通常比 PNG 更适合展示这类连接。
- 如果远端渲染失败，当前实现会退回一个包含 Mermaid 文本的简化 SVG 占位结果。

## `expandSubgraph` 的含义

`expandSubgraph` 控制子图展开层级，适合在“只看主干”与“展开全部内部结构”之间切换。

- `0`：不展开子图，只把子工作流或循环体当作一个整体节点看待。
- 正整数：按层级逐步展开，例如 `1` 表示向下展开一层。
- `true`：尽可能完全展开所有子图。

需要注意的是，`workflow.draw(...)` / `workflow.drawBytes(...)` 这一层公共入口并不接受负数作为调用参数；如果传入负数，当前实现会直接抛异常。内部可视化实现会把 `true` 归一化成 `-1`，再交给 Mermaid 导出逻辑做“全部展开”。

如果你只是想先核对主路径是否连对，推荐从 `0` 开始；只有在确认需要排查子图内部边关系时，再提高展开层级。

## 与“构建工作流”页怎么衔接

[构建工作流](构建工作流.md) 的主线是“创建实例 -> 注册组件 -> 连边 -> 执行”。可视化页是在这条主线之后补上一句：**图搭好以后，先把它画出来再执行，排查成本通常更低。**

一个最小衔接示例如下：

```java
import java.nio.file.Files;
import java.nio.file.Path;

String mermaid = workflow.draw("transfer-flow", "mermaid", 0, false);
System.out.println(mermaid);

byte[] png = workflow.drawBytes("transfer-flow", "png", 0);
if (png.length > 0) {
    Files.write(Path.of("transfer-flow.png"), png);
}

byte[] svg = workflow.drawBytes("transfer-flow", "svg", 1);
Files.write(Path.of("transfer-flow.svg"), svg);
```

这一段体现了三个事实：

1. `draw(...)` 负责导出文本，而不是图片。
2. 图片导出要走 `drawBytes(...)`。
3. 可视化展示的就是当前已经注册好的节点和边，所以它很适合在真正执行前检查 `addConnection(...)`、`addConditionalConnection(...)`、`addStreamConnection(...)` 是否符合预期。

## 什么时候优先看可视化

下面几类问题，先导出 Mermaid 往往最省时间：

- 明明注册了组件，但执行路径和预期不一致。
- 条件路由很多，想先确认分支标签和目标节点是否挂对。
- 子工作流或循环体比较复杂，想先确认父子图关系。
- 流式边和普通边混用，想确认哪些连接会走 streaming 路径。
