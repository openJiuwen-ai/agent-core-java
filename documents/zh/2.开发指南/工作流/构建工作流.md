# 构建工作流

本页按 Java 当前真实 API 走一遍最小工作流搭建主线：

1. 创建 `WorkflowCard` 和 `Workflow`
2. 注册 `Start`、业务组件、`End`
3. 建立连接关系
4. 用 `invoke(...)` 执行
5. 在需要时扩展到 `stream(...)`

如果你还不熟悉术语，建议先读 [关键概念](关键概念.md)。如果你想先建立整体定位，可先回看 [概述](概述.md)。

> 说明
>
> - 这里先聚焦 **单条 workflow 的构建和执行**，不展开 `WorkflowAgent` 的多工作流选择。
> - 如果你的业务节点依赖大模型，请先参考 [基础功能 / 接入大模型](../基础功能/接入大模型.md) 准备 `ModelClientConfig` 和 `ModelRequestConfig`。

## 我们要构建什么

主线示例采用 Java 仓库里已经存在的 `QuestionerComponent` 模式：

- `Start` 接收用户输入
- `QuestionerComponent` 负责补齐缺失字段
- `End` 输出最终文本

这条主线沿用 Python 文档中“单条金融 workflow”的教程语义，并映射到 Java 当前真实 API 与测试覆盖的 `QuestionerComponent` 模式，优点是：

- 节点类型都来自当前公开 API
- 可以直接演示 `WorkflowOutput` 和 `WorkflowExecutionState.INPUT_REQUIRED`
- 容易看清“同一 session 恢复执行”这条实际开发中很重要的路径

在主线之后，本页再补一个最小流式扩展示例，说明 `stream(...)` 怎么接入。

## Step 1：定义 `WorkflowCard`

先给 workflow 准备元信息和输入 schema。最常见要素有 `id`、`name`、`version`、`description`、`inputParams`。

```java
import com.openjiuwen.core.workflow.WorkflowCard;
import java.util.List;
import java.util.Map;

Map<String, Object> inputSchema = Map.of(
        "type", "object",
        "properties", Map.of(
                "query", Map.of(
                        "type", "string",
                        "description", "用户输入"
                )
        ),
        "required", List.of("query")
);

WorkflowCard card = WorkflowCard.builder()
        .id("transfer_flow")
        .name("转账服务")
        .version("1.0")
        .description("补齐转账金额并返回最终结果")
        .inputParams(inputSchema)
        .build();
```

这里的 `inputParams` 既是文档描述，也是把 workflow 暴露给更上层能力时的输入说明来源。

## Step 2：创建 `Workflow` 并注册入口节点

有了卡片之后，就可以创建 `Workflow`。入口节点通常使用 `Start`，它的作用是把 workflow 输入透传给后续节点。

```java
import com.openjiuwen.core.workflow.Workflow;
import com.openjiuwen.core.workflow.component.Start;

Workflow workflow = new Workflow(card);
workflow.setStartComp(
        "start",
        new Start(),
        Map.of("query", "${query}"),
        null
);
```

这里的 `inputsSchema` 用的是引用表达式写法：

- `"${query}"` 表示从 workflow 顶层输入读取 `query`
- 后续节点如果要读取 `Start` 的输出，则使用 `"${start.query}"`

## Step 3：注册业务组件

下面以 `QuestionerComponent` 为例。它适合“字段可能缺失，需要在运行时补问”的场景，这也是 Java 源码和测试已经覆盖的真实路径。

示例假定你已经准备好了：

- `ModelClientConfig clientConfig`
- `ModelRequestConfig requestConfig`

它们的构造方式见 [接入大模型](../基础功能/接入大模型.md)。

```java
import com.openjiuwen.core.workflow.component.llm.FieldInfo;
import com.openjiuwen.core.workflow.component.llm.QuestionerComponent;
import com.openjiuwen.core.workflow.component.llm.QuestionerConfig;
import java.util.List;
import java.util.Map;

QuestionerConfig questionerConfig = new QuestionerConfig();
questionerConfig.setModelClientConfig(clientConfig);
questionerConfig.setModelConfig(requestConfig);
questionerConfig.setQuestionContent("请补充转账金额，必须是数字或带货币单位的金额描述。");
questionerConfig.setExtractFieldsFromResponse(true);
questionerConfig.setFieldNames(List.of(
        FieldInfo.builder()
                .fieldName("amount")
                .description("转账金额，必须是数字或带货币单位的金额描述。")
                .required(true)
                .build()
));
questionerConfig.setWithChatHistory(false);
questionerConfig.setMaxResponse(10);

workflow.addWorkflowComp(
        "questioner",
        new QuestionerComponent(questionerConfig),
        Map.of("query", "${start.query}"),
        null
);
```

这里要注意两点：

1. `questioner` 是组件 id，后面恢复交互时会再次用到。
2. `inputsSchema` 只描述“这个节点从哪里取输入”，**并不自动形成执行顺序**；执行顺序还要靠下一步的连边。

## Step 4：注册结束节点并建立连接

结束节点使用 `End`。如果配置了 `responseTemplate`，它会把上游字段渲染成最终返回文本。

```java
import com.openjiuwen.core.workflow.component.End;

workflow.setEndComp(
        "end",
        new End(Map.of(
                "responseTemplate", "转账服务完成，记录的转账金额为 {{amount}}。"
        )),
        Map.of("amount", "${questioner.amount}"),
        null
);

workflow.addConnection("start", "questioner");
workflow.addConnection("questioner", "end");
```

到这里，一条最小线性 workflow 就完整了：

`start -> questioner -> end`

> 关键提醒
>
> - **注册组件** 解决的是“节点是什么”。
> - **连边** 解决的是“节点按什么路径执行”。
>
> 文档或代码里如果只看到了 `addWorkflowComp(...)`，但没有看到 `addConnection(...)` / `addConditionalConnection(...)` / `addStreamConnection(...)`，通常还不能算图已经编排完成。

## Step 5：创建 session 并执行 `invoke(...)`

现在开始执行这条 workflow。对于 `invoke(...)`，最推荐的入门写法是：

- 用 `WorkflowSessions.createWorkflowSession(...)` 创建 session
- 调用 `workflow.invoke(...)`
- 根据 `WorkflowExecutionState` 判断是完成，还是需要补充输入

```java
import com.openjiuwen.core.session.WorkflowSessionApi;
import com.openjiuwen.core.session.interaction.InteractiveInput;
import com.openjiuwen.core.workflow.WorkflowExecutionState;
import com.openjiuwen.core.workflow.WorkflowOutput;
import com.openjiuwen.core.session.internal.WorkflowSessions;
import java.util.Map;

WorkflowSessionApi session = WorkflowSessions.createWorkflowSession("conversation-001");

WorkflowOutput output = workflow.invoke(
        Map.of("query", "我要转账"),
        session,
        null
);

if (WorkflowExecutionState.INPUT_REQUIRED.equals(output.getState())) {
    InteractiveInput reply = new InteractiveInput();
    reply.update("questioner", "2000元");

    output = workflow.invoke(reply, session, null);
}

if (WorkflowExecutionState.COMPLETED.equals(output.getState())) {
    System.out.println(output.getResult());
}
```

这里有三个非常重要的点：

### 1. `invoke(...)` 返回的是 `WorkflowOutput`

也就是说，调用方拿到的不是裸结果，而是：

- `output.getResult()`
- `output.getState()`

### 2. `INPUT_REQUIRED` 不等于失败

当 `QuestionerComponent` 需要继续追问时，workflow 会先返回 `INPUT_REQUIRED`。这表示：

- 图没有执行失败
- 图也没有真正结束
- 调用方应该继续把用户补充信息送回同一 session

### 3. 恢复执行时要复用同一个 session

如果你换了一个新的 session，workflow 就失去了之前已经积累的状态，常见的交互补问链路也就接不上了。

这也是 Java 的 `WorkflowAgent` 与交互恢复测试都会显式保留 session / conversation id 的原因。

## Step 6：把 workflow 扩展到 `stream(...)`

上面的主线展示的是批量执行。接下来只补最关键的一步：**如果某个节点可以产出流式内容，就可以用 `addStreamConnection(...)` + `responseMode = "streaming"` 把它接成流式 workflow。**

最常见的场景是 `LLMComponent`。

### 6.1 注册支持流式输出的节点

```java
import com.openjiuwen.core.workflow.component.llm.LLMCompConfig;
import com.openjiuwen.core.workflow.component.llm.LLMComponent;
import java.util.List;
import java.util.Map;

LLMCompConfig llmConfig = new LLMCompConfig();
llmConfig.setModelClientConfig(clientConfig);
llmConfig.setModelConfig(requestConfig);
llmConfig.setTemplateContent(List.of(
        Map.of("role", "system", "content", "你是一个简洁的助手。"),
        Map.of("role", "user", "content", "{{query}}")
));
llmConfig.setResponseFormat(Map.of("type", "text"));
llmConfig.setOutputConfig(Map.of(
        "answer", Map.of(
                "type", "string",
                "description", "模型回答",
                "required", true
        )
));

Workflow streamWorkflow = new Workflow();
streamWorkflow.setStartComp("start", new Start(), Map.of("query", "${query}"), null);
streamWorkflow.addWorkflowComp(
        "llm",
        new LLMComponent(llmConfig),
        Map.of("query", "${start.query}"),
        null
);
```

### 6.2 把 `End` 切换成 streaming 模式

对流式 workflow 来说，`End` 节点一般需要单独声明 `streamInputsSchema`，并把 `responseMode` 设为 `"streaming"`。

```java
streamWorkflow.setEndComp(
        "end",
        new End(Map.of("responseTemplate", "{{answer}}")),
        null,
        null,
        Map.of("answer", "${llm.answer}"),
        null,
        "streaming"
);

streamWorkflow.addConnection("start", "llm");
streamWorkflow.addStreamConnection("llm", "end");
```

这里要区分两类输入：

- `inputsSchema`：批处理输入
- `streamInputsSchema`：流式输入

在这个例子里，`End` 接收的是 LLM 的增量输出，因此重点是 `streamInputsSchema`。

### 6.3 调用 `stream(...)`

```java
import com.openjiuwen.core.session.stream.OutputSchema;
import com.openjiuwen.core.session.stream.StreamMode;
import com.openjiuwen.core.workflow.WorkflowChunk;
import java.util.Iterator;
import java.util.List;
import java.util.Map;

Iterator<WorkflowChunk> chunks = streamWorkflow.stream(
        Map.of("query", "请用一句话介绍 openJiuwen Java 工作流"),
        WorkflowSessions.createWorkflowSession(),
        null,
        List.of(StreamMode.OUTPUT)
);

while (chunks.hasNext()) {
    WorkflowChunk chunk = chunks.next();
    if (chunk instanceof OutputSchema output) {
        System.out.println(output.getPayload());
    }
}
```

这里要记住一个 Java 版特征：`stream(...)` 返回的是**同步 iterator**。

## 什么时候用 `invoke(...)`，什么时候用 `stream(...)`

| 调用方式 | 更适合什么场景 | 典型返回 |
| --- | --- | --- |
| `invoke(...)` | 一次拿到最终结果；可能包含交互暂停和恢复 | `WorkflowOutput` |
| `stream(...)` | 希望边执行边消费输出 | `Iterator<WorkflowChunk>` |

你可以把它们理解成：

- `invoke(...)` 看重“**完整结果**”
- `stream(...)` 看重“**增量过程**”

## 条件连接、子工作流和后续扩展

本页不深挖这些主题，但你在继续学习时可以按下面的方向扩展：

- **条件连接**：使用 `addConditionalConnection(...)`、`BranchRouter` 或 `BranchComponent` 实现路由分支。
- **子工作流**：使用 `SubWorkflowComponentImpl` 把一条子 `Workflow` 包装成父图中的一个节点。
- **组件目录**：进入 [使用组件](使用组件/README.md) 深入看 `Start`、`End`、`LLMComponent`、`QuestionerComponent` 等组件的配置细节。

## 一页总结

如果把本页压缩成一句话，Java 工作流的主线就是：

1. 创建 `WorkflowCard` 和 `Workflow`
2. 注册 `Start`、业务节点、`End`
3. 用普通边、条件边或流式边连起来
4. 创建 `WorkflowSessions`
5. 根据需要调用 `invoke(...)` 或 `stream(...)`

这条主线掌握后，你再去看组件页、子工作流页或可视化页，会更容易分清“图结构”“组件能力”“运行时输出”三层各自负责什么。
