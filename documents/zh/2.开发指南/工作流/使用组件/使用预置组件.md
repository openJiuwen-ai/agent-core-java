# 使用预置组件

这里聚焦 Java 当前已经公开、稳定、可文档化的工作流预置组件。判断标准很直接：

- 类型能在 `com.openjiuwen.core.workflow.component` 及其公开子包中定位到。
- API 文档和源码都能找到对应定义。
- 用途能被工作流主干页、Java 示例或现有公开类名直接说明。
- 不把 `*Executable`、`Template*`、`*Input` / `*Output`、状态类和内部 helper 写成主推荐入口。

如果你需要先看组件目录分类，回到 [使用组件](README.md)。如果你想把组件放回图里观察边关系，可结合 [工作流可视化](../工作流可视化.md) 一起阅读。

## 先掌握这三个类型

### `Start`

`Start` 是 workflow 的入口节点，职责非常单纯：接收工作流输入，并把输入按映射关系传给后续节点。

它最常出现的位置是：

```java
workflow.setStartComp("start", new Start(), Map.of("query", "${query}"), null);
```

使用 `Start` 时最重要的两点是：

- 它通常不负责业务逻辑，而是负责把顶层 `inputs` 接进图里。
- 你在 `setStartComp(...)` 里写的映射，就是后续节点读取 `${start.xxx}` 的来源。

如果你对一条 workflow 的输入边界还没想清楚，先把 `Start` 配对，通常能让后续组件的输入关系清晰很多。

### `End`

`End` 是 workflow 的出口节点，用来收敛中间结果并生成最终输出。

它既可以直接输出结构化数据，也可以在配置了模板时渲染出最终文本，因此是 Java workflow 中最常见的收口组件。

典型写法如下：

```java
workflow.setEndComp(
        "end",
        new End(Map.of("responseTemplate", "转账服务完成，记录的转账金额为 {{amount}}。")),
        Map.of("amount", "${questioner.amount}"),
        null
);
```

从能力上看，`End` 也是少数同时覆盖多种输出模式的现成组件：

- `invoke`：一次性返回最终结果。
- `stream`：把结果逐段输出。
- `transform`：把上游流式输入逐段转成输出流。
- `collect`：先汇聚流，再生成最终结果。

因此，只要你的 workflow 需要明确的最终返回值，几乎都应该显式配置一个 `End`。

### `IntentDetectionComponent`

`IntentDetectionComponent` 在根包里对应的是一个**语义型抽象基类**，它本身继承自 `BranchComponent`，用于表达“这个节点负责做意图识别并把流程路由到不同分支”。

要注意一点：在 Java 当前公开 API 里，真正适合直接实例化并加入 workflow 的，通常是 `component.llm` 子包下的 `IntentDetectionComponentImpl`，而不是这个抽象基类本身。

最常见的使用路径是：

```java
IntentDetectionComponentImpl detector = new IntentDetectionComponentImpl(config);
detector.addBranch("转账", "transfer_flow");
detector.addBranch("理财", "wealth_flow");
detector.addBranch("余额", "balance_flow");
```

理解它时，可以把它拆成两层：

- `IntentDetectionComponent`：语义和继承层面上的“意图识别路由节点”。
- `IntentDetectionComponentImpl`：Java 当前真正可直接构造、配置分支并注册到图中的实现类。

## 按场景选择常用预置组件

### 对话与模型调用

| 类型 | 适合场景 | 说明 |
| --- | --- | --- |
| `LLMComponent` | 已经知道提示词和输出格式，想直接把一次模型调用接成 workflow 节点 | 负责根据 `LLMCompConfig` 创建真正的执行体。 |
| `QuestionerComponent` | 用户输入不完整，需要在执行过程中追问并恢复同一 session | Java examples 已覆盖这条路径，是工作流交互式补问的核心组件。 |
| `IntentDetectionComponentImpl` | 一条入口后面有多条业务分支，需要先做意图分类 | 内部维护 `BranchRouter`，适合做 workflow 级别路由。 |

这一组组件最适合和 [基础功能 / 接入大模型](../../基础功能/接入大模型.md) 以及 `examples/workflow_agent` 一起看。

### 知识与资源检索

| 类型 | 适合场景 | 说明 |
| --- | --- | --- |
| `KnowledgeRetrievalComponent` | 希望把知识检索结果作为 workflow 的中间节点输出 | 位于 `component.resource` 子包，负责封装检索执行器与输入输出模型。 |

如果你的 workflow 不是“纯 LLM 生成”，而是要先检索再回答，这通常是最直接的资源型组件入口。

### 工具调用

| 类型 | 适合场景 | 说明 |
| --- | --- | --- |
| `ToolComponent` | 已经有 Java `Tool`，想把它作为 workflow 节点调用 | 先通过 `ToolComponentConfig` 指定工具，再用 `bindTool(...)` 绑定实际工具实例。 |

这类组件适合把已有工具体系平滑接回 workflow，而不是把工具调用硬编码进某个自定义节点。

### 组合、复用与循环

| 类型 | 适合场景 | 说明 |
| --- | --- | --- |
| `SubWorkflowComponentImpl` | 希望把一条现有 workflow 当作父图中的一个节点复用 | 它本身实现了 `SubWorkflowComponent`，并且可以流式或批量委派内部子工作流执行。 |
| `LoopComponentImpl` | 需要让一段子图按次数、数组或表达式循环执行 | 是 Java 当前最直接的循环组件实现入口。 |
| `AdvancedLoopComponentImpl` | 需要更细粒度控制循环体、循环中断和回调 | 更偏高级控制入口，适合已经明确要操作循环体和 `LoopController` 的场景。 |

如果你的问题只是“把几步串起来”，通常先不用上循环和子工作流。只有当 workflow 出现明显的复用或重复执行需求时，再引入这一组组件。

## 哪些类型不建议当作主入口

下面这些类型当然仍然有价值，但不建议在“使用预置组件”的主清单里当成第一入口：

- `TemplateBatchProcessor`、`TemplateProcessor`、`TemplateUtils`
- `LLMExecutable`、`QuestionerExecutable`、`ToolExecutable`、`KnowledgeRetrievalExecutable`
- `QuestionerInput`、`QuestionerOutput`、`ToolComponentInput`、`KnowledgeRetrievalOutput` 等输入输出 DTO
- `ComponentConfig`、`IOConfig`、`NodeConfig`、`ComponentState`
- `LoopBreakComponent`、`LoopSetVariableComponent`、`EmptyExecutable`、`PostLoopBody`
- `LoopComponent`、`AdvancedLoopComponent`、`SubWorkflowComponent` 这类抽象接口

原因并不复杂：这些类型更多是在支撑组件运行、描述组件配置，或者服务于高级扩展场景，而不是“读完就能马上开始搭第一条 workflow”的主入口。

## 一个实用的选型顺序

如果你是从零开始搭 Java workflow，通常可以按下面顺序选组件：

1. 先固定入口和出口：`Start` + `End`
2. 再补业务节点：`LLMComponent`、`QuestionerComponent`、`KnowledgeRetrievalComponent` 或 `ToolComponent`
3. 如果出现多分支入口，再引入 `IntentDetectionComponentImpl`
4. 如果出现图复用，再引入 `SubWorkflowComponentImpl`
5. 如果出现重复执行，再考虑 `LoopComponentImpl` 或 `AdvancedLoopComponentImpl`

这个顺序的好处是：你先把最稳定的主干搭起来，再逐步引入更复杂的控制结构。
