# 定义组件输入输出格式

本页只解释 Java 当前工作流组件的输入输出是怎样声明、引用和落到运行时图配置里的。重点不是复述 DTO 字段，而是回答三个更实际的问题：

- 节点到底从哪里取输入。
- 节点执行后的结果怎样暴露给下游。
- 什么时候该关心 `IOConfig`、`ComponentConfig`、`NodeConfig`，什么时候只需要在 `Workflow` 上配 schema。

如果你还没有搭过第一条 workflow，建议先读 [构建工作流](../构建工作流.md)。如果你已经开始区分 batch / stream 能力，建议再配合 [组件支持的能力类型](组件支持的能力类型.md) 一起看。

## Java 当前的主入口在哪里

Java 版没有把组件 I/O 单独做成一套链式 builder。当前最常见、也是最推荐的入口仍然是 `Workflow` 自身：

- `setStartComp(...)`：给起点节点声明输入映射。
- `addWorkflowComp(...)`：给中间节点声明 batch / stream 输入输出映射。
- `setEndComp(...)`：给结束节点声明收口输入，并在需要时声明 stream 输入和响应模式。

也就是说，**日常写 workflow 时，你大多数时候并不需要手动 new `IOConfig` 或 `NodeConfig`**。这些类型主要由 `BaseWorkflow` 在注册节点时自动组装进内部 `workflowSpec`。

## 先分清三层含义

| 层次 | 代表类型 | 你最该关心什么 |
| --- | --- | --- |
| 工作流注册入口 | `Workflow.setStartComp(...)`、`addWorkflowComp(...)`、`setEndComp(...)` | 真正决定节点如何接收输入、暴露输出。 |
| 节点 I/O 描述壳 | `IOConfig` | 保存一组 `inputsSchema` + `outputsSchema`，分别对应 batch 或 stream 方向。 |
| 节点规格描述 | `NodeConfig`、`ComponentConfig` | `NodeConfig` 组合能力列表与 batch / stream 两套 `IOConfig`；`ComponentConfig` 更偏公共配置壳和 metadata，不是日常 I/O 绑定入口。 |

把这三层拆开后，阅读 Java workflow 源码会容易很多：

- 你在 `Workflow` 上写的 schema 是“开发者入口”。
- `IOConfig` / `NodeConfig` 是“内部记录形式”。
- `ComponentConfig` 不是给你单独描述上下游引用关系的主要位置。

## 引用表达式是 I/O 组织的核心

Java 当前公开 API 里，组件输入输出格式主要靠 **schema + 引用表达式** 描述，不额外暴露单独的 I/O 转换 DSL。

最常见的几种引用方式如下：

- `${query}`：读取 workflow 顶层输入里的 `query`。
- `${inputs}` 或 `${inputs.message}`：读取名为 `inputs` 的顶层对象，或它的嵌套字段。
- `${start.query}`：读取上游节点 `start` 的输出字段 `query`。
- `${loop.answers[0]}`：读取数组输出里的某个下标，当前系统测试已经覆盖这种写法。

可以把它理解成一句规则：**schema 的 value 负责“告诉当前节点去哪里拿值”，schema 的 key 负责“告诉当前节点本地把它叫成什么名字”。**

## batch 输入输出怎么声明

线性 workflow 最常见的是 batch 输入和 batch 输出。下面这个例子与 Java 仓库里 `QuestionerComponent` 的真实接法一致：

```java
Workflow workflow = new Workflow(card);
workflow.setStartComp("start", new Start(), Map.of("query", "${query}"), null);

workflow.addWorkflowComp(
        "questioner",
        new QuestionerComponent(questionerConfig),
        Map.of("query", "${start.query}"),
        null
);

workflow.setEndComp(
        "end",
        new End(Map.of("responseTemplate", "转账服务完成，记录的转账金额为 {{amount}}。")),
        Map.of("amount", "${questioner.amount}"),
        null
);

workflow.addConnection("start", "questioner");
workflow.addConnection("questioner", "end");
```

这段代码里有三层 I/O 关系：

1. `Start` 把顶层输入里的 `query` 收进来。
2. `questioner` 从 `${start.query}` 读取上游输出。
3. `End` 再从 `${questioner.amount}` 读取字段，渲染最终模板。

这里没有单独写 `outputsSchema`，因为 `QuestionerComponent` 已经直接产出下游要消费的字段。如果你想把组件真实返回字段重命名后再暴露给下游，才需要显式配置 `outputsSchema`。

## batch 和 stream 可以同时存在

Java 当前 `addWorkflowComp(...)` 一次就能声明四组 schema：

- `inputsSchema`
- `outputsSchema`
- `streamInputsSchema`
- `streamOutputsSchema`

这意味着同一个节点可以同时面对 batch 路径和 stream 路径。仓库测试里最典型的场景是：

- 上游组件 `a` 通过 `stream()` 产生流式帧。
- 中间组件 `b` 用 `streamInputsSchema` 接流。
- 结束节点 `end` 再决定是收口成 batch，还是继续以 streaming response 输出。

下面给一个只依赖公开 API 的最小骨架。这里的 `producer` 是一个自定义 `WorkflowComponent`，它接收 batch 输入并通过 `stream(...)` 向下游连续吐出帧：

```java
WorkflowComponent producer = new WorkflowComponent() {
        @Override
        @SuppressWarnings("unchecked")
        public Iterator<Object> stream(Object inputs, NodeSessionApi session, ModelContext context) {
                Map<String, Object> inputMap = (Map<String, Object>) inputs;
                List<Object> frames = new ArrayList<>();
                for (Object item : (List<Object>) inputMap.get("array")) {
                        frames.add(Map.of("output", item));
                }
                return frames.iterator();
        }
};

workflow.addWorkflowComp(
        "producer",
                producer,
        true,
                Map.of("array", "${start.array}"),
        null,
                null,
        Map.of("chunk", "${output}"),
        List.of(ComponentAbility.STREAM)
);

workflow.setEndComp(
        "end",
        new End(),
        null,
        Map.of("chunk", "${producer.chunk}"),
        null,
        "streaming"
);
```

这个骨架说明了两件关键事实：

- 同一个节点可以在保留 batch 输入的同时，对外暴露 stream 结果。
- 结束节点是否以流式方式返回，不只取决于边，还取决于 `responseMode = "streaming"`。

如果你还希望这个 `producer` 同时向 batch 下游暴露一个重命名后的最终字段，可以在上面的 `outputsSchema` 位置再补一层 batch 输出映射。

## `IOConfig`、`NodeConfig`、`ComponentConfig` 各自该怎么看

### `IOConfig`

`IOConfig` 只保存一对 schema：

- `inputsSchema`
- `outputsSchema`

它本身并不负责执行，也不决定节点顺序。你可以把它看成“某一条 I/O 通道的描述壳”。在 `BaseWorkflow.addWorkflowComp(...)` 里，batch schema 会被包装成一份 `IOConfig`，stream schema 会再包装成另一份 `IOConfig`。

### `NodeConfig`

`NodeConfig` 是节点级别的规格说明，里面组合了：

- `abilities`
- `ioConfigs`
- `streamIoConfigs`

因此它更像“这个节点在工作流图里的配置快照”。如果你是在读 API 文档或调试 `workflowSpec`，它很关键；如果你只是写业务 workflow，通常只需要在 `Workflow` 层配参数，让框架自动生成它。

### `ComponentConfig`

`ComponentConfig` 当前更偏公共配置壳，核心字段是 `metadata`。它并不替代 `NodeConfig` 去描述上下游 schema，也不是当前 Java workflow 中输入输出绑定的主入口。

换句话说：

- 想表达“节点有哪些 I/O schema”，看 `NodeConfig` / `IOConfig`。
- 想表达“我在写 workflow 时怎么配”，直接看 `Workflow` 的注册方法。
- 想表达“组件本身的公共配置或 metadata”，再看 `ComponentConfig`。

## Java 当前的两个校验约束

`BaseWorkflow` 在注册组件时已经做了两类很关键的 I/O 校验：

### 1. batch 和 stream schema 不能重名冲突

如果同一个节点里：

- `inputsSchema` 和 `streamInputsSchema` 展平后出现相同 key，或者
- `outputsSchema` 和 `streamOutputsSchema` 展平后出现相同 key，

当前实现会直接报错。

这意味着最稳妥的做法是：**batch 字段和 stream 字段尽量语义化分开命名，不要复用同一层 key。**

### 2. I/O schema 只负责数据映射，不负责执行顺序

即使你已经写了 `${start.query}`、`${questioner.amount}` 这样的引用，如果没有再补：

- `addConnection(...)`
- `addStreamConnection(...)`
- `addConditionalConnection(...)`

图仍然没有真正编排完成。

所以，schema 解决的是“值从哪来”，边解决的是“节点什么时候跑”。

## 三种最常见的 I/O 组织方式

### 1. 入口节点只做字段对齐

`Start` 最适合把顶层输入统一命名，然后让后续节点都只面向 `${start.xxx}` 编程。这样后面即使调用方的顶层字段名变化，也只需要改入口节点。

### 2. 中间节点按业务语义重命名

如果某个节点返回的是底层字段名，比如 `output`、`result` 这类通用字段，建议在 `outputsSchema` 这一层就把它重命名成更稳定的业务名，再交给下游。

### 3. batch 和 stream 分成两套消费口径

当同一个组件既能提供最终结果，也能提供增量片段时，推荐让 batch 和 stream 各自有清晰命名，而不是让下游猜测应该消费哪一路数据。

## 当前边界

- Java 当前公开 workflow API 主要围绕 schema 和引用表达式；仓库里没有公开的 `inputsTransformer` / `outputsTransformer` 注册入口。
- `IOConfig`、`NodeConfig`、`ComponentConfig` 更适合用来理解内部规格和 API 形态，不是第一步就要直接实例化的业务入口。
- 能力类型和 batch / stream 的调用语义，放到 [组件支持的能力类型](组件支持的能力类型.md) 继续展开。
