# 编排组件

本页只讨论 Java 当前 workflow 的“图是怎么搭起来的”：节点注册之后，普通边、流式边、条件路由、子工作流和循环怎样组合，才能形成一条可执行的组件链路。

如果你当前还没有区分节点的输入输出或能力类型，建议先读 [定义组件输入输出格式](定义组件输入输出格式.md) 和 [组件支持的能力类型](组件支持的能力类型.md)。

## 编排解决的不是“节点是什么”，而是“节点怎么连”

写 Java workflow 时，至少要同时完成三件事：

1. 注册节点：`setStartComp(...)`、`addWorkflowComp(...)`、`setEndComp(...)`
2. 配好 schema：让节点知道自己从哪里取值、向下游暴露什么字段
3. 建立边关系：让执行器知道该按什么路径调度节点

很多初学者会把第 2 步和第 3 步混在一起。最简单的判断方法是：

- `Map.of("amount", "${questioner.amount}")` 这类 schema，解决的是“读哪个值”。
- `addConnection("questioner", "end")` 这类调用，解决的是“何时执行到 end”。

两者缺一不可。

## Java 当前有哪些编排入口

`Workflow` 当前最关键的三个图级方法是：

- `addConnection(Object srcCompId, String targetCompId)`
- `addStreamConnection(String srcCompId, String targetCompId)`
- `addConditionalConnection(String srcCompId, Object router)`

其中前两个会直接落到 `ConnectionType` 对应的边语义：

- `CONNECTION`：普通边
- `STREAM_CONNECTION`：流式边

要特别注意一点：**条件路由是 Java 当前的图级编排能力，但它并不额外对应一个 `ConnectionType` 枚举值。** 它是通过 `addConditionalConnection(...)` 加上 router 来表达的，而不是单独的边类型常量。

## 普通边：最基础的 batch 编排

普通边用 `addConnection(...)` 建立，适合：

- `Start -> 业务节点`
- `业务节点 -> End`
- `COLLECT` 之后继续流回普通 batch 节点

最常见的线性主干就是：

```java
workflow.addConnection("start", "questioner");
workflow.addConnection("questioner", "end");
```

如果一条路径上所有节点都按 batch 方式工作，普通边通常已经足够。

## 流式边：让 chunk 真正往下游流动

流式边用 `addStreamConnection(...)` 建立。它的作用不是“让节点变成流式”，而是**告诉图执行器，这条边上传递的是 stream，而不是一次性结果。**

仓库测试里的典型链路是：

```java
flow.addConnection("start", "a");
flow.addStreamConnection("a", "b");
flow.addStreamConnection("b", "c");
flow.addConnection("c", "end");
```

这条链路对应的角色关系很清楚：

- `a` 负责 `STREAM`
- `b` 负责 `TRANSFORM`
- `c` 负责 `COLLECT`
- `end` 再以 batch 方式收口

因此，看到流式边时，你应该立刻去检查两个问题：

1. 上游节点有没有 `STREAM` 或 `TRANSFORM` 能力。
2. 下游节点是不是在用 `streamInputsSchema` 消费这条边。

## 条件路由：在图上选下一条路径

Java 当前提供了两种常见条件编排方式。

### 1. 直接给 `addConditionalConnection(...)` 传函数 router

这条路径在 `WorkflowTest` 中已有覆盖。最小思路是：

- 上游节点先把需要判断的字段写进 session / state
- router 再根据当前 state 决定返回哪个目标节点 id

```java
flow.addConditionalConnection("start", (Function<Object, Object>) sessionObj -> {
    RouterSession session = (RouterSession) sessionObj;
    if (session.getGlobalState("start.a") != null) {
        return "a";
    }
    return "b";
});
```

### 2. 使用 `BranchRouter` 或 `BranchComponent`

如果你的路由条件更适合声明式表达，Java 当前更推荐 `BranchRouter` / `BranchComponent` 路线：

```java
BranchRouter router = new BranchRouter();
router.addBranch("${start.a} is not None", "a", null);
router.addBranch("${start.b} is not None", "b", null);
flow.addConditionalConnection("start", router);
```

或者把它做成图里的一个显式节点：

```java
BranchComponent branch = new BranchComponent();
branch.addBranch("${a} <= 10", List.of("b"), "small");
branch.addBranch("${a} > 10", List.of("a"), "big");

flow.addWorkflowComp("sw", branch);
flow.addConnection("start", "sw");
```

这两条路径的区别在于：

- `addConditionalConnection(...)` 更像“从某个节点发出条件路由”。
- `BranchComponent` 更像“把路由决策本身做成图里的一个节点”。

## 合流时要考虑 `waitForAll`

多前驱汇总时，编排不只是在图上把边都画过去，还要明确目标节点是否要等待全部前驱结果。

仓库里的 `createWaitForAllWorkflow(...)` 测试已经说明：同一个 `collect` 节点，`waitForAll = true` 和 `false` 会得到不同结果。

这在两类场景里尤其关键：

- 一个 batch 节点要汇总多个普通前驱
- 一个 `COLLECT` / `TRANSFORM` 节点要稳定消费流式输入

对 Java 当前实现来说，一个足够稳妥的经验是：

- 只要你在做合流、聚合、变换，就主动检查 `waitForAll`。
- 只要节点声明了 `COLLECT` 或 `TRANSFORM`，`waitForAll` 必须为 `true`。

## 子工作流：把整条 workflow 当成一个节点接进父图

当某一段逻辑已经能单独构成一条 workflow 时，Java 当前最直接的复用方式是 `SubWorkflowComponentImpl`。

最小结构如下。为了让例子自包含，下面直接用匿名 `WorkflowComponent` 做一个“原样返回输入”的中间节点：

```java
WorkflowComponent passthrough = new WorkflowComponent() {
    @Override
    public Object invoke(Object inputs, NodeSessionApi session, ModelContext context) {
        return inputs;
    }
};

Workflow innerFlow = new Workflow();
innerFlow.setStartComp("inner_start", new Start(), Map.of("value", "${value}"), null);
innerFlow.addWorkflowComp("inner_process", passthrough, Map.of("value", "${inner_start.value}"), null);
innerFlow.setEndComp("inner_end", passthrough, Map.of("value", "${inner_process.value}"), null);
innerFlow.addConnection("inner_start", "inner_process");
innerFlow.addConnection("inner_process", "inner_end");

Workflow outerFlow = new Workflow();
outerFlow.setStartComp("start", new Start(), Map.of("value", "${value}"), null);
outerFlow.addWorkflowComp("sub", new SubWorkflowComponentImpl(innerFlow), Map.of("value", "${start.value}"), null);
outerFlow.setEndComp("end", new End(), Map.of("result", "${sub.value}"), null);
outerFlow.addConnection("start", "sub");
outerFlow.addConnection("sub", "end");
```

这里要抓住两个关键点：

- 父图仍然把 `sub` 当成普通节点连边。
- 子图内部怎么执行，由 `SubWorkflowComponentImpl` 负责委派，不需要父图手动展开每个内部节点。

如果你还想把父子图一起画出来，可以再配合 [工作流可视化](../工作流可视化.md) 查看展开效果。

## 循环：把一段子图反复执行

Java 当前的循环编排至少有两层入口：

- `LoopComponentImpl`：更接近“把一个循环组作为节点接进图里”的用法
- `AdvancedLoopComponentImpl`：更接近“直接控制循环体、条件和回调”的高级入口

仓库测试里两种路线都能找到依据。

### 用 `LoopComponentImpl` 包装循环组

在中断恢复系统测试里，循环组件的接法是：

```java
outerWorkflow.addWorkflowComp(
        "loop",
        new LoopComponentImpl(loopGroup, Map.of("answers", "${sub.answer}")),
        Map.of("loop_type", "number", "loop_number", 1),
        null
);
```

这说明父图只需要把：

- 循环类型
- 循环次数 / 数组 / 表达式
- 最终输出映射

作为当前节点的输入和输出来理解即可。

### 用 `AdvancedLoopComponentImpl` 直接控制循环体

在 `WorkflowTest` 中，`AdvancedLoopComponentImpl` 直接接收：

- `LoopGroup`
- 循环条件
- break 节点列表
- 循环回调

这条路径更适合你已经明确要操作循环体内部状态或回调逻辑，而不只是“重复执行几次”。

## 一个实用的编排顺序

如果你是从零开始搭一条稍复杂的 Java workflow，下面这套顺序通常最稳：

1. 先用 `Start` 和 `End` 固定入口出口。
2. 再把中间节点加进来，并在注册时配好 schema。
3. 先用 `addConnection(...)` 走通 batch 主线。
4. 只有确定需要流式链路时，再补 `addStreamConnection(...)`。
5. 如果出现分支，再引入 `BranchRouter`、`BranchComponent` 或函数 router。
6. 如果出现图复用或重复执行，再引入 `SubWorkflowComponentImpl`、`LoopComponentImpl` 或 `AdvancedLoopComponentImpl`。
7. 最后用 [工作流可视化](../工作流可视化.md) 检查整张图再执行。

## 编排前的四项自检

- 节点 id 是否只使用字母、数字、下划线或连字符。
- batch schema 和 stream schema 是否出现同名 key 冲突。
- `COLLECT` / `TRANSFORM` 节点是否已经显式设置 `waitForAll = true`。
- 每个 schema 引用背后是否真的有对应的 `addConnection(...)`、`addStreamConnection(...)` 或条件路由。

## 当前边界

- 这里聚焦图级编排，不展开组件内部实现、提示词、模型配置或多工作流 agent 路由。
- `ConnectionType` 当前只覆盖普通边和流式边；条件路由属于编排 API 语义，不是第三个枚举值。
- 组件具体有哪些能力、schema 应该怎样命名，分别放在 [组件支持的能力类型](组件支持的能力类型.md) 和 [定义组件输入输出格式](定义组件输入输出格式.md) 继续展开。
