# 组件支持的能力类型

本页只解释 Java 当前 workflow 里的 `ComponentAbility` 到底代表什么，以及它怎样影响组件的调用方式、可用连接和 `waitForAll` 约束。

如果你还没有先看过组件目录，建议先读 [使用组件](README.md)。如果你当前最关心的是“这些能力在图里怎么连”，请继续读 [编排组件](编排组件.md)。

## 先抓住一个核心判断

Java 当前的四种能力，本质上就是四种输入输出形态：

| 能力 | 输入形态 | 输出形态 | 对应方法 |
| --- | --- | --- | --- |
| `INVOKE` | batch | batch | `invoke(...)` |
| `STREAM` | batch | stream | `stream(...)` |
| `COLLECT` | stream | batch | `collect(...)` |
| `TRANSFORM` | stream | stream | `transform(...)` |

这张表比任何组件名单都更重要，因为它直接决定了运行时该调用组件的哪个方法。

## Java 当前的枚举定义

`ComponentAbility` 位于 `com.openjiuwen.core.workflow.component`，当前公开的四个枚举值分别带有很直接的描述：

- `INVOKE("invoke", "batch in, batch out")`
- `STREAM("stream", "batch in, stream out")`
- `COLLECT("collect", "stream in, batch out")`
- `TRANSFORM("transform", "stream in, stream out")`

也就是说，Java 这里没有额外的“半流式”或“异步批处理”能力名词，判断标准就是输入和输出是否是流。

## 四种能力分别适合什么场景

### `INVOKE`

`INVOKE` 是最普通的 batch 节点。它拿到完整输入，执行一次，然后返回完整输出。

最常见的场景有：

- `Start` 透传顶层输入。
- `QuestionerComponent` 读取当前输入并返回字段结果或中断请求。
- `ToolComponent` 执行一次工具调用。
- 大多数只需一次性返回结果的自定义节点。

如果一条边前后都是普通 batch 数据，默认先从 `INVOKE` 思维开始理解，通常不会错。

### `STREAM`

`STREAM` 表示组件接收完整输入，但不是一次性返回结果，而是逐块产生输出帧。

仓库测试里最典型的例子是 `ProducerNode`：

- 输入是完整数组。
- 输出是逐个元素产生的 `output` 帧。

这一类节点的典型连接方式是：

- 上游通过 `addConnection(...)` 把 batch 数据送进来。
- 下游通过 `addStreamConnection(...)` 消费流。

对大模型节点来说，如果你希望它把 token / chunk 持续往后推，理解成 `STREAM` 最合适。

### `COLLECT`

`COLLECT` 和 `STREAM` 刚好相反：它吃的是流，吐的是一次性结果。

最典型的用途是：

- 把上游多帧输出汇总成一个最终值。
- 把多个 stream chunk 聚合成字符串、数组或统计结果。
- 让结束节点在接收流之后统一返回一个 batch 结果。

仓库测试里的 `CollectCompNode` 就是这条路径：

- 通过 `streamInputsSchema` 读取上游流。
- 在 `collect(...)` 中遍历所有帧。
- 最后一次性返回聚合结果。

### `TRANSFORM`

`TRANSFORM` 表示组件消费流，并继续输出流。它适合做逐帧改写、过滤、补充字段或重新包装。

典型用途包括：

- 对 LLM streaming chunk 做逐段清洗。
- 给上游流添加统一结构壳。
- 在不打断流式链路的前提下插入中间处理节点。

仓库测试里的 `TransformCompNode` 就是这个模型：上游每来一帧，它就处理一帧，再继续往下游发出去。

## 一张足够实用的判断表

如果你不想先背能力名，直接按“输入是不是流、输出是不是流”来判断也可以：

| 当前节点看到的输入 | 当前节点要产出的输出 | 优先考虑的能力 |
| --- | --- | --- |
| 普通对象 / Map | 普通对象 / Map | `INVOKE` |
| 普通对象 / Map | 多个 chunk | `STREAM` |
| 多个 chunk | 普通对象 / Map | `COLLECT` |
| 多个 chunk | 多个 chunk | `TRANSFORM` |

这也是为什么文档里总是把能力页和连边页放在一起看。能力本身描述的是 I/O 形态，而图上的边会把这种形态真正落实成执行路径。

## Java 当前怎样声明能力

### 普通中间节点

对中间节点来说，能力通常通过 `addWorkflowComp(...)` 最后一个参数显式声明。下面沿用 `WorkflowTest` 里的 `TransformCompNode` 测试节点命名，它代表一个实现了 `transform(...)` 的自定义 `WorkflowComponent`：

```java
workflow.addWorkflowComp(
        "b",
        new TransformCompNode(),
        true,
        Map.of("value1", "${a.value}"),
        null,
        Map.of("value", "${a.value}"),
        null,
        List.of(ComponentAbility.TRANSFORM)
);
```

这类写法最常见于：

- 自定义节点
- 需要显式声明 `STREAM` / `COLLECT` / `TRANSFORM` 的兼容测试和高级编排

### 结束节点

`End` 比较特殊。Java 当前 `Workflow.setEndComp(...)` 会根据 `responseMode` 和 `streamInputsSchema` 自动推导结束节点能力：

- 默认情况：至少带 `INVOKE`
- 默认模式但声明了 `streamInputsSchema`：再补 `COLLECT`
- `responseMode = "streaming"` 且只有 batch 输入：使用 `STREAM`
- `responseMode = "streaming"` 且有 stream 输入：使用 `TRANSFORM`

也就是说，结束节点不一定总是“批量返回最终值”，它也可以成为流式链路的一部分。

## `waitForAll` 不是可选知识点

Java 当前实现对 `TRANSFORM` 和 `COLLECT` 有一个明确约束：

- 只要组件声明了 `TRANSFORM` 或 `COLLECT`
- `waitForAll` 就必须为 `true`

这是 `BaseWorkflow.validateCompAbility(...)` 的硬校验，不满足会直接报错。

原因也很直接：

- `TRANSFORM` / `COLLECT` 都依赖完整的流式输入通道准备好。
- 如果不等待必要的上游，就很难保证输入流是可消费的。

因此，在 Java workflow 里，看到 `COLLECT` / `TRANSFORM` 时，应该立刻联想到 `waitForAll = true`。

## 连接方式和能力的对应关系

只看能力名还不够，你还需要知道它在图里通常怎么接：

| 能力 | 上游常见连接 | 下游常见连接 |
| --- | --- | --- |
| `INVOKE` | `addConnection(...)` | `addConnection(...)` |
| `STREAM` | `addConnection(...)` | `addStreamConnection(...)` |
| `COLLECT` | `addStreamConnection(...)` | `addConnection(...)` |
| `TRANSFORM` | `addStreamConnection(...)` | `addStreamConnection(...)` |

这不是“文档建议”，而是由输入输出形态自然推出来的结果。

## 内建组件怎么理解能力

这里不重复完整组件清单，只给出最重要的理解方式：

- `Start` 可以先按 `INVOKE` 理解，它负责把顶层输入送进图里。
- `QuestionerComponent`、`ToolComponent` 这类典型业务节点，优先按 `INVOKE` 理解。
- `LLMComponent` 在需要流式输出时，可以落到 `STREAM` 路径。
- `End` 是最特殊的一个，它可能表现为 `INVOKE`、`STREAM`、`COLLECT` 或 `TRANSFORM`，由 `setEndComp(...)` 的参数决定。
- `SubWorkflowComponentImpl` 既实现了 `invoke(...)` 也实现了 `stream(...)`，因此它可以作为可复用子图节点接进 batch 或 stream 路径。

如果你已经在 [使用预置组件](使用预置组件.md) 建立过组件印象，这里的重点就不是“还有哪些组件”，而是“同一个组件在不同图结构里可能以什么方式被调用”。

## 一个最小的能力链路示例

仓库测试里有一条非常适合拿来理解能力协作的链路：

`start -> a -> b -> c -> end`

其中：

- `a` 是 `STREAM`
- `b` 是 `TRANSFORM`
- `c` 是 `COLLECT`
- `end` 是普通 batch 收口

它说明了能力页里最核心的一件事：**能力并不是孤立标签，而是描述节点在整条数据链路中的角色。**
