# 预置协作模式

Java 当前仓库并没有提供一组完整的“内置团队模式”框架类。当前源码、API 文档和 examples 能共同证明的，是几种可组合的协作结构。下面按 `当前支持`、`示例支持` 和 `当前未内置` 区分这些真实存在的路径。

## 功能定位

如果你已经理解了 [AgentAsTool](AgentAsTool.md) 和 [AgentTeams](AgentTeams.md) 的基础入口，本页要解决的是“现在到底能怎么协作”。答案不是单一模式，而是几条层次不同的路径：

1. 宿主 Agent 把子能力暴露成可调用能力
2. 自己继承 `BaseGroup` 组织一个团队边界
3. 使用 legacy `ControllerGroup` 做消息路由
4. 参考 `hierarchical_group` 的 leader-worker 示例

## 当前可验证的协作模式

| 模式 | 主要入口 | 状态 | 适用场景 |
| --- | --- | --- | --- |
| 能力暴露式协作 | `AbilityManager`、`LlmAgent`、`WorkflowAgent` | 当前支持 | 一个宿主 Agent 统一调度子能力 |
| 自定义 group 协作 | `BaseGroup`、`GroupCard`、`GroupConfig`、`Session` | 当前支持 | 需要稳定公共 API 和明确团队边界 |
| controller 路由协作 | `ControllerGroup`、`BaseGroupController` | 示例支持 | 需要点对点、订阅广播或兼容旧路由语义 |
| leader-worker 分层示例 | `examples/groups/hierarchical_group` | 示例支持，仅示例层 | 需要一个能运行的层级协作样例 |
| 更高层预置团队族 | `Hierarchical Tools`、`Hierarchical MessageBus`、`Handoff` 等协作结构 | 当前未内置 | 当前 Java 仓库没有对应正式框架实现 |

## 1. 能力暴露式协作

这是当前最轻量的协作方式：不先创建一个独立团队对象，而是让宿主 Agent 通过 `AbilityManager` 调用子能力。

它的典型形态是：

- 子 `Tool` 注册为可调用工具
- 子 `Workflow` 注册为可调用工作流
- 子 `Agent` 注册为 `AgentCard`，再由宿主 Agent 像工具一样发起调用

这种模式的特点是：

- 结构最简单，调用关系天然围绕一个宿主 Agent 展开
- 模型可直接在同一个 `ToolInfo` 列表里选择子能力
- 适合“主管 Agent 统一调度多个专长能力”的场景

它的边界也很明确：

- 更像“单个宿主 Agent 的能力树”，不是独立的团队运行时
- 成员之间的消息转发、广播和恢复语义，需要你自己在宿主逻辑里组织

如果你要写“leader 调多个 specialist”的轻量协作页，这通常是最稳的第一选择。

## 2. 自定义 group 协作

当你需要一个真正的“团队边界”时，推荐改用 `BaseGroup`：

- `GroupCard` 描述团队身份
- `GroupConfig` 描述运行阈值
- `BaseGroup` 管理成员注册与执行入口
- `Session` / `MultiAgentSessions` 承载团队级会话

这条路径的优点是：

- 属于当前 `multiagent` 包的正式公共 API
- 团队成员、会话、执行边界清晰
- 后续如果要把团队注册为资源，也能直接接上 `Runner.resourceMgr().addAgentGroup(...)`

这条路径不直接赠送一个现成的协作策略。换句话说，Java 当前支持“建团队骨架”，但 leader 怎么分发、worker 怎么协同，仍然要由你自己的 group 子类决定。

## 3. controller 路由协作

如果你需要更接近“消息驱动团队”的语义，当前最贴近仓库事实的入口仍然是 legacy `ControllerGroup + BaseGroupController`：

- `ControllerGroup` 负责把外部输入归一化成 `GroupEvent`
- `BaseGroupController` 负责消息队列、显式路由、订阅关系与广播
- `sendToAgent(...)` 会把消息点对点送到指定成员
- `publish(...)` 会按 `customEventType` 找到订阅者，并用虚拟线程并发调用

这条路径适合：

- 你正在解释现有 legacy 协作能力
- 你需要“显式 receiver_id / publish-subscribe”这样的路由语义
- 你在阅读或维护 `examples/groups/hierarchical_group`

但它不是推荐的新主线，因为：

- 相关类型都带 `@Deprecated`
- 它更偏兼容层和运行时路由，而不是新的团队公共 API

## 4. leader-worker 分层示例

`examples/groups/hierarchical_group` 是当前 Java 仓库里最具体的协作样例。它能验证的是一个 example 层 leader-worker 结构：

1. 外部请求先进入 group
2. `HierarchicalGroupController` 优先处理显式 `receiver_id`
3. 如果命中了订阅类型，则走 `publish(...)`
4. 否则默认路由给 leader `main_controller`
5. `HierarchicalLeaderAgent` 再根据关键词把任务分派到具体 worker
6. 如果 worker 触发交互中断，leader 会在 session state 里记录 `pending_worker_id`，让下一轮用户回复继续回到原 worker

这条模式的定位很重要：

- 它能说明 Java 已经具备 leader-worker 协作的可运行样例
- 它不能说明 Java 已经有一个正式公开的 `HierarchicalGroup` / `HierarchicalTeam` 框架类
- 这里的 leader 路由是示例内的确定性关键词分发，不是完整的 LLM intent detection 主线

因此本页把它标成“等价支持，但仅示例层”。

## 5. 当前未内置的协作结构

下面这些常见协作结构，在当前 Java 仓库里都不属于“已正式支持”的内置能力：

- `Hierarchical Tools`
- `Hierarchical MessageBus`
- `Handoff`
- 一体化的 team factory / transport / storage 生命周期框架

当前 Java 最接近它们的现实对应是：

- `Hierarchical Tools` 更接近“能力暴露式协作 + 宿主 Agent 调度”
- `Hierarchical MessageBus` 更接近“controller 路由协作 + publish-subscribe 能力”
- `Handoff` 目前没有一个同名、同语义的正式框架落点

更准确的理解方式是：这些需求可以用现有能力近似实现，但 Java 当前并没有内置同名框架。

## 选型建议

- 如果你要一个最轻量、最接近今天可落地的协作入口，先用能力暴露式协作。
- 如果你需要清晰的团队边界和正式公共 API，优先用 `BaseGroup`。
- 如果你要解释 legacy 路由或复用现有 example，使用 `ControllerGroup` / `BaseGroupController`。
- 如果你需要现成的高层团队族，先按“Java 当前未内置”理解，再从现有能力组合落地。
