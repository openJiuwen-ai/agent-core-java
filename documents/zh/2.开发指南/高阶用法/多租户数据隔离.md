# 多租户数据隔离

多租户数据隔离让同一个 DeepAgent / Runner 进程在为不同租户（tenant）服务时，把工作区、临时文件、检查点、KV 状态、长期记忆、Skill 等数据按 `tenantId` 隔离开，互不可见、互不可越界。它从 `0.1.7` 开始提供，核心代码位于 `com.openjiuwen.core.multitenant`。

隔离能力是**按开关分层**的：默认关闭（`enableTenantIsolation=false`），行为与历史完全一致、零迁移成本；一旦开启即进入**严格模式**，调用入口必须显式携带有效 `tenantId`，否则直接抛 `IllegalStateException` 快速失败，避免「以为隔离了其实没隔离」的隐蔽缺陷。

> 本页以 Java 当前公开 API、配置项和测试覆盖范围为准。设计依据见仓库 `yoskills/jiuwen/jobs/issue29/多租户数据隔离设计规格-整合版.md`。

## 核心角色

| 类型 | 作用 | 你通常什么时候接触它 |
| --- | --- | --- |
| `TenantContext` | 不可变租户上下文，承载 `tenantId` 与业务自定义 `extensions` | 构造租户标识时 |
| `TenantContextHolder` | `InheritableThreadLocal` 线程级上下文持有器，`setCurrentTenant` 含 `tenantId` 格式校验 | 理解上下文如何在同线程/子线程传播时 |
| `TenantNamespaceFactory` / `TenantNamespaceFactories` | 命名空间策略：KV key 前缀（`:`）与文件路径（`tenants/{tenantId}`） | 想统一改写隔离命名规则时 |
| `TenantKVStoreKeyResolver` | 把原始 KV key 解析为租户作用域 key（`tenantId:rawKey`） | 理解 Checkpointer / Memory / Todo 的 KV 隔离时 |
| `TenantWorkspaceResolver` | 解析租户工作区、skill、tmp、checkpoint、team_memory 等目录 | 理解文件系统隔离与目录结构时 |
| `TenantPathSecurity` | 路径穿越防御（规范化 + 边界 + 软链接解析） | 关心安全边界时 |
| `TieredWorkspaceManager` + `WorkspaceStore` SPI | 本地 + 远程（OBS/S3/HDFS）分层工作区存储 | 需要把工作区放到对象存储时 |
| `OverlaySkillManager` | Skill 公共 + 租户双层查找，显式覆盖、可撤销 | 关心租户 Skill 隔离时 |
| `TmpFileCleaner` | 后台定时清理过期租户 tmp 文件（TTL） | 关心临时文件生命周期时 |
| `TenantResourceCleaner` | 租户资源清理接口（workspace / KV state / 锁） | 业务方注销租户时 |
| `DeepAgentConfig` / `RunnerConfig` | 多租户开关与数据根目录等配置 | 启动前配置时 |

## 何时需要它

当 DeepAgent 框架以单例方式服务多个企业租户，且存在以下诉求时启用多租户隔离：

- 不同租户的临时文件、工作区写入不能互相访问或干扰；
- Skill 目录需要按租户粒度隔离；
- 智能体后台需要按 `tenantId`（而非仅 session）隔离数据；
- 合规要求禁止跨租户数据越界访问。

框架**只做数据空间隔离，不做租户管理**：租户的创建/注销由业务方负责，框架不校验用户是否属于某租户，只校验 `tenantId` 格式合规。

## 启用多租户

在 `DeepAgentConfig` 上开启开关并指定租户数据根目录；Runner 侧在 `RunnerConfig` 上同样提供开关与数据根目录。

```java
import com.openjiuwen.harness.schema.config.DeepAgentConfig;
import com.openjiuwen.core.multitenant.TenantContext;

DeepAgentConfig config = DeepAgentConfig.builder()
        .model(model)
        .systemPrompt("你是编码助手。")
        .workspacePath("./workspace")
        // 多租户开关：开启即进入严格模式
        .enableTenantIsolation(true)
        .tenantDataRoot("./workspace")
        // 临时文件 TTL 与扫描间隔（默认 24h / 1h）
        .tmpTtl(java.time.Duration.ofHours(24))
        .tmpTtlScanInterval(java.time.Duration.ofHours(1))
        // Todo / Session 存储介质：file | kv
        .todoStorageType("kv")
        .sessionStoreType("file")
        // KV 存储（Checkpointer 与 Todo 共享同一套连接）
        .kvStoreConfig(Map.of(
                "type", "redis",
                "conf", Map.of("connection", Map.of("url", "redis://127.0.0.1:6379"))))
        .build();
```

关键配置项（均位于 `DeepAgentConfig`，`RunnerConfig` 提供 `enableTenantIsolation` 与 `tenantDataRoot`）：

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| `enableTenantIsolation` | `false` | 是否开启多租户隔离（严格模式） |
| `tenantDataRoot` | `null` | 租户数据根目录，`tenants/{tenantId}/` 挂在其下 |
| `tmpTtl` | `Duration.ofHours(24)` | 租户 tmp 文件过期阈值 |
| `tmpTtlScanInterval` | `Duration.ofHours(1)` | tmp 清理扫描间隔 |
| `todoStorageType` | `"file"` | Todo 存储介质：`file` 或 `kv` |
| `sessionStoreType` | `"file"` | Session 存储介质 |
| `kvStoreConfig` | `null` | KV 存储配置（Checkpointer + Todo 共享） |
| `workspaceSecondaryTiers` / `workspaceTierConfigs` | `null` | 分层工作区的远端 tier 配置 |

## 怎么把 tenantId 传进去

框架不自动推断租户身份，调用方必须显式传入。共有几条入口，最终都汇聚到 `bindTenantContext()`：设置 `TenantContextHolder`（含格式校验）+ 把 `CwdContext` 绑定为租户路径，资源层组件自动从上下文读取租户信息，执行完毕 `unbindTenantContext()` 清除。

### 方式一：快捷入口（无 session 场景）

```java
TenantContext tenantCtx = TenantContext.builder()
        .tenantId("dept-01")
        .build();
// 直接 bind/unbind，内部完成 invoke
Map<String, Object> result = agent.invoke(inputs, tenantCtx);
```

### 方式二：Session 内嵌（推荐）

```java
AgentSessionApi session = AgentSessionApi.create(sessionId, null, agent.getCard())
        .withTenantContext(tenantCtx);
// invoke(inputs, session) 会自动从 session 提取 tenantContext
Map<String, Object> result = agent.invoke(inputs, session);
```

### 方式三：Runner 静态入口

`Runner` 暴露了一组带 `TenantContext tenantCtx` 末参的静态重载，由 `RunnerImpl` 统一完成 `resolveTenantContext → bind → 执行 → unbind`：

```java
Object result = Runner.runAgent(
        agent, inputs, session, context, envs, tenantCtx);
Iterator<Object> stream = Runner.runAgentStreaming(
        agent, inputs, session, context, List.of(StreamMode.OUTPUT), envs, tenantCtx);
```

同类重载覆盖 `runWorkflow` / `runWorkflowStreaming` / `runAgentGroup` / `runAgentGroupStreaming` / `runAgentAsync` / `runAgentStreamingAsync`，签名与各自的无租户版本一致，仅末尾追加 `TenantContext tenantCtx`。

### 方式四：CLI 与 MQ

- CLI：`CLIOptions.tenantId` 由 `HarnessCli.buildTenantContext(opts)` 读取并构造 `TenantContext`，随后以快捷入口 `agent.invoke(inputs, tenantCtx)` 执行；
- MQ：`AgentAdapter.extractTenantContext(inputs)` 从 MQ 输入 Map 的 `tenant_id` 字段提取租户上下文，再交给 `Runner.runAgent(...)`。

## 严格模式（Strict Mode）

当 `enableTenantIsolation=true` 时，DeepAgent 在 `bindTenantWorkspace()` **之前**调用 `requireTenantContext(ctx)` 校验：`ctx` 为 null 或 `!ctx.isTenantAware()` 时直接抛：

```text
IllegalStateException: Tenant isolation is enabled but no tenantId was provided.
Either pass a valid TenantContext with non-empty tenantId,
or disable enableTenantIsolation in DeepAgentConfig.
```

- `invoke(inputs, session)` 从 session 提取 `tenantContext`，session 未携带时同样报错；
- `stream(...)` 系列入口同理；
- `requireTenantContext()` 带**嵌套调用感知**：若当前线程已绑定有效租户（外层入口已 bind），内层调用（如 `invoke(inputs, ctx) → invoke(inputs) → invoke(inputs, null session)`）会跳过校验，避免合法调用在内层误报错；
- `enableTenantIsolation=false`（默认）时 `requireTenantContext()` 直接返回，原有向后兼容逻辑零侵入。

## 隔离了哪些资源

### 需要隔离的资源

| 资源 | 存储组件 | 隔离方式 |
| --- | --- | --- |
| Workspace | `TenantWorkspaceResolver` | 文件系统路径隔离 |
| Skills | `TenantWorkspaceResolver` + `OverlaySkillManager` | 路径隔离 + 显式覆盖 |
| Tmp 临时文件 | `TenantWorkspaceResolver` | 路径隔离 + TTL 自动清理 |
| Checkpoints | `TenantWorkspaceResolver` + KV 前缀 | 文件路径 + KV 前缀 |
| Team Memory | `TenantWorkspaceResolver` | 文件系统路径隔离 |
| Todo（文件模式） | `TenantWorkspaceResolver` | 路径隔离 |
| Todo（KV 模式） | `TenantKVStoreKeyResolver` | KV key 前缀 |
| Session / Agent / Workflow / Graph State | `TenantKVStoreKeyResolver` | KV key 前缀 |
| LongTermMemory、用户记忆/变量 | `TenantKVStoreKeyResolver` | KV key 前缀 |
| Distributed Lock | `TenantKVStoreKeyResolver` | KV key 前缀 |

### 不隔离的资源（公共共享）

智能体配置、运行日志、`ResourceMgr` 资源池（Tool/Workflow/Prompt/Model 等）、MessageQueue、CallbackFramework、MCP Server 配置、Prompt 模板、Model 配置、Migration 版本标记。

## 目录结构与命名空间

`tenants/{tenantId}/` **就是**该租户的 workspace 目录（无 `/workspace` 子目录），其他资源挂在其下；无租户时直接以 `baseWorkspacePath` 为根，完全向后兼容。

```text
baseWorkspacePath/
├── tmp/                       # 默认临时目录（无租户时使用）
├── skills/                    # 默认/公共 Skill
├── tenants/
│   ├── dept-01/               # 这就是租户 dept-01 的 workspace
│   │   ├── skills/
│   │   ├── tmp/
│   │   ├── checkpoints/
│   │   ├── team_memory/
│   │   ├── todo/
│   │   └── .overlay/          # Skill 覆盖标记目录
│   │       └── {skillName}.override
│   └── dept-02/
│       └── ...
```

`WorkspaceType` 枚举对应这些子目录：`WORKSPACE("")`、`SKILLS("skills")`、`TMP("tmp")`、`CHECKPOINTS("checkpoints")`、`TEAM_MEMORY("team_memory")`、`TODO("todo")`。

KV key 统一用 `:` 作为租户前缀分隔符，来自 `TenantNamespaceFactories.KV_STORE_DEFAULT`（`tenantId + ":" + rawKey`）：

| 场景 | 无租户 | 有租户 `dept01` |
| --- | --- | --- |
| Todo | `sess-1:todo` | `dept01:sess-1:todo` |
| Agent 状态 | `sess-1:agent:react_agent:state_blobs` | `dept01:sess-1:agent:react_agent:state_blobs` |
| 批量清理 | `deleteByPrefix("sess-1:")` | `deleteByPrefix("dept01:")` |

> 说明：`rawKey` 内部可能自带 `/`（如 `memory_scope_config/{scopeId}`），它只是 key 的一部分，不是租户分隔符。所有 KV 资源的租户分隔符统一为 `:`。

## 安全防护

租户路径安全是三层纵深防御：

1. `TenantContext.safeTenantId()` 把 `[^a-zA-Z0-9_-]+` 规范化为 `_`，作为最后防线；
2. `TenantContextHolder.setCurrentTenant()` 校验 `tenantId` 必须匹配 `[a-zA-Z0-9_-]+`，不合规抛 `IllegalArgumentException`；
3. `TenantPathSecurity.resolveSafePath(relativePath, tenantRoot)`：`toAbsolutePath().normalize()` + `startsWith(tenantRoot)` 阻止 `../` 穿越，并对软链接做 `toRealPath()` 二次校验。

运行期，`CwdContext` 通过 `InheritableThreadLocal<String> TENANT_ROOT` 约束同线程文件操作边界，`LocalFsOperation.validateTenantBoundary()` 在文件操作前校验路径必须在 `tenantRoot` 之内，越界抛 `SecurityException`。

## Skill 显式覆盖（OverlaySkillManager）

Skill 查找遵循「租户私有 → 未被覆盖的公共 → not found」优先级。租户可**显式覆盖**同名公共 Skill：覆盖后即使租户私有 Skill 被删除，公共 Skill 仍不可见，直到 `revokeOverride()` 撤销。覆盖标记存于 `tenants/{tenantId}/.overlay/{skillName}.override`（与 `skills` 平级）。无租户时只查找公共 Skill，向后兼容。

## Todo 存储可替换

Todo（任务清单）是 DeepAgent 在 task loop 模式下追踪任务进度和步骤状态的核心数据结构。`TodoStorage` 是存储介质无关的抽象，通过 SPI 机制可切换底层存储——默认使用本地文件，生产环境可切换为 Redis 等远程 KV 存储。

### SPI 架构

`TodoStorage` 的可替换能力基于三层 SPI：

| 层级 | 类型 | 作用 |
| --- | --- | --- |
| 接口 | `TodoStorage` | 定义 `load(sessionId)` / `save(sessionId, todos)` / `delete(sessionId)` 三个核心操作 |
| SPI 入口 | `TodoStorageProvider` | 声明 `typeName()` 并实现 `create(conf)` |
| 工厂 | `TodoStorageFactory` | `ServiceLoader` 自动发现 Provider，`create(type, conf)` 按类型创建实例 |

SPI 注册文件（`META-INF/services/com.openjiuwen.harness.tools.TodoStorageProvider`）当前注册了两个 Provider：

```text
com.openjiuwen.harness.tools.FileTodoStorageProvider    → typeName = "file"
com.openjiuwen.harness.tools.KvTodoStorageProvider      → typeName = "kv"
```

### 两种存储实现

#### FileTodoStorage（默认）

`FileTodoStorage` 基于本地文件系统，将 todo 数据以 JSON 格式写入磁盘：

- 无租户时：写入 `{workspace}/.todo/{sessionId}/todo.json`
- 有租户时：通过 `TenantWorkspaceResolver` 自动切换路径，写入 `tenants/{tenantId}/todo/{sessionId}/todo.json`

`resolveWorkspace()` 在每次 `load/save/delete` 时检查 `TenantContextHolder`：若当前线程绑定了租户上下文且 `isTenantAware()`，则使用租户路径；否则使用默认 workspace。

#### KvTodoStorage（KV 模式，支持 Redis）

`KvTodoStorage` 基于 `BaseKVStore` SPI，**存储介质无关**——传入 `InMemoryKVStore` 即为内存模式，传入 `RedisStore` 即为 Redis 模式。核心实现：

```java
public class KvTodoStorage implements TodoStorage {
    private final BaseKVStore kvStore;

    private String buildKey(String sessionId) {
        String rawKey = sessionId + ":todo";
        return TenantKVStoreKeyResolver.resolveKey(rawKey);  // 自动添加租户前缀
    }

    public List<TodoItem> load(String sessionId) {
        String json = String.valueOf(kvStore.get(buildKey(sessionId)));
        return JsonUtils.safeJsonLoads(json, TodoItem[].class, new TodoItem[0]);
    }

    public void save(String sessionId, List<TodoItem> todos) {
        kvStore.set(buildKey(sessionId), JsonUtils.safeJsonDumps(todos, "[]"));
    }

    public void delete(String sessionId) {
        kvStore.delete(buildKey(sessionId));
    }
}
```

关键设计要点：

- **依赖 `BaseKVStore` 抽象而非具体 Redis 实现**：无需单独的 `RedisTodoStorage` 类，整个 Todo KV 存储只依赖一个 `BaseKVStore` 实例
- **租户隔离通过 `TenantKVStoreKeyResolver.resolveKey(rawKey)` 自动处理**：无需业务代码手动拼接前缀
- **KV key 格式**：
  - 无租户：`{sessionId}:todo`（如 `sess-abc123:todo`）
  - 有租户：`{tenantId}:{sessionId}:todo`（如 `dept01:sess-abc123:todo`）
- **与 Checkpointer 共享同一套 `BaseKVStore` 实例与 Redis 连接**：一套 `kvStoreConfig` 配置同时驱动 Checkpointer 和 Todo 的存储介质

### Redis 配置

将 Todo 存储切换到 Redis 模式需要两步配置：

1. 设置 `todoStorageType` 为 `"kv"`
2. 配置 `kvStoreConfig` 指定 Redis 连接

#### 单机 Redis 配置

```java
DeepAgentConfig config = DeepAgentConfig.builder()
        .model(model)
        .systemPrompt("你是编码助手。")
        .workspacePath("./workspace")
        .enableTenantIsolation(true)
        .tenantDataRoot("./workspace")
        // 步骤 1：Todo 存储类型改为 kv
        .todoStorageType("kv")
        // 步骤 2：KV 存储配置（Checkpointer 与 Todo 共享）
        .kvStoreConfig(Map.of(
                "type", "redis",
                "conf", Map.of(
                        "host", "127.0.0.1",
                        "port", 6379,
                        "password", "")))
        .build();
```

#### 集群 Redis 配置

```java
.kvStoreConfig(Map.of(
        "type", "redis",
        "conf", Map.of(
                "cluster", "true",
                "host", "redis-cluster.example.com",
                "port", 6379)))
```

#### URL 格式配置

配置中也支持 `connection.url` 的方式指定 Redis 地址：

```java
.kvStoreConfig(Map.of(
        "type", "redis",
        "conf", Map.of("connection", Map.of(
                "url", "redis://:password@127.0.0.1:6379"))))
```

`RedisKVStoreProvider` 内部通过反射创建 Jedis（单机）或 JedisCluster（集群）客户端，不直接依赖 Redis 客户端库的 API，支持 Jedis / Lettuce / Redisson 多种客户端。

### 共享 KV 实例机制

`KvTodoStorage` **优先复用 DeepAgent 已注入的 `BaseKVStore` 实例**，避免重复创建 Redis 连接。注入链路：

1. `HarnessFactory.createDeepAgent(...)` → `injectKvStore(agent, config)`：根据 `kvStoreConfig` 创建 `BaseKVStore`（如 `RedisStore`）并注入 `agent.setKvStore(kvStore)`
2. `TaskPlanningRail.buildTodoStorageConfig(deepAgent, "kv")`：
   - **优先**：`deepAgent.getKvStore()` 不为 null → 传入 `sharedKvStore` 参数，直接复用已注入实例
   - **降级**：`kvStore` 为 null → 从 `config.getKvStoreConfig()` 提取配置，通过 `KVStoreFactory.create(type, conf)` 新建实例

这意味着在生产环境中，`kvStoreConfig` 配置的 Redis 连接**同时服务 Checkpointer 和 Todo**，无需为 Todo 单独配置一套 Redis 连接。`kvStoreConfig` 为 null 时 `injectKvStore` 跳过注入，Todo 自动降级为 `FileTodoStorage`。

### 租户感知重载

`TodoStorage` 的 `load/save/delete` 提供了带 `TenantContext` 的默认重载（显式租户感知）：

```java
default List<TodoItem> load(String sessionId, TenantContext tenantContext) throws IOException {
    if (tenantContext != null && tenantContext.isTenantAware()) {
        try {
            TenantContextHolder.setCurrentTenant(tenantContext);
            return load(sessionId);
        } finally {
            TenantContextHolder.clearCurrentTenant();
        }
    }
    return load(sessionId);
}
```

在 ThreadLocal 上下文丢失（如异步线程池场景）时，仍可通过显式传入 `TenantContext` 临时 bind 并正确隔离。

### TodoTool 创建路径

运行时 Todo 工具通过 `TaskPlanningRail` 创建，支持三种路径：

```java
TodoTool.fromConfig(storageType, conf)
```

| `todoStorageType` | 创建路径 |
| --- | --- |
| `"file"`（默认） | `FileTodoStorageProvider.create(conf)` → `FileTodoStorage` |
| `"kv"`（有共享 KV 实例） | `KvTodoStorageProvider.create(conf)` → `new KvTodoStorage(sharedKvStore)` |
| `"kv"`（无共享 KV 实例） | `KVStoreFactory.create(kvStoreType, kvStoreConf)` → `new KvTodoStorage(kvStore)` |

若 `todoStorageType` 为 `"kv"` 但未注册 KvTodoStorageProvider（如缺少扩展依赖），`TaskPlanningRail` 会降级到 `FileTodoStorage` 并输出 warning 日志。

### RunnerConfig 中的配置

通过 `RunnerConfig` 启动时同样支持 KV 配置：

```java
RunnerConfig config = RunnerConfig.builder()
        .enableTenantIsolation(true)
        .kvStoreConfig(Map.of(
                "type", "redis",
                "conf", Map.of("host", "127.0.0.1", "port", 6379)))
        .build();
Runner.setConfig(config);
Runner.start();
```

### KV key 承载的完整数据

KV 模式下，一个 session 的 todo 数据仅占用一个 key（`{sessionId}:todo` 或 `{tenantId}:{sessionId}:todo`），value 为 `TodoItem[]` 的 JSON 序列化。与 Checkpointer 的 session 状态 key（`{sessionId}:agent:...` / `{sessionId}:workflow:...`）共存于同一 KV 存储实例中，前缀不同、互不冲突。

租户批量清理时，`TenantResourceCleaner.cleanupKVState(tenantId)` 通过 `deleteByPrefix("{tenantId}:")` 一键清除该租户所有 KV 数据（包括 todo、agent state、workflow state、graph state、memory 等）；`cleanupTodo(tenantId, sessionId)` 则单独清除指定 session 的 todo 目录或 KV key。

## 临时文件 TTL 清理

`TmpFileCleaner`（`com.openjiuwen.core.multitenant`）在后台定时扫描并删除过期 tmp 文件：

- 构造：`new TmpFileCleaner(ttl, scanInterval, baseWorkspacePath, workspaceResolver)`；
- `start()`：`scheduleAtFixedRate` 启动扫描，扫描默认 tmp 目录与各 `tenants/*/tmp`，按 `lastModifiedTime` 超过 TTL 删除；
- `stop()`：优雅关闭调度器；`DeepAgent` 实现 `AutoCloseable`，`close()` 会停止 cleaner。

调度线程为守护线程（`tmp-file-cleaner`），不阻塞 JVM 退出。

## 资源清理接口

`TenantResourceCleaner` 提供按租户清理资源的接口，由业务方在注销租户时调用（Tmp TTL 清理除外）：

| 方法 | 清理范围 |
| --- | --- |
| `cleanupWorkspace(tenantId)` | 删除整个租户 workspace 目录树 |
| `cleanupSkills(tenantId)` | 删除租户 skill 目录 |
| `cleanupCheckpoints(tenantId, sessionId)` | 删除指定 session 的 checkpoint 目录 |
| `cleanupTeamMemory(tenantId, teamId)` | 删除指定团队的 team_memory |
| `cleanupTodo(tenantId, sessionId)` | 删除指定 session 的 todo 目录 |
| `cleanupKVState(tenantId)` | 删除该租户所有 `tenantId:*` 前缀的 KV key |
| `cleanupKVState(tenantId, sessionId)` | 删除该租户指定 session 的 KV key |
| `cleanupDistributedLocks(tenantId)` | 释放该租户持有的分布式锁 |
| `cleanupAll(tenantId)` | 组合以上所有清理 |

## 异步场景下的上下文传播

`TenantContextHolder` 使用 `InheritableThreadLocal`，`new Thread()` 创建的子线程自动继承；但线程池复用线程、Reactor `boundedElastic`、`CompletableFuture` 默认 ForkJoinPool **不会**自动继承。框架的保障措施：

- 所有入口方法均用 try/finally：`setCurrentTenant()` → 执行 → `clearCurrentTenant()`；
- 流式入口用 `TenantUnbindIterator` 包装器，在 `hasNext() == false` 或异常时才 unbind；
- Reactor 异步路径显式捕获 `TenantContext` 并在 `defer`/`fromCallable` 内 bind/unbind，终态（COMPLETE/ERROR/CANCEL）都触发清理。

新增异步路径时需显式捕获并 bind/unbind：

```java
TenantContext captured = TenantContextHolder.getCurrentTenant();
executor.submit(() -> {
    try {
        TenantContextHolder.setCurrentTenant(captured);
        // 业务逻辑
    } finally {
        TenantContextHolder.clearCurrentTenant();
    }
});
```

## 当前 Java 能力边界

- 默认 `enableTenantIsolation=false`，完全向后兼容；开启后才进入严格模式。
- 框架不校验租户合法性，只校验 `tenantId` 格式（`[a-zA-Z0-9_-]+`）。
- `safeTenantId()` 是最后防线，存在字符碰撞风险（如 `dept-01` 与 `dept.01` 都规范化为 `dept_01`），因此要求业务方传入合规 `tenantId`，碰撞由 `setCurrentTenant` 拦截。
- **Vector Store 集合名隔离与 DB Store `tenant_id` 列改造属后续阶段，当前版本未隔离**；关系数据库（MessageManager/ScopeUserMapping）与向量库数据当前不按租户隔离。
- 租户资源清理由业务方触发，框架不主动清理（Tmp TTL 除外）。
- `InheritableThreadLocal` 对线程池复用线程不自动传播，异步路径必须显式捕获。
