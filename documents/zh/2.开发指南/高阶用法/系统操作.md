# 系统操作

`系统操作` 对应 `com.openjiuwen.core.sysop`。它把**文件系统**、**代码执行**和**命令执行**收敛到同一套门面与卡片模型里，使上层 Agent、workflow 或 dev tool 不必分别关心底层平台差异。

对 Java 当前仓库来说，这一层已经形成了稳定的公开 API，但要明确区分两件事：

- `LOCAL` 模式是当前 examples 和测试实际覆盖的主线；
- `SANDBOX` 模式已经有公共类型和门面接口，但具体 `fs` / `code` / `shell` 沙箱实现仍是占位实现，不应写成已经完整可用的外部沙箱方案。

## 1. 核心对象

| 类型 | 作用 | 当前使用重点 |
| --- | --- | --- |
| `OperationMode` | 定义运行模式 | `LOCAL` 与 `SANDBOX` |
| `SysOperationCard` | 描述系统能力卡片与运行配置 | 运行模式、`workConfig`、`gatewayConfig` |
| `SysOperation` | 统一门面 | 懒加载 `fs()`、`code()`、`shell()` |
| `LocalWorkConfig` | 本地模式配置 | `workDir`、`shellAllowlist` |
| `SandboxGatewayConfig` | 沙箱模式配置 | `gatewayUrl`、`params`、认证信息 |
| `SysOperationToolAdapter` | 工具适配器 | 把系统操作方法封装为 `LocalFunction` 工具 |

## 2. 注册与生命周期

Java 侧的主线入口是 `Runner.resourceMgr().addSysOperation(...)`：

```java
SysOperationCard sysOpCard = SysOperationCard.builder()
        .mode(OperationMode.LOCAL)
        .workConfig(LocalWorkConfig.builder().workDir(null).build())
        .build();

Runner.resourceMgr().addSysOperation(sysOpCard, null);
```

这一步在资源管理器里会做两件事：

1. 用 `SysOperationCard` 创建一个 `SysOperation` 门面实例；
2. 通过 `SysOperationToolAdapter` 把当前模式下可暴露的方法提取成工具卡片并一并注册。

对应地，移除系统能力时也可以走资源管理器统一清理，让关联的 sysop 工具一起移除。

## 3. `SysOperation` 门面如何组织三类能力

`SysOperation` 本身不直接实现文件、代码或命令逻辑。它的职责是：

- 读取 `SysOperationCard` 中的模式与配置；
- 根据 `OperationRegistry` 按名称创建具体操作实例；
- 对同一个门面实例缓存已创建过的子操作。

Java 当前公开了三类标准子接口：

### 3.1 文件系统：`fs()`

`BaseFsOperation` 暴露的核心能力包括：

- `readFile`
- `readFileStream`
- `writeFile`
- `uploadFile` / `downloadFile`
- `listFiles`
- `listDirectories`
- `searchFiles`

这也是 skill、prompt builder 或自定义 dev tool 最常用的一组系统能力。

### 3.2 代码执行：`code()`

`BaseCodeOperation` 当前公开：

- `executeCode`
- `executeCodeStream`

Java examples 里最典型的用途，是让 Agent 通过 Python 执行轻量脚本或数据处理逻辑，例如 `examples/skill_use` 中的图片缩放场景。

### 3.3 命令执行：`shell()`

`BaseShellOperation` 当前公开：

- `executeCmd`
- `executeCmdStream`

这一层适合受控命令调用，而不是无限制 shell。实际可执行范围由 `LocalWorkConfig.shellAllowlist` 约束。

## 4. `SysOperationCard` 与工具 ID

`SysOperationCard` 不只是配置对象，它还是整个 sysop 工具命名的锚点。Java 当前使用统一的工具 ID 规则：

```text
{cardId}.{opType}.{methodName}
```

例如：

- `my_sysop.fs.readFile`
- `my_sysop.code.executeCode`
- `my_sysop.shell.executeCmd`

如果你需要显式生成工具 ID，可以使用：

```java
String readToolId = SysOperationCard.generateToolId(sysOpCard.getId(), "fs", "readFile");
String codeToolId = SysOperationCard.generateToolId(sysOpCard.getId(), "code", "executeCode");
String cmdToolId = SysOperationCard.generateToolId(sysOpCard.getId(), "shell", "executeCmd");
```

这套命名规则的价值在于：上层 Agent、workflow 或 dev tool 不需要记住底层实现类，只要约定 card id + op type + method name 即可。

## 5. 工具适配：`SysOperationToolAdapter`

`SysOperationToolAdapter` 是 sysop 和 Agent 工具体系之间的桥梁。它会：

- 遍历当前模式支持的操作名；
- 读取子操作暴露出来的 `ToolCard` 列表；
- 用 `LocalFunction` 把目标方法包起来；
- 对 `Map<String, Object>` 输入做基础类型转换；
- 返回 `(toolId, LocalFunction)` 对，供资源管理器注册。

这也是为什么上层一般不需要手写 `readFile`、`executeCode`、`executeCmd` 的工具包装。

对 Agent 来说，最常用的不是直接操作适配器，而是通过资源管理器取出已经注册好的工具卡片：

```java
Object readToolCard = Runner.resourceMgr().getSysOpToolCards(sysOpCard.getId(), "fs", "readFile");
Object codeToolCard = Runner.resourceMgr().getSysOpToolCards(sysOpCard.getId(), "code", "executeCode");
Object cmdToolCard = Runner.resourceMgr().getSysOpToolCards(sysOpCard.getId(), "shell", "executeCmd");

agent.getAbilityManager().add(readToolCard);
agent.getAbilityManager().add(codeToolCard);
agent.getAbilityManager().add(cmdToolCard);
```

`examples/skill_use/SkillUseExample.java` 采用的就是这条路径。

## 6. `LOCAL` 模式：当前最稳的主线

`OperationMode.LOCAL` 是 Java 当前 examples、测试和文档都实际覆盖的主线模式。

### 6.1 本地配置项

`LocalWorkConfig` 主要包含两个部分：

- `workDir`：本地工作目录。相对路径通常会围绕它解析；
- `shellAllowlist`：允许执行的命令前缀列表。

仓库里的默认白名单已经覆盖了较常见的本地命令，例如：

- `echo`
- `dir`
- `python` / `python3`
- `pip` / `pip3`
- `git`
- `node` / `npm`
- `copy` / `move`

但文档层面的推荐仍然是：**尽量按任务缩小白名单，而不是直接完全放开**。

### 6.2 本地实现现状

当前仓库已有完整本地实现：

- `LocalFsOperation`
- `LocalCodeOperation`
- `LocalShellOperation`

这也是为什么 Java 当前的 skill use、skill create、prompt builder 等能力都优先围绕 local sysop 展开。

## 7. `SANDBOX` 模式：当前只说明公开边界

`OperationMode.SANDBOX` 与 `SandboxGatewayConfig` 已经进入公共 API，说明上层抽象已经为“远端受控执行环境”预留了位置。

但要特别说明 Java 当前仓库的事实状态：

- `SandboxFsOperation`
- `SandboxCodeOperation`
- `SandboxShellOperation`

这三个类目前都会抛出 `UnsupportedOperationException`。因此本页只说明：

- Java 已有 `SANDBOX` 模式枚举；
- Java 已有网关配置对象；
- Java 已把 local/sandbox 的切换位设计进 `SysOperationCard` 与 `SysOperation`。

**不把它扩写成已经公开、可直接部署的外部沙箱实现。**

## 8. 在 Agent 里的典型接入方式

对单 Agent 来说，sysop 的典型接入顺序通常是：

1. 创建 `SysOperationCard`；
2. 调用 `Runner.resourceMgr().addSysOperation(...)` 注册；
3. 把需要的 sysop 工具卡片加入 `AbilityManager`；
4. 在 Agent 配置里记录 `sysOperationId`。

这一写法在 `examples/skill_use` 和 `SkillCreator` 里都能看到，只是挂载的工具集合不同：

- `SkillUseExample` 主要挂 `readFile`、`executeCode`、`executeCmd`；
- `SkillCreator` 主要挂 `readFile`、`writeFile`、`listFiles`、`listDirectories`、`searchFiles`。

## 9. 使用建议

- 如果你要写一个当前仓库里可直接验证的 Java 示例，优先使用 `LOCAL`。
- 如果你要设计未来可以迁移到沙箱的调用链，仍然建议以 `SysOperationCard` + 工具 ID 的方式组织代码，这样上层结构可以保持不变。
- 把 `系统操作` 理解成**执行抽象层**，不要和 skill 的元数据层混在一起。
