# 多模态推理（图片/视频理解与生成）

这里重点说明框架的多模态推理能力：一类是**多模态理解**——把本地图片/视频以 base64 data URI 注入ReAct 循环，让视觉模型"看到"素材后回答问题；一类是**多模态生成**——通过 `Model` 门面的`generateImage` / `generateVideo` 调用厂商生图、生视频端点，把 URL 或二进制结果交还调用方。核心代码分别在 `core` 的 `ReActAgent`（理解注入）与 `OpenAIModelClient`（生成任务引擎），四种场景的完整可运行实现在 `examples/multi-modal-inference`：`ImageDescribeExample`、`VideoDescribeExample`、`ImageGenerationExample`、`VideoGenerationExample`。

## 功能定位

先看四个关键问题：

1. 一个本地图片/视频，怎样经过工具调用变成视觉模型可识别的多模态消息。
2. `Model.generateImage` / `Model.generateVideo` 怎样以"厂商无关"的方式对接不同厂商端点，为什么 core 里不应该出现任何厂商名。
3. 厂商端点差异（路径、请求体、轮询、结果位置）由哪一层消化：通用 kwargs、demo 预设表，还是配置文件。
4. 图片与视频在压缩、大小上限、消息形状上有哪些不同的处理策略。

## 核心概念

| 对象 | 作用 | 你需要关心什么 |
| --- | --- | --- |
| `LoadImageTool` / `LoadVideoTool` | 理解 demo 内的本地加载工具 | 读文件 → 校验/压缩 → base64 data URI → 返回 `data.multimodal` |
| `data.multimodal` | 工具结果中的多模态载荷 | 图片项 `{type=image, source_path, label, data_url}`；`type=video` 同构 |
| `ReActAgent.appendMultimodalToolResultsMessage` | 理解注入入口 | 每轮工具执行后扫描结果，把 multimodal 条目转成带 `image_url`/`video_url` 内容的 UserMessage |
| `buildToolMessageContent` | 工具消息文本生成 | 只取 `data.content` 作为文本；缺失时会 `String.valueOf` 整个结果，把 base64 带进文本上下文 |
| `Model.generateImage` | 生图门面 | 默认 `POST {base}/images/generations`，同步返回 URL/base64 |
| `Model.generateVideo` | 生视频门面 | 通用"创建 → 轮询 → 取片"任务引擎，行为由 `video_*` kwargs 配置 |
| `VideoTaskConfig` | 视频任务流配置 | 由 kwargs 弹出解析：路径模板、请求体形态、结果解析、状态集 |
| `IMAGE_PRESETS` / `VIDEO_PRESETS` | demo 厂商预设表 | 按 `API_BASE` 域名匹配，值为传给 core 的通用 kwargs；core 不感知厂商 |

## 场景一：图片理解（ImageDescribeExample）

输入一张本地图片，视觉模型基于实际可见内容回答问题。实现是两轮 ReAct 执行：

```text
用户消息（问题 + 图片路径）
  -> 第 1 轮：模型看到路径，调用 LoadImageTool(path=...)
  -> LoadImageTool：读盘 -> 等比缩放(最长边<=1024px) -> JPEG 重压缩(质量0.85) -> base64 data URI
     返回 {success, data: {content, multimodal: [{type=image, source_path, label, data_url}]}}
  -> ReActAgent.appendMultimodalToolResultsMessage 扫描工具结果，
     把 multimodal 条目转为 [{type=text}, {type=image_url, image_url={url=data:image/jpeg;base64,...}}]
     的 UserMessage 追加进上下文
  -> 第 2 轮：视觉模型看到图片，基于实际可见内容输出描述
```

实现要点：

- **图片必须压缩**：`LoadImageTool` 按 `MAX_EDGE_PX=1024` 等比缩放并重压缩为 JPEG（质量 0.85），解码失败回退原始字节——原始图片直接 base64 会把请求体撑到数 MB。
- **`data.content` 必须提供**：`AbilityManager.buildToolMessageContent` 生成工具消息文本时只取 `data.content`；缺失时会 `String.valueOf` 整个工具结果，把几十万字符的 base64 带进文本上下文。demo 返回的 `content` 是一句短提示（"图片已加载成功…请立即基于图片回答"）。
- **`data:image/` 前缀决定注入**：`ReActAgent.iterMultimodalImageItems` 只保留 `type=image`且 `data_url` 以 `data:image/` 开头的条目，HTTP URL 会被过滤——因此工具只接受本地文件路径。
- **默认输入来自 classpath**：无参数运行时，`resources` 内置的 `1080p.jpeg` 被解包到临时文件（`deleteOnExit` 自动清理）再交给工具；`args[0]` / `-Dopenjiuwen.example.imagePath` /环境变量 `IMAGE_PATH` 可覆盖。

## 场景二：视频理解（VideoDescribeExample）

输入一段本地视频，实现与图片理解同构（`LoadVideoTool` → `type=video` 条目 → 视频消息注入），差异点全部来自视频本身的体积与格式：

```text
用户消息（问题 + 视频路径）
  -> 第 1 轮：模型看到路径，调用 LoadVideoTool(path=...)
  -> LoadVideoTool：读盘 -> 10MB 大小上限校验 -> 按扩展名判定 MIME -> 整段 base64 data URI
     返回 {success, data: {content, multimodal: [{type=video, source_path, label, data_url}]}}
  -> ReActAgent.iterMultimodalVideoItems 过滤后转为带 video_url 内容的 UserMessage
  -> 第 2 轮：视觉模型看到视频，输出描述
```

实现要点：

- **视频不做转码压缩**：JDK 标准库无法重编码 MP4，`LoadVideoTool` 只做 10MB 大小上限校验，超限直接报错；8MB 视频约产生 11MB 请求体，过大需自行裁剪片段。
- **MIME 按扩展名判定**：`URLConnection` 猜测失败时按 `.mp4/.mov/.webm` 等扩展名映射，默认 `video/mp4`；`data:video/` 前缀是 `iterMultimodalVideoItems` 的注入条件。
- **消息体积远大于图片**：整段 base64 随请求发送，调试时可关闭敏感过滤观察`Before request chat model` 日志中的 `video_url` 内容。

## 场景三：图片生成（ImageGenerationExample）

输入一段提示词，调用生图模型同步生成图片并下载到本地。实现是一条同步 HTTP 创建链路：

```text
POST {image_create_path | /images/generations}
请求体：{model, prompt, n, size, negative_prompt, seed}   <- 只发有值字段 + kwargs 透传
响应解析：默认 data[].url -> images；data[].b64_json -> imagesBase64
          或 image_urls_path 指向的字符串数组（如 data.image_urls）
-> demo 按 URL/base64 下载落地为 PNG
```

实现要点：

- **请求体只发有值字段**：`promptExtend` / `watermark` 不映射——它们不是 OpenAI images API的字段，严格端点会拒绝未知参数；厂商专有字段（如 `aspect_ratio`、`prompt_optimizer`）经kwargs 透传进请求体。
- **解析路径可配置**：kwargs `image_create_path` 覆盖创建端点（默认 `/images/generations`），`image_urls_path` 指向响应中图片 URL 数组的点分 JSON 路径；不传 kwargs 时按 OpenAI 官方响应形状解析。
- **报错携带响应摘要**：解析不到任何图片时，业务异常信息包含响应体前 300 字符——部分厂商用HTTP 200 + 业务错误码（如 `base_resp.status_code`）表达失败，摘要可以直接定位原因。
- **demo 预设表**：`IMAGE_PRESETS` 按 `API_BASE` 域名匹配。以 MINIMAX 为例：`image_create_path=/v1/image_generation`、`image_urls_path=data.image_urls`、模型覆盖为`image-01`，附带 `aspect_ratio=1:1`、`response_format=url`、`prompt_optimizer=true` 默认值；预设值为字符串，`true`/`false` 会在组装 kwargs 时规范化为布尔（字符串布尔会被严格端点拒绝）。未命中域名走 OpenAI 官方默认。结果中的图片 URL 有时效性，demo 当场下载落地为`generated/generated-时间戳-序号.png`。

## 场景四：视频生成（VideoGenerationExample）

输入提示词（可选首帧图），走"创建任务 → 轮询状态 → 取片"的异步任务链路。core 把各厂商形状差异抽象为一条**配置驱动的通用任务流**：

```text
POST {video_create_path | /videos}                        创建任务，响应携带 {taskId}
GET  {video_poll_path | {createPath}/{taskId}}            按 poll_interval_seconds 轮询，
                                                          状态进入成功集/失败集或超时
取片：video_result_url_path 命中 -> videoUrl
      否则配置了 video_file_retrieve_path -> {fileId} 查文件描述 ->
            video_file_url_path 指向的 download_url -> 下载二进制
      否则 video_result_download_path（默认 {pollPath}/content）-> 下载二进制
```

实现要点：

- **请求体两种形态**：kwargs `video_body=prompt`（默认，`model/prompt/size/seconds` 字段）或`video_body=reference`（`model` + `content` 数组承载文本、`image_url` 首帧、`audio_url` 引用，附 `duration`/`resolution`）；剩余 kwargs 合并进创建请求体。
- **取片三级优先**：轮询响应中先按 `video_result_url_path`（未配置则通用扫描`content.video_url` → `video_url` → `url`）取 URL；配置了 `video_file_retrieve_path`（含 `{fileId}` 占位）则走文件中转，`video_file_url_path` 默认 `file.download_url`；都没有时按 `video_result_download_path`（含 `{taskId}`，默认 `{pollPath}/content`）下载二进制。结果以 `videoUrl` 或 `videoData` 二选一返回。
- **轮询控制**：`poll_interval_seconds`（默认 5）、`max_wait_seconds`（默认 600），轮询在调用线程上同步阻塞；状态集默认 `completed/succeeded/success` 成功、`failed/error/cancelled/canceled/expired/fail` 失败，可用`video_success_statuses` / `video_failure_statuses` 覆盖。
- **demo 预设表**：`VIDEO_PRESETS` 按 `API_BASE` 域名匹配，内置两条预设——MINIMAX（`/v2/video_generation` 创建、`/v1/query/video_generation?task_id={taskId}` 轮询、文件中转取片，默认 768P/4s）与 ARK（`/contents/generation/tasks` 创建轮询、`content.video_url` 取片，默认 720p/5s）；未命中走 OpenAI 官方默认。结果落地为`generated/video-时间戳.mp4`。

## 厂商适配原则

core 与厂商名解耦，厂商差异由外层消化，优先级从高到低：

1. **显式 kwargs**：调用 `generateImage` / `generateVideo` 时直接传（可用`-Dopenjiuwen.example.image*` / `-Dopenjiuwen.example.video*` 系统属性在 demo 中注入）。
2. **demo 预设表**：按 `API_BASE` 域名匹配 `IMAGE_PRESETS` / `VIDEO_PRESETS`，命中的域名自动组装 kwargs（含模型名覆盖、默认分辨率/时长、布尔值规范化）。
3. **core 默认值**：全部未命中时走 OpenAI 官方端点与响应形状。

接入新厂商 = 预设表加一行（demo 代码），或零代码用系统属性手工传参；apiconfig.json始终保持最简五键（API_BASE / API_KEY / MODEL_PROVIDER / MODEL_NAME / LLM_SSL_VERIFY）。注意 `MODEL_NAME` 在各 demo 间共享：生视频与生图的模型不同（甚至不同厂商），demo 预设表会按需覆盖模型名。

## 快速开始

视频理解（`examples/multi-modal-inference`）：

```java
ReActAgent agent = new ReActAgent(agentCard);
ReActAgentConfig config = ReActAgentConfig.builder()
        .promptTemplate(List.of(Map.of("role", "system", "content", SYSTEM_PROMPT)))
        .maxIterations(3)
        .build()
        .configureModelClient(provider, apiKey, apiBase, modelName, sslVerify);
agent.configure(config);
// 注册 LoadImageTool / LoadVideoTool 后由 Runner.runAgent 驱动，见示例模块
```

图片生成（命中厂商预设由 demo 组装 kwargs，直接调用时等价于）：

```java
Model model = new Model(clientConfig, requestConfig);
ImageGenerationResponse response = model.generateImage(
        List.of(new UserMessage(prompt)),        // 单条用户消息承载提示词
        modelName, size, negativePrompt, n,      // 模型为空则用配置中的 MODEL_NAME
        true, false, 0, Map.of(                  // kwargs：端点/结果解析配置 + 厂商字段
                "image_create_path", "/v1/image_generation",
                "image_urls_path", "data.image_urls"))
        .toCompletableFuture().get(300, TimeUnit.SECONDS);
```

视频生成（不传 kwargs 即 OpenAI 官方流程；以下示例启用"内容数组 + 文件中转"形态）：

```java
VideoGenerationResponse response = model.generateVideo(
        List.of(new UserMessage(prompt)), imgUrl, audioUrl,
        modelName, size, resolution, duration,
        true, false, null, null,
        Map.of("video_body", "reference",
                "video_create_path", "/v2/video_generation",
                "video_poll_path", "/v1/query/video_generation?task_id={taskId}",
                "video_file_retrieve_path", "/v1/files/retrieve?file_id={fileId}&purpose=video_generation",
                "video_file_url_path", "file.download_url"))
        .toCompletableFuture().get(30, TimeUnit.MINUTES);
// videoUrl 或 videoData 二选一返回
```

## 示例入口

完整可运行示例在 `examples/multi-modal-inference`（独立 Maven 模块，构建与运行说明见其 README）：

| 主类 | 场景 | 输入 | 输出 |
| --- | --- | --- | --- |
| `ImageDescribeExample` | 图片理解 | resources 内置 `1080p.jpeg` 或指定路径 | 视觉模型描述 |
| `VideoDescribeExample` | 视频理解 | resources 内置 `video.mp4` 或指定路径 | 视觉模型描述 |
| `ImageGenerationExample` | 图片生成 | 提示词（+ 宽高比/尺寸） | `generated/` 下的 PNG |
| `VideoGenerationExample` | 视频生成 | 提示词（+ 可选首帧图） | `generated/` 下的 MP4 |

调试时可关闭敏感过滤（`UserConfig.setIsSensitive(false)` 或环境变量 `IS_SENSITIVE=false`），让 `Before request chat model` 日志携带完整 messages/tools，确认 `image_url` / `video_url`数据实际发送的位置；生产环境不要关闭。

## 使用边界

1. **理解类**：模型必须是支持视觉（图片）或视频输入的多模态模型，纯文本模型会直接报错；图片/视频只接受本地文件路径（HTTP URL 会被 `data:image/`、`data:video/` 前缀过滤掉）；图片自动压缩，视频不转码且受 10MB 上限限制。
2. **生成类**：轮询在调用线程上同步阻塞（与 DashScope 实现一致），`max_wait_seconds` 控制上限；部分厂商返回的图片/视频 URL 有时效性，demo 会当场下载落地；`size`/`aspect_ratio` 等取值由各厂商校验，跨厂商时注意格式差异（如 `x` 分隔与 `16:9` 比例）；部分厂商用HTTP 200 + 业务错误码表达失败，需结合错误摘要判断。
3. **调试边界**：关闭敏感过滤后日志会携带完整多模态消息（含大段 base64），仅限本地调试使用。
