# 回调框架

这里重点说明 Java 当前公开的 `com.openjiuwen.core.runner.callback.AsyncCallbackFramework` 全局事件回调框架。

这点要先讲清：

- Java 版当前公开的是基于 `Function<Map<String, Object>, Object>` 的事件回调框架。
- 并行、延迟、超时是由框架内部的 executor 来完成，而不是让回调自己变成 `CompletableFuture` 风格接口。

这里讨论的是 **Runner 侧的全局事件回调框架**，不是 Session 里的 per-session callback manager，也不是 tracer/trace stream 那一套。

## 先记住三个边界

1. `Runner.getCallbackFramework()` 返回的是全局 Runner 级事件总线；`Runner.callbackFramework` 是同一个全局实例的静态字段。
2. `session.callback.CallbackManager` 是 Session 观测 / tracer 用的另一套机制。
3. Guardrail、agent rail 会复用 `AsyncCallbackFramework` / `DecoratorFramework`，但 workflow trace 不走这里。

如果你是为了看 Session trace、span、`TraceSchema`，请转到 [Session / 调测能力](Session/调测能力.md)。

## 核心对象

| 类型 | 作用 | 什么时候看它 |
| --- | --- | --- |
| `AsyncCallbackFramework` | 注册、触发、过滤、链式执行、指标与历史的总入口 | 日常接入时 |
| `CallbackInfo` | 单个回调的元数据 | 你要看 priority、namespace、timeout 等参数时 |
| `EventFilter` / `FilterResult` / `FilterAction` | 过滤器体系 | 你要做校验、限流、参数改写时 |
| `CallbackChain` / `ChainContext` / `ChainResult` / `ChainAction` | 链式执行与回滚 | 你要做事务式多步回调时 |
| `CallbackMetrics` | 调用次数、耗时、错误率 | 你要做观测与性能排查时 |
| `HookType` | 生命周期钩子枚举 | 你要在 BEFORE / AFTER / ERROR 插逻辑时 |

## 回调签名和事件模型

Java 当前的回调不是多参数 lambda，而是统一签名：

```java
Function<Map<String, Object>, Object>
```

也就是：

- 所有 keyword 风格参数都放在 `Map<String, Object>` 里
- 位置参数统一塞在 `_args`

也就是：位置参数统一通过 `_args` 传入，具名参数统一放在 `Map<String, Object>` 里。

### 最小示例

```java
import com.openjiuwen.core.runner.Runner;
import com.openjiuwen.core.runner.callback.AsyncCallbackFramework;

import java.util.List;
import java.util.Map;

AsyncCallbackFramework framework = Runner.getCallbackFramework();

framework.register(
        "order.created",
        kwargs -> "audit:" + kwargs.get("orderId"),
        10,
        "audit_callback"
);

List<Object> results = framework.triggerResults(
        "order.created",
        new Object[0],
        Map.of("orderId", "A-1001")
);
```

这里最关键的行为是：

- 同一事件下可以注册多个回调
- priority 数字越大越先执行
- `once = true` 的回调执行一次后会被自动禁用

## 注册和注销：先把组织方式设计好

`AsyncCallbackFramework.register(...)` 支持的元数据并不少：

- `priority`
- `once`
- `namespace`
- `tags`
- `eventFilters`
- `rollbackHandler`
- `errorHandler`
- `maxRetries`
- `retryDelay`
- `timeout`
- `callbackName`

这意味着你一开始就可以把回调按“业务域”组织清楚，而不是等回调越来越多后再补救。

### 常见的注销入口

- `unregister(event, callback)`
- `unregisterNamespace(namespace)`
- `unregisterByTags(tags)`
- `unregisterEvent(event)`

如果你在测试、插件加载或临时开关场景里动态注册回调，这些方法会比手工维护一堆布尔开关更可靠。

## filter：真正决定回调能不能跑

Java 当前的 filter 执行顺序是：

1. 全局过滤器 `addGlobalFilter(...)`
2. 事件级过滤器 `addFilter(event, ...)`
3. 回调级过滤器 `register(..., eventFilters, ...)`

`FilterAction` 当前支持四种动作：

- `CONTINUE`
- `STOP`
- `SKIP`
- `MODIFY`

对应的结果结构是 `FilterResult`。也就是说，filter 不只能“拦不拦”，还可以直接改参数。

### 当前内置过滤器

Java 仓库里当前公开了 7 个内置 filter：

- `AuthFilter`
- `CircuitBreakerFilter`
- `ConditionalFilter`
- `LoggingFilter`
- `ParamModifyFilter`
- `RateLimitFilter`
- `ValidationFilter`

### 一个最实用的入门例子

```java
import com.openjiuwen.core.runner.callback.ValidationFilter;

framework.register(
        "invoice.submit",
        kwargs -> "ok:" + kwargs.get("amount"),
        0,
        false,
        "finance",
        null,
        List.of(new ValidationFilter(data ->
                data.get("amount") instanceof Integer amount && amount > 0)),
        null,
        null,
        0,
        0.0,
        null,
        "invoice_validator"
);
```

这一层非常适合做：

- 参数合法性校验
- 限流
- 熔断
- 条件执行
- 统一参数改写

## 触发模式：不只有 `trigger(...)`

`AsyncCallbackFramework` 当前公开了多组常用触发入口：

| 方法 | 作用 | 适用场景 |
| --- | --- | --- |
| `triggerResults(...)` | 顺序执行并收集结果 | 需要回调返回值时的默认主线 |
| `trigger(...)` | 触发事件但不返回结果 | `DecoratorFramework` 兼容入口 |
| `triggerParallel(...)` | 并发执行回调 | 多个独立 I/O 回调 |
| `triggerUntil(...)` | 按顺序执行直到某个结果满足条件 | 首个命中即停 |
| `triggerChain(...)` | 把上一回调结果传给下一回调，并支持回滚 | 事务式多步流程 |
| `triggerWithTimeout(...)` | 给整个事件设置总超时 | SLA 控制 |
| `triggerDelayed(...)` | 延迟触发 | 定时或稍后执行 |
| `triggerStream(...)` / `triggerGenerator(...)` | 把多项结果整理成 `Iterator` | 批量输入或可迭代结果聚合 |

### Java 当前实现要特别注意的两点

1. `triggerParallel(...)` 当前用的是 `Executors.newFixedThreadPool(...)`，因此这里不应写成虚拟线程执行器。
2. `triggerStream(...)` 和 `triggerGenerator(...)` 虽然返回 `Iterator<?>`，但当前实现会先把结果聚合进 `List`，再返回 iterator；它们不是逐项实时推送。

所以如果你是冲着“边生产边消费”的严格流式语义来用这两个接口，当前 Java 实现还没到那个粒度。

## chain / rollback：适合多步流程，而不是简单观察

如果你的多个回调之间不是独立关系，而是：

- 第一步成功后才能做第二步
- 中途失败要回滚前面的步骤

就应该用 `triggerChain(...)`，而不是普通 `trigger(...)`。

### `ChainContext` 里有什么

`ChainContext` 当前会保存：

- 原始 `args`
- 原始 `kwargs`
- 已执行回调的 `results`
- 可共享的 `metadata`
- 当前索引、开始时间、是否完成、是否回滚

也就是说，链里的回调不只能看“上一个结果”，还可以通过 `context.setMetadata(...)` / `getMetadata(...)` 共享额外状态。

### 触发回滚的方式

- 回调返回 `ChainResult(action = ROLLBACK, ...)`
- 回调最终抛错
- 回调超时且重试耗尽

一旦回滚，`CallbackChain` 会按执行逆序调用已登记的 `rollbackHandler`。

## hook：生命周期里的插桩点

`HookType` 当前定义了四种枚举值：

- `BEFORE`
- `AFTER`
- `ERROR`
- `CLEANUP`

但要注意 Java 当前实现的真实行为：

- `triggerResults(...)` 与 `triggerGenerator(...)` 主路径明确执行的是 `BEFORE`、`AFTER`、`ERROR`
- `CLEANUP` 虽然在枚举里存在，但当前 `AsyncCallbackFramework` 主触发路径没有显式调用它

### 错误不会默认终止整个事件

这是 Runner callback 和很多人直觉不一样的地方：

- 某个 callback 抛错后，框架会更新 metrics、执行 `ERROR` hook、写日志
- 如果 `ERROR` hook 没有要求重抛，`triggerResults(...)` 会继续跑后面的回调

真正把错误重新抛出的做法，是在 `ERROR` hook 里往 `hookKwargs` 写 `_raise`。`BaseGuardrail` 当前就是用这个机制把 guardrail block 重新抛回调用方的。

## metrics / history / state persistence：这套框架不只是事件总线

### 指标

`CallbackMetrics` 当前记录：

- `call_count`
- `avg_time`
- `min_time`
- `max_time`
- `error_count`
- `error_rate`
- `last_call_time`

对应入口：

- `getMetrics(...)`
- `resetMetrics()`
- `getSlowCallbacks(threshold)`

### 历史

历史默认是关闭的，需要显式：

```java
framework.enableEventHistory(true);
```

当前实现会把事件历史保存在内存里，默认上限是 `1000` 条。对应能力包括：

- `getEventHistory(...)`
- `replayEvents(...)`

### 状态快照

`saveState(filepath)` 会把：

- callback 元数据
- metrics
- history

写成 JSON 文件。但它不会保存 Java 函数本体，所以它更适合观测与排查，不是完整的“回调函数持久化方案”。

## DSL 本质上是包装函数

`AsyncCallbackFramework` 里提供了一组便于组织事件逻辑的 DSL 名称：

- `on(...)`
- `triggerOnCall(...)`
- `emits(...)`
- `emitsStream(...)`
- `emitAround(...)`
- `transformIo(...)`
- `transformIoByEvents(...)`

这些 DSL 的本质都是：

- 返回一个新的 `Function<Map<String, Object>, Object>`
- 需要你自己显式包装原函数再调用

而且当前仓库里还没有“自动把所有 Tool / LLM / Workflow 调用统一接到 transform 事件上”的公开实现，因此 transform 系列能力仍需要显式包装。

## 它和 Guardrail、Runner、Session 的关系

### 和 Runner 的关系

- `RunnerImpl` 在初始化时创建一个全局 `AsyncCallbackFramework`
- `Runner.getCallbackFramework()` / `Runner.callbackFramework` 会把这个全局实例暴露出来

所以它是 **Runner 级** 能力，不是某个 workflow session 私有的回调表。

### 和 Guardrail 的关系

`BaseGuardrail.register(framework)` 当前会：

1. 给目标事件加一个 `HookType.ERROR` hook，用于重抛异常
2. 以高优先级回调注册真正的风险检测逻辑

也就是说，guardrail 不是 callback framework 旁边的另一套机制，它就是建立在这套 Runner callback 之上的。

### 和 Session 调测的关系

Session 那边的 `CallbackManager`、`BaseHandler`、`TriggerEvent`、`Tracer` 是另一套 per-session 分发链路。它们的关注点是：

- 节点生命周期事件
- trace span
- `TraceSchema` 流输出

这和 Runner 级 `AsyncCallbackFramework` 的关注点不同：

- 全局事件注册
- 过滤 / 回滚 / 并发 / 历史 / metrics

两者都叫 callback，但不是同一个层次的 callback。

## 还有一个实际入口：agent rail

Java 当前 `AgentCallbackManager.registerRail(...)` / `BaseAgent.registerRail(...)` 是基于 `Runner.getCallbackFramework()` 做的。它会把 agent 事件名加上 `agentId_` 前缀，再注册到全局 callback framework 上。

这意味着：

- agent rail 不是独立事件系统
- 全局 agent rail 只是对全局 callback framework 做了一层 agent 作用域封装

### 实例级 agent rail

Java 还提供实例级 agent rail，用于只影响当前 Agent 对象实例：

- `BaseAgent.registerInstanceRail(AgentRail rail)` / `BaseAgent.unregisterInstanceRail(AgentRail rail)`
- `AgentCallbackManager.registerInstanceRail(AgentRail rail, Object agent)` / `AgentCallbackManager.unregisterInstanceRail(AgentRail rail, Object agent)`
- `AgentCallbackManager.clearInstance(AgentCallbackEvent event)`
- `AgentCallbackManager.hasInstanceHooks(AgentCallbackEvent event)`

实例级 agent rail 不进入全局 Runner callback framework，也不用 `agentId` 做隔离。它绑定的是当前 Java Agent 对象实例，所以即使两个 Agent 使用相同 card id，实例级 rail 也互不影响。Java 仅提供 camelCase 入口，没有 `register_instance_rail`、`unregister_instance_rail`、`clear_instance` 或 `has_instance_hooks`。

同一事件触发时，执行顺序固定为：

1. 先跑全局 callback，包括 `registerCallback(...)` 和全局 `registerRail(...)` 接入的回调。
2. 再跑当前 Agent 对象的实例 callback，即 `registerInstanceRail(...)` 接入的回调。

两个 scope 内部分别按 priority 数字越大越先执行，同 priority 按注册顺序执行；全局和实例之间不做跨 scope priority 比较。因此，一个低 priority 的全局 rail 仍然会早于任何实例级 rail 执行。

异常处理也按阶段短路：普通异常记录或忽略后继续执行后续回调；`AbortError` / `Error` 会传播并短路。如果全局阶段传播了 `AbortError` / `Error`，不会继续进入实例阶段。

使用实例级 rail 时还要注意三个边界：

- 注销实例级 rail 时，SDK 使用注册时保存的 callback 对象身份；不会重新调用 `rail.getCallbacks()`，从未注册或已注销的 rail 会直接完成注销。
- 同一 Agent 对象不承诺并发安全，避免在多个线程里同时改同一个对象的实例级 rail。
- SDK 不检测同一 rail 是否同时注册为全局 rail 和实例级 rail；如果需要双注册，需要调用方自己承担重复触发和注销顺序的语义。

## 当前 Java 实现里要特别注意的点

- 页名虽然叫“异步回调框架”，但回调签名本身是同步 `Function<Map<String, Object>, Object>`。
- `triggerResults(...)` 遇到单个回调异常时默认会继续执行后续回调；是否中断取决于 hook 或链式回滚语义。
- `triggerStream(...)` / `triggerGenerator(...)` 当前不是严格增量迭代，而是先聚合后返回 `Iterator`。
- `HookType.CLEANUP` 已定义，但当前主触发路径没有显式执行它。
- 当前仓库没有公开的“全局自动包装 Tool / LLM / Workflow 调用到 transform 事件”的实现。
