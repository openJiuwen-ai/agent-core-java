# 算力亲和：KV Cache Release 全链路

这里重点说明 `com.openjiuwen.core.context.context.KVCacheManager` 与配套的 `InferenceAffinityModel` / `InferenceAffinityModelClient`：一套让上下文引擎在压缩或卸载历史消息后，主动通知推理引擎（vLLM + openJiuwen-vllm-affinity 插件）释放失效 KV cache block 的优化链路。主线是开 `ContextEngineConfig.enableKvCacheRelease(true)`，让 `SessionModelContext.getContextWindow` 末尾自动 diff 上一轮与当前窗口，发现前缀变化时通过 `/release_kv_cache` 端点告知推理后端从指定 index 起的 block 可释放。

## 功能定位

先看四个关键问题：

1. Java 里怎样打开 KV cache release 开关，并指定走 InferenceAffinity provider。
2. 上下文引擎做压缩/卸载后，怎样自动触发 release 而不破坏处理器链。
3. 为什么有两条 release 路径（`InferenceAffinityModel` 直连 vs `Model` 委托 client），何时各走一条。
4. release 调用失败（端点未实现、4xx/5xx、网络异常）时怎样容错而不中断 Agent 循环。

## 核心概念

| 对象 | 作用 | 你需要关心什么 |
| --- | --- | --- |
| `KVCacheManager` | diff + 分发 | 持 `sessionId` 与上一轮 `ContextWindow`，调 `release(window, model)` 触发 |
| `ContextWindow` | 窗口快照 | release 比较的输入，包含 system/context messages 与 tools |
| `InferenceAffinityModel` | Path 1 独立入口 | demo / 直接构造场景，持 `InferenceAffinityModelClient` |
| `Model` | Path 2 包装入口 | `ReActAgent` 常用路径，持 `BaseModelClient`，可能为 `InferenceAffinityModelClient` |
| `BaseModelClient` | 客户端抽象基类 | 默认 `supportsKvCacheRelease()` 返 `false`，`release(...)` no-op |
| `InferenceAffinityModelClient` | HTTP 叶节点 | `@Override` release → `POST /release_kv_cache` |
| `ContextEngineConfig` | 配置开关 | `enableKvCacheRelease` 默认 `false`，opt-in |
| `ReActAgent.buildContextWindowKwargs()` | kwargs 注入入口 | 决定是否把 `llm` 塞进 kwargs 透传到 `getContextWindow` |

### release 触发时机

只在 `SessionModelContext.getContextWindow` 末尾触发，**不在 `addMessages` 阶段**。原因：release 需要比较的是「上一轮送入模型的窗口」与「本轮即将送入模型的窗口」，只有处理器链跑完后窗口才稳定，此时 diff 才准确。

### 前缀 diff 语义

`KVCacheManager.checkReleaseNeeded(window)` 比较两类元素：

- **messages**：从前往后逐条 `equals` 比较，首个不一致的 index 即 `messagesReleasedIndex`；若全一致则 `msgIdx = prevMsgs.size()`（视为无需 release）。
- **tools**：同样逻辑，得 `toolsReleasedIndex`。

只要任一类检测到变化（`shouldRelease=true`），且至少一个 index 非 null，就调 model 的 `release(...)`。

### 双路径分发

```java
if (model instanceof InferenceAffinityModel iam) { ... }       // Path 1: 独立类
else if (model instanceof Model m && m.supportsKvCacheRelease()) { ... }  // Path 2: Model 包装
```

两条路径最终都落到 `InferenceAffinityModelClient.release(...)` 发 HTTP。区别只是入口形态：

- Path 1：`InferenceAffinityModel` 是独立类，demo 或直接构造场景常用。`ReActAgent` 不走这条。
- Path 2：`Model` 是 factory 路径，`ReActAgent` 默认用 `Model` 持 `BaseModelClient`，client 可能是 `InferenceAffinityModelClient`。`Model.supportsKvCacheRelease()` 委托 client 判断。

## 设计决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| model 注入位置 | `ReActAgent.buildContextWindowKwargs()` | kwargs 是已有通道，无需新签名 |
| model 类型检查 | 双路径 `instanceof InferenceAffinityModel` OR `instanceof Model` | 用 `instanceof` + `supportsKvCacheRelease()` 等价 duck typing |
| release 触发位置 | `SessionModelContext.getContextWindow` 末尾 | 处理器跑完再 release，diff 才准确 |
| 不可逆性 | release 失败容错 catch + warning | HTTP 404/500 不应中断 Agent 循环 |
| 配置开关 | `ContextEngineConfig.enableKvCacheRelease` 默认 `false` | opt-in，不影响默认用户 |
| 能力探测 | `Model.supportsKvCacheRelease()` → `BaseModelClient.supportsKvCacheRelease()` | 类型安全版本 duck typing |

## 全链路

```
[Agent 侧]                [Context 侧]              [Inference 侧]

ReActAgent.callModel
  └ buildContextWindowKwargs()
        ↓ model=llm 注入 kwargs
  └ context.getContextWindow(..., kwargs)
        ↓ processors 执行压缩/卸载 → window 变化
SessionModelContext.getContextWindow 末尾
  └ kvCacheManager.release(window, model)
        ↓ diff prev vs curr window → 首个变化 index
KVCacheManager.release
  ├ Path 1: model instanceof InferenceAffinityModel
  └ Path 2: model instanceof Model && supportsKvCacheRelease
        ↓ 委托
Model.release / InferenceAffinityModel.release
  └ client.release(...)
        ↓ HTTP POST
InferenceAffinityModelClient.release
  └ POST {apiBase}/release_kv_cache
        ↓
[server] vllm + jiuwen_vllm_affinity.kv_cache_plugin
  └ api_server.release_kv_cache handler
  └ serving_chat.release_kv_cache → token-level diff
  └ EngineCore.release_kv_cache → block_hashes[release_block_index:]
  └ SingleTypeKVCacheManager.aging_block → 解绑 session
  └ TwoPhaseBlockQueue.aging_block → 移入 release 段
```

### 与 vllm-affinity 插件的契约

请求：`POST /release_kv_cache`，body 是 `ChatCompletionRequest` 超集：

```json
{
  "model": "GLM-5.2",
  "cache_salt": "session-abc",
  "cache_sharing": true,
  "messages": [...],
  "messages_released_index": 3,
  "tools": [...],
  "tools_released_index": 1
}
```

响应：

| 状态 | Body | 说明 |
| --- | --- | --- |
| 200 | `{"cache_salt": "...", "block_released": <int>}` | 成功，`block_released` = 解绑 block 数 |
| 400 | `ErrorResponse` | 请求格式错误 |
| 404 | `ErrorResponse` 或 HTML | 端点未实现（普通 OpenAI 兼容端点） |
| 500 | `ErrorResponse` | 服务端异常 |

服务端语义：`block_released` = session 绑定被解的 block 数；block 不立即释放，而是从 `normal` 段移入 `release` 段，下次分配优先复用（`free > release > normal`）。

## 快速开始

最小示例：开 `enableKvCacheRelease`，配 InferenceAffinity provider，指向 vllm + affinity 插件端点。

```java
import com.openjiuwen.core.context.schema.ContextEngineConfig;
import com.openjiuwen.core.foundation.llm.Model;
import com.openjiuwen.core.foundation.llm.schema.ModelClientConfig;
import com.openjiuwen.core.foundation.llm.schema.ModelRequestConfig;
import com.openjiuwen.core.singleagent.agents.ReActAgent;
import com.openjiuwen.core.singleagent.schema.ReActAgentConfig;

ContextEngineConfig ceConfig = ContextEngineConfig.builder()
        .maxContextMessageNum(200)
        .defaultWindowRoundNum(10)
        .enableKvCacheRelease(true)   // ← 开关
        .build();

ModelClientConfig clientConfig = ModelClientConfig.builder()
        .clientProvider("InferenceAffinity")  // 或 "inference_affinity"
        .apiBase("http://vllm-host:8000")      // vllm + affinity 插件端点
        .apiKey("...")
        .build();

Model llm = new Model(clientConfig, new ModelRequestConfig());
ReActAgent agent = ReActAgent.builder()
        .config(ReActAgentConfig.builder()
                .contextEngineConfig(ceConfig)
                .build())
        .llm(llm)
        .build();
```

开关打开后，每个 `getContextWindow` 末尾会自动 diff 并 release；不需要手动调 `kvCacheManager.release(...)`。

### 手动调用（demo 场景）

若不走 `ReActAgent` 而是直接构造 `InferenceAffinityModel` + 手动管理 `SessionModelContext`，可显式调 release：

```java
InferenceAffinityModel model = new InferenceAffinityModel(clientConfig, modelRequestConfig);
ContextWindow window = context.getContextWindow(sys, tools, null, null, Map.of("model", model));
// getContextWindow 内部已调 release；若需手动补一次：
// kvCacheManager.release(window, model);
```

## Demo 与测试用例原理

PR `eb4b88fd 支持推理引擎协同算力亲和` 附带 `examples/kv-cache-demo` 子模块与两组单元测试，它们是验证链路「真的会 diff + 真的会发 HTTP + 真的不崩」的核心证据。

### `examples/kv-cache-demo`：端到端压测

入口 `MicroCompactProcessorKvCacheExample.main` 委托 `MicroCompactProcessorKvCacheExampleSupport.run`。设计目标写在 Support 类 Javadoc：

1. **大 tool result 制造 KV 压力**：`WeatherReporter` mock 工具返回 ~48 KB（`TOOL_RESULT_CHARS = 48 * 1024`）内容，单次调用占多个 KV block。
2. **多轮 + 同工具累计触发压缩**：`ROUNDS_PER_WORKER = 10`，`MicroCompactProcessorConfig` 设 `triggerThreshold=1, keepRecentPerTool=1`。`MicroCompactProcessor` 触发条件是某工具 ToolMessage 数 > `triggerThreshold + keepRecentPerTool`（即 >2）；达到后把除最近 `keepRecentPerTool` 条外的旧 ToolMessage 内容替换成 `[Old tool result content cleared]`。
3. **并发拉满 vllm batch**：`WORKER_COUNT = 16`，`ThreadPoolExecutor`（`X.CON.06` 合规：bounded queue + 命名 daemon 线程 + `CallerRunsPolicy`）跑 16 个 worker session。
4. **provider 切换跑 A/B**：`apiconfig.json` 里 `MODEL_PROVIDER=InferenceAffinity` 开 release；`=OpenAI` 关 release 作对照组。

链路（ON 模式，单 worker 单轮）：

```
worker.runWorker
  └ Runner.runAgent(query, conversation_id)            # query="北京天气如何"
     └ ReActAgent iteration 1/3
        ├ LLM 决定调 WeatherReporter(city=北京)
        ├ 工具执行 → 48KB ToolMessage 入 session
        └ LLM 第二轮读 ToolMessage 生成最终回复
  └ round 2: session 已有 1 条旧 ToolMessage + 新一轮又调一次工具
     ├ 新 ToolMessage 加入 → MicroCompactProcessor.triggerAddMessages=true（累计 >2）
     ├ onAddMessages: 旧 ToolMessage.content 替换为 [Old tool result content cleared]
     └ ReActAgent.callModel → context.getContextWindow(kwargs={model=llm})
        ├ 处理器链跑完 → ContextWindow 稳定
        └ getContextWindow 末尾: kvCacheManager.release(window, llm)
           ├ diff prev vs curr: 旧 ToolMessage index 处内容变化 → msgIdx
           └ Model.release → InferenceAffinityModelClient.release → POST /release_kv_cache
```

**为什么替换内容会触发 release？** `KVCacheManager` 对 messages 从前往后逐条 `equals` 比较找出首个变化 index；旧 ToolMessage 被替换成 `[Old tool result content cleared]` 后，那条 message 与上一轮窗口的不一致，首个变化 index 落在该位置。前缀那部分（system + 早期 user）一致，所以只 release 后缀 block。

**ON 与 OFF 该看什么**（README 与 Support 类尾部打印提示）：

| 观测项 | ON（InferenceAffinity） | OFF（OpenAI） |
| --- | --- | --- |
| vllm 日志 `[jiuwen-kv] 3-release / 4-evict` | 出现 | 不出现 |
| Prefix cache hit rate | 高（统计 59%） | 低（统计 50.75%） |
| GPU KV cache usage | 高（32.73%） | 低（20.39%） |
| 平均 prompt throughput (tokens/s) | 6554.35 | 6022.22 |
| 平均 generation throughput (tokens/s) | 12.84 | 8.85 |

> 上表数字取自一次实测（OFF: 119 sample, ON: 119 sample）；量级会随负载波动，但 ON 各指标全面高于 OFF 的结论稳定。

Demo 末尾打印 `total_wall_seconds` / `sum_round_seconds` / `max_round_seconds` / `avg_round_seconds`，以及每轮 `[wN rM]` 行 + `[wN context] messages=, tokens~=, active_tool=, cleared_tool=` 快照，可一眼看出压缩是否生效（`cleared_tool` 应递增）。

关键断言形态（Path 1）：

```java
verify(mockModel).release(eq("session-1"), eq(w1.getMessages()), eq(1),
    eq(w1.getToolList()), isNull(), isNull());
```

注意 release 传的是 **上一轮窗口的 messages 与 tools**（`w1.getMessages()`），不是当前轮 `w2` —— 语义是「告诉推理引擎从 prev window 的第 N 条起失效」。`msgIdx=1` 因 `SystemMessage` 在 index 0 保持一致，UserMessage 在 index 1 内容变化。

## 配置与运行方式

### 开关与能力探测

`enableKvCacheRelease=true` 后，`ReActAgent.buildContextWindowKwargs()` 会：

1. 读 `ContextEngineConfig.enableKvCacheRelease`。
2. 检查 `llm.supportsKvCacheRelease()`：
   - 都为 true → kwargs 注入 `model=llm`，链路打通。
   - 开关 true 但不支持 → 打一次 warning（`kvReleaseWarningLogged` 守护，不重复），kwargs 不注入 `model`，链路不生效。
   - 开关 false → kwargs 不注入 `model`，不 warning。

`kvReleaseWarningLogged` 在 `config` 变更时重置（`oldConfig.contextEngineConfig != newConfig.contextEngineConfig`），允许换配置后重新探测。

### InferenceAffinity provider 注册

`InferenceAffinityModelClientFactory` 默认以 `InferenceAffinity` 与 `inference_affinity` 两个名字注册到 fallback factory 列表。`ModelClientConfig.clientProvider` 填任一即可命中。

### HTTP body 字段映射

| Java 字段 | HTTP body key | 说明 |
| --- | --- | --- |
| `sessionId` | `cache_salt` | session 级隔离 |
| `messages` | `messages` | 上一轮窗口的完整消息 |
| `messagesReleasedIndex` | `messages_released_index` | 首个变化消息 index |
| `tools` | `tools` | 上一轮窗口的 tools（可选） |
| `toolsReleasedIndex` | `tools_released_index` | 首个变化 tool index（可选） |
| `model` | `model` | 模型名，null 时 fallback 到 `ModelRequestConfig.modelName` |

`cache_sharing` 固定为 `true`（与 release 语义配套）。

### 容错行为

`InferenceAffinityModelClient.release` 仅在 HTTP 2xx 返 `true`，否则返 `false`，不抛异常。`KVCacheManager.release` 内 try/catch，失败仅打 `Loggers.CONTEXT_ENGINE.warning`，不中断 Agent 循环。即：

- 端点未实现（404）→ warning，Agent 继续。
- 服务端异常（500）→ warning，Agent 继续。
- 网络异常 → warning，Agent 继续。
- 成功（200）→ 无额外 log，block_released 数返给插件侧记录。

## 适用场景

### 何时打开 `enableKvCacheRelease`

- 用 InferenceAffinity provider 指向 vllm + openJiuwen-vllm-affinity 插件。
- 多轮长对话，上下文引擎会触发压缩（`DialogueCompressor` / `RoundLevelCompressor`）或卸载（`MicroCompactProcessor` / `MessageOffloader`）。
- 并发 session 较多，LRU 尾部滞后导致命中率下降明显。

### 何时不要打开

- 用普通 OpenAI / DashScope 端点（不支持 `/release_kv_cache`）。
- 单轮对话或上下文从不变化（release 无意义，徒增 HTTP 开销）。
- 推理后端不是 vllm + affinity 插件组合。

### 两条路径的选择

| 路径 | 入口 | 何时用 |
| --- | --- | --- |
| Path 1 | `InferenceAffinityModel` 直连 | demo、直接构造、不走 `ReActAgent` |
| Path 2 | `Model` 委托 `BaseModelClient` | `ReActAgent` 默认路径，client 为 `InferenceAffinityModelClient` |

`ReActAgent` 走 Path 2；demo 手动调可走 Path 1。两条路径最终都落到 `InferenceAffinityModelClient.release`。

## 暂未实现的能力

当前链路已具备完整的 diff + 双路径分发 + HTTP 容错，但下列更高阶的特性尚未覆盖：

- **工具调用 pause 期间 cache 保活**：agent 工具执行期间 session KV block 在 vllm 侧无引用，并发场景下被 LRU 淘汰。当前无 keepalive 或 `retention_directives` 标注能力。
- **会话结束时主动释放整个 session cache**：`SessionModelContext` 销毁或 session timeout 时无主动调 `release_session(sessionId)` 的入口，仍依赖引擎侧 LRU 淘汰。
- **多 session 优先级标注**：多 agent 并发时各 session KV block 互相 LRU 淘汰，当前无优先级字段注入能力。
- **主动前缀预热**：session 创建后、用户首条消息前，无主动发最小请求预热 system prompt + tools 前缀的机制。
- **cache 命中率观测**：`InferenceAffinityModelClient` 解析了 `cacheTokens` 进 `UsageMetadata`，但未上报到 `ContextStats` 或独立 `CacheStats`，无法在压缩触发前后对比命中率。
- **压缩决策感知 cache 状态**：`ContextProcessor` 触发压缩只看 token 数 / 消息数阈值，不考虑 cache 命中状态。

## 使用边界

- 这里聚焦 Java 当前 `com.openjiuwen.core.context.context.KVCacheManager` 与配套 `InferenceAffinityModel` / `InferenceAffinityModelClient` 已存在的能力。
- 推荐主线落在 `ContextEngineConfig.enableKvCacheRelease(true)` + `InferenceAffinity` provider + `ReActAgent` 默认路径（Path 2）。
- demo / 直接构造场景可走 Path 1（`InferenceAffinityModel` 直连）。
- 推理后端必须是 vllm + openJiuwen-vllm-affinity 插件；普通 OpenAI 兼容端点不支持 `/release_kv_cache`，会返 4xx，框架容错跳过。
- 文档不替代正式的 API 文档；具体方法签名与字段语义以源码为准。
