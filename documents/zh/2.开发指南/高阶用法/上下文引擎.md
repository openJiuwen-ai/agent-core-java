# 上下文引擎

Java 版上下文主线围绕 `com.openjiuwen.core.context` 展开。`ContextEngine` 负责创建和复用上下文，`ModelContext` 负责承载消息与窗口构造，`ContextProcessor` 负责压缩和卸载，`ContextWindow` 则是最终发给模型的一次窗口快照。

如果你的需求是“控制当前调用时带哪些历史消息、保留多少轮、是否把旧消息卸载出去”，应该看这一页；如果你的需求是“持久保存用户长期偏好”，请回到 `LongTermMemory`；如果你在看 `examples/context_evolver`，那是把 context API 和扩展算法结合起来的进阶路径，而不是根包上下文 API 的等价替身。

## 能力定位

- `ContextEngine` 管理 `sessionId + contextId` 级别的上下文生命周期。
- `SessionModelContext` 是当前默认实现，负责消息缓冲、处理器链、窗口构造、状态保存和卸载缓存。
- `ContextWindow` 表示一次真正送入模型的窗口，而不是整个上下文池。
- `ContextProcessor` 让压缩、卸载、总结这类动作以处理器链的方式插入 `addMessages()` 和 `getContextWindow()` 两个阶段。
- `StatefulContext` 与 `OffloadCapableContext` 则定义了“可保存状态”和“可卸载消息”的扩展能力边界。

## 核心类型

| 类型 | 作用 | 何时使用 |
| --- | --- | --- |
| `ContextEngine` | 上下文引擎入口，负责创建、缓存、清理和保存上下文 | 管理整个上下文生命周期时 |
| `ContextEngineConfig` | 配置消息上限、窗口默认值、reload 与 KV cache 释放 | 初始化上下文引擎时 |
| `ModelContext` | 上下文抽象 API，暴露消息管理和窗口构造方法 | 业务逻辑只依赖抽象接口时 |
| `SessionModelContext` | 当前默认实现，同时实现 `StatefulContext` 和 `OffloadCapableContext` | 需要理解真实行为细节时 |
| `ContextWindow` | 最终发给模型的窗口对象，包含 system/context messages、tools 和统计信息 | 调用模型前取窗口时 |
| `ContextProcessor` | 上下文处理器抽象 | 想对消息做压缩或卸载时 |
| `ProcessorSpec` | 通过类型名和配置描述处理器实例 | 创建 context 时装配处理器链 |

当前引擎启动时会预注册五个内置处理器：

- `CurrentRoundCompressor`
- `DialogueCompressor`
- `RoundLevelCompressor`
- `MessageOffloader`
- `MessageSummaryOffloader`

## 接入步骤

### 1. 先定清楚窗口策略，再创建引擎

`ContextEngineConfig` 里当前最重要的配置项有：

- `maxContextMessageNum`
- `defaultWindowMessageNum`
- `defaultWindowRoundNum`
- `enableReload`
- `enableKvCacheRelease`

```java
ContextEngine engine = new ContextEngine(ContextEngineConfig.builder()
        .maxContextMessageNum(200)
        .defaultWindowMessageNum(40)
        .defaultWindowRoundNum(8)
        .enableReload(true)
        .build());
```

这几个整数字段必须大于 `0`；无效值会在 `config.validate()` 阶段直接报错，而不是拖到运行时再兜底。

### 2. 用 session 和 contextId 创建或复用上下文

主入口是 `createContext(...)`：

```java
ModelContext context = engine.createContext(
        "planner",
        session,
        processors,
        historyMessages,
        tokenCounter
);
```

当前行为有几个要点：

- 缓存键是 `sessionId + "_" + contextId`
- 同一个 `sessionId + contextId` 再次调用时会复用已有上下文
- `contextId == null` 时会归一化成默认 ID
- `contextId` 中的点号会被替换成下划线

如果你只需要最简路径，也可以直接调用 `createContext(contextId, session)`。

### 3. 在 `ModelContext` 上追加消息，再构造窗口

上下文创建出来后，日常操作都在 `ModelContext` 上完成：

```java
context.addMessages(List.of(new UserMessage("你好")));
ContextWindow window = context.getContextWindow(systemMessages, tools, 20, 4);
```

这里需要区分两个概念：

- `ModelContext` 保存的是运行中的上下文状态
- `ContextWindow` 是一次实际送入模型的快照

`ContextWindow` 里会聚合：

- `systemMessages`
- `contextMessages`
- `tools`
- `ContextStats`

而 `ContextWindow.getMessages()` 返回的是 `systemMessages + contextMessages` 按顺序拼好的消息列表。

### 4. 处理器、卸载和 reload 能力都在上下文层完成

当前处理器链只参与两个阶段：

- `addMessages()`
- `getContextWindow()`

如果你要做自定义处理器，可用：

```java
ContextEngine.registerProcessor("MyProcessor", MyProcessor.class, config -> new MyProcessor());
```

再在创建 context 时传入 `ProcessorSpec`。当前默认实现 `SessionModelContext` 同时具备两种重要扩展能力：

- `OffloadCapableContext`：可把旧消息卸载到缓冲区
- `StatefulContext`：可把 `messages` 和 `offload_messages` 保存回会话状态

当 `enableReload = true` 时，`SessionModelContext` 会自动暴露 `reload_original_context_messages` 工具，并在系统消息里追加 reload 提示词；当 `enableKvCacheRelease = true` 且在 `kwargs` 里传入 `model` 时，还会尝试触发 KV cache 释放逻辑。

### 5. 会话结束或切换阶段时记得保存和清理

上下文并不会自动永久落盘。当前主流程是：

```java
engine.saveContexts(session, null);
engine.clearContext("planner", session.getSessionId());
```

- `saveContexts(session, null)` 会把当前会话下所有 `StatefulContext` 保存回 `session.updateState(Map.of("context", states))`
- `clearContext(contextId, sessionId)` 可清单个上下文
- `clearContext(null, sessionId)` 可清整个会话
- `clearContext(null, null)` 会直接清空整个上下文池

如果你把上下文和 Session 绑定起来使用，这一步应当成为显式的生命周期动作，而不是依赖 GC 或服务重启。

### 6. 把 `examples/context_evolver` 当成进阶延伸，不是根包教程

`examples/context_evolver` 值得看，但它解决的是“上下文演化 + 记忆检索增强 + summarize”这类扩展问题。阅读顺序建议是：

1. 先吃透 `ContextEngine`、`ModelContext`、`ContextWindow`
2. 再去看 `ContextEvolverQuickstartExample`

这样你才不会把扩展算法里的 `TaskMemoryService`、trajectory summarize 和 HotpotQA 循环误认成 `com.openjiuwen.core.context` 的主 API。

## 当前实现边界

- Java 当前以同步 API 为主线，围绕 `createContext(...)`、`addMessages(...)`、`getContextWindow(...)`、`saveContexts(...)` 组织。
- Java 明确暴露了 `SessionModelContext`、`StatefulContext`、`OffloadCapableContext` 和处理器注册机制，适合把“压缩、卸载、reload”写成根包上下文语义的一部分。
- `examples/context_evolver` 位于 `com.openjiuwen.extensions.context_evolver`，它是扩展能力，不是 `ContextEngine` 的同义实现。
- Java 当前的内置处理器和 reload 行为都以现有注册表和 `SessionModelContext` 为准，不应把额外的上下文工程 DSL 误写进根包 API。
