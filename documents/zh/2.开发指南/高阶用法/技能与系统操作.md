# 技能与系统操作

Java 版 skill 与 sysop 的协同关系可以概括成一句话：

> **skill 负责告诉 Agent“该看什么、该怎么做”；sysop 负责给 Agent 真正可执行的文件、代码与命令能力。**

如果把这两层混为一谈，就很容易把 `SKILL.md` 里的任务说明误解为框架自动能力，或者反过来把 `SysOperation` 的执行抽象误解为 skill 系统的一部分。

## 1. 两层模型：元数据层 vs 执行层

| 层次 | 关键对象 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| skill 元数据层 | `Skill`、`SkillManager`、`RemoteSkillUtil`、`SkillUtil`、`BaseAgent.registerSkill(...)` | 发现 skill、同步远程 skill、生成 skill prompt、把 skill 名称/描述/目录告诉模型 | 不直接执行文件读写、代码运行或命令调用 |
| sysop 执行层 | `SysOperation`、`SysOperationCard`、`OperationMode`、`SysOperationToolAdapter`、`readFile`/`executeCode`/`executeCmd` 等工具卡片 | 提供真正的系统操作能力，并把这些能力暴露给 Agent | 不理解具体 skill 的语义，也不主动决定该读哪个 `SKILL.md` |

把这张表记住，就能理解 Java 当前 skill use 的全部主线。

## 2. 为什么 skill 必须借助 sysop

### 2.1 skill prompt 只是在“提示模型去读技能”

`SkillUtil.getSkillPrompt()` 的职责，是把已注册 skills 组织成一段系统提示词。内容会告诉模型：

- 当前有哪些 skill；
- 每个 skill 的描述是什么；
- skill 目录在哪里；
- 需要时应使用 `readFile` 去读对应的 `SKILL.md`。

这说明 skill 的第一步，本质上就是一个**读取技能说明文件**的动作，而这个动作本身并不由 `SkillUtil` 执行。

### 2.2 Java 当前不会自动替你挂载 sysop 工具

这是 Java 版和一些读者直觉之间最容易错位的地方：

- `registerSkill(...)` 会注册 skill 元数据；
- `registerRemoteSkills(...)` 会从 GitHub 下载 skill 文件；
- 但当前实现**不会自动把** `readFile`、`executeCode`、`executeCmd` 挂到 Agent。

`ReActAgent` 在发现已有 skills 但能力列表里缺少 `readFile` 时，只会发出告警，不会替你自动修复能力集。

### 2.3 skill 需要什么工具，取决于 skill 本身

最小依赖通常是：

- `readFile`：读取 `SKILL.md`

进一步依赖则看 skill 的任务说明：

- 需要生成或修改文本文件时，常见还要 `writeFile`；
- 需要运行脚本时，常见要 `executeCode`；
- 需要调用本地命令行时，常见要 `executeCmd`。

所以 skill 与 sysop 的协同不是“框架神秘联动”，而是一个明确的依赖关系：**skill 决定要做什么，sysop 决定能不能做、怎么做。**

## 3. 主线示例：`examples/skill_use`

`examples/skill_use/SkillUseExample.java` 是当前 Java 仓库里最适合拿来理解 skill + sysop 协同的一条主线。

### 3.1 框架通用能力：固定的协同骨架

从框架角度看，它做了五件通用的事：

1. 创建 `ReActAgent`；
2. 注册一个 `OperationMode.LOCAL` 的 `SysOperationCard`，并把 `sysOperationId` 写回 Agent 配置；
3. 显式把需要的 sysop 工具卡片挂到 `AbilityManager`；
4. 注册本地 skills，并可选同步远程 GitHub skill；
5. 调用 `Runner.runAgent(...)` 执行任务。

用最小化代码表达，就是：

```java
ReActAgent agent = createAgent(filesBaseDir, outputDir, maxIterations);
String sysOperationId = ((ReActAgentConfig) agent.getConfig()).getSysOperationId();

addSysOpTool(agent, sysOperationId, "fs", "readFile");
addSysOpTool(agent, sysOperationId, "code", "executeCode");
addSysOpTool(agent, sysOperationId, "shell", "executeCmd");

agent.registerRemoteSkills(skillsDir.toString(), githubTree, token); // 可选
agent.registerSkill(skillsDir.toString());

Runner.runAgent(agent, Map.of("query", query, "conversation_id", "492"), null, null);
```

这条骨架对绝大多数 Java skill 场景都成立。

### 3.2 示例特定路径：`image_resizer` 不是框架强约束

`skill_use` 示例选择的 skill 是图片缩放，这使它带有一些**示例特定条件**：

- 默认会尝试从 GitHub 下载 `image_resizer`；
- 输入目录里放的是图片；
- skill 内部要通过 Python/OpenCV 执行缩图逻辑；
- 本机需要可直接调用的 `python`，且 Python 环境可能需要 `opencv-python`。

这些都属于**示例路径**，不是所有 Java skills 都必须具备的框架约束。

对框架来说，真正通用的是：

- skill 说明文件进入 prompt；
- Agent 有权限读取该说明文件；
- skill 需要的系统工具被显式暴露；
- 最后由 `AbilityManager` 在 tool call 阶段调用这些工具。

## 4. 补充入口：`examples/skill_create`

`examples/skill_create` 展示的是协同链路的另一个方向：不是“使用已有 skill 完成任务”，而是“借助系统能力生成新 skill”。

### 4.1 示例流程

当前 Java 示例的完整流程是：

1. 下载一个 PDF；
2. 用 `PDFParser` 提取文本并写成 Markdown；
3. 创建 `SkillCreator`；
4. `SkillCreator.createAgent()` 内部注册本地 sysop；
5. 额外挂载 `readFile`、`writeFile`、`listFiles`、`listDirectories`、`searchFiles`；
6. 注册 skill creator 自带的本地 skills；
7. 调用 `generate(...)` 输出新的 skill 目录。

### 4.2 这里哪些是框架通用能力，哪些只是示例 glue code

| 层次 | 内容 |
| --- | --- |
| 框架通用能力 | `SkillCreator` 依赖 sysop 文件工具，让 Agent 能读取输入 Markdown、枚举目录并写出 `SKILL.md` 等结果文件 |
| 示例 glue code | 下载 PDF、提取文本、生成中间 Markdown 文件 |

也就是说，`examples/skill_create` 证明的是：**skill 生成这件事本身，也离不开 sysop 作为底层执行层。** 但并不是说所有 skill 创建都必须从 PDF 开始。

## 5. 一个实用的协同判断表

当你在设计一个新 skill 时，可以用下面这张表快速判断应该补哪些 sysop 工具：

| skill 任务形态 | 至少需要的系统能力 | 典型工具名 |
| --- | --- | --- |
| 只读技能说明、查找已有文本 | 文件读取 | `readFile` |
| 根据模板生成/改写文本文件 | 文件读取 + 文件写入 + 文件检索 | `readFile`、`writeFile`、`listFiles`、`searchFiles` |
| 执行脚本、数据处理、代码生成验证 | 文件读取 + 代码执行 | `readFile`、`executeCode` |
| 调用本地 CLI、构建工具或系统命令 | 文件读取 + 命令执行 | `readFile`、`executeCmd` |

这张表也解释了为什么：

- `skill_use` 更像“读取说明 + 执行代码/命令”；
- `skill_create` 更像“读取素材 + 生成文件树”。

## 6. 推荐协同顺序

对当前 Java 公开 API，比较稳的协同顺序如下：

1. **先定 skill 来源**：本地已有 skill，还是需要先从 GitHub 同步；
2. **再定 sysop 模式**：当前优先 `LOCAL`；
3. **按最小权限挂工具**：只暴露这次任务真正需要的 sysop tool cards；
4. **注册 skills**：让 `SkillManager` 生成元数据，并让 `ReActAgent` 在运行时补 skill prompt；
5. **执行任务**：由 Agent 根据 skill prompt 决定何时读取 `SKILL.md`，并调用 sysop 工具完成后续步骤。

## 7. 当前 Java 边界与注意事项

- skill 元数据层与 sysop 执行层已经都公开，但两者之间**没有“根据 skill 自动推断工具集”**的框架能力；
- GitHub 远程 skill 当前本质是文件下载能力，仍需后续本地 `registerSkill(...)`；
- `OperationMode.SANDBOX` 已进入 API，但当前 `SandboxFsOperation` / `SandboxCodeOperation` / `SandboxShellOperation` 仍未实现；
- 示例里的 Python、OpenCV、PDF 等外部依赖属于具体任务环境，不应理解成 Java skill 框架的硬前置条件。
