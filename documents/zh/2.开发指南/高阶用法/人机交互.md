# 人机交互

Java 版的人机交互能力集中在 `com.openjiuwen.core.session.interaction`。它解决的不是“前端怎么渲染问题”，而是运行时更本质的一条链路：

1. 某个节点或 agent 发现还缺用户输入；
2. 当前执行被打断并返回交互事件；
3. 调用方收集回答；
4. 用 `InteractiveInput` 在同一个 session / conversation 中恢复执行。

这条链路是理解 `QuestionerComponent`、workflow 中断恢复、`WorkflowAgent` 多轮补问和 checkpointer 的前提。

## 核心类型

| 类型 | 作用 | 典型使用场景 |
| --- | --- | --- |
| `InteractiveInput` | 承载用户回填内容的值对象 | 恢复 workflow / agent 执行 |
| `InteractionOutput` | 输出给调用方的交互载荷，核心字段只有 `id` 与 `value` | 提示 UI 或命令行该问什么 |
| `BaseInteraction` | 交互处理基类，负责从 session 状态中合并排队输入 | workflow / agent 交互共用底座 |
| `WorkflowInteraction` | 工作流级交互器，通过 `GraphInterrupt` 打断图执行 | 节点补问、工作流等待输入 |
| `AgentInteraction` | agent 级交互器，通过 checkpointer + `AgentInterrupt` 打断 | agent 多轮对话或上层控制器恢复 |
| `SimpleAgentInteraction` | 更轻量的 agent 交互器，只负责 checkpoint + 中断 | 不需要输出结构化 `InteractionOutput` 时 |

## 先理解两个基本对象

### `InteractionOutput`

`InteractionOutput` 很轻量，只包含两个核心字段：

- `id`：这次交互属于哪个节点 / 会话
- `value`：要返回给调用方展示或处理的交互内容

也就是说，Java 当前的人机交互协议本质上不是一套复杂表单，而是“**谁在等输入** + **它在等待什么**”。

### `InteractiveInput`

恢复执行时，调用方要把用户回答重新封装成 `InteractiveInput`。它有两种互斥模式：

#### 1. 节点定向输入

```java
InteractiveInput input = new InteractiveInput();
input.update("questioner", "2000元");
```

这适合：

- workflow 同一轮有多个问题
- 你已经知道要把回答送回哪个节点
- `WorkflowAgent` 需要靠 node id 找回被打断的 workflow

#### 2. 原始输入

```java
InteractiveInput input = new InteractiveInput("retry");
```

这适合：

- 只需要表达“一条新的恢复指令”
- 不需要显式指定 node id
- `examples/interact` 这类失败后继续同一 session 的场景

### 一个重要限制

`InteractiveInput` 这两种模式不能混用：

- 如果已经是 `rawInputs` 模式，再调用 `update(...)` 会报错；
- `nodeId` 或 `value` 传 `null` 也会报交互输入错误。

## `BaseInteraction`：排队输入从哪里来

`BaseInteraction` 会把 session 里的 `Constant.INTERACTIVE_INPUT` 队列和默认输入合并起来，并回写到 session state。对调用方来说，这意味着：

- 如果当前 session 已经有排队输入，交互器会优先消费它们；
- 只有在没有可用输入时，才会真正触发“中断并等待用户回答”。

这也是“同一 session 继续执行”能成立的基础之一。

## 工作流级交互：`WorkflowInteraction`

`WorkflowInteraction` 负责在 workflow 节点内部打断图执行。它的语义可以概括成：

1. 先检查当前 session 是否已经有可消费的交互输入；
2. 如果有，直接返回输入，workflow 继续执行；
3. 如果没有：
   - 生成 `InteractionOutput(nodeId, value)`
   - 如有输出流则写出 `type = "__interaction__"` 的 chunk
   - 提交当前组件状态
   - 抛出 `GraphInterrupt` 包装，让图引擎进入可恢复中断态

### `id` 是怎么来的

`WorkflowInteraction` 输出的 `InteractionOutput.id` 优先取：

- `NodeSession.executableId()`

如果当前 session 不是 `NodeSession`，就退回：

- `session.sessionId()`

这也是为什么很多 workflow 恢复代码都会把组件 id / node id 保留下来。

## Agent 级交互：`AgentInteraction`

`AgentInteraction` 的核心语义与 workflow 类似，但更偏上层：

1. 如果已存在排队输入，直接返回；
2. 如果没有输入：
   - 若 session 挂了 `Checkpointer`，先执行 `interruptAgentExecute(session)`
   - 如有输出流，则写出 `InteractionOutput(session.sessionId(), value)`
   - 抛出 `AgentInterrupt`

这里要注意两点：

- agent 级 `InteractionOutput.id` 默认是 `sessionId`，而不是 workflow 里的节点 id；
- agent 级恢复一般依赖同一个 `conversation_id` / session id，而不是 workflow node id 本身。

## `SimpleAgentInteraction` 与 `AgentInteraction` 的区别

`SimpleAgentInteraction` 更轻量，只有两步：

1. 调 checkpointer 保存当前 agent 状态；
2. 直接抛 `AgentInterrupt(message)`。

它**不会**额外构造或输出 `InteractionOutput`。所以如果你需要显式交互事件载荷，就不能把它写成和 `AgentInteraction` 完全等价。

## 恢复主线一：原生 `Workflow` 的补问与继续执行

这是最适合理解底层语义的一条线。`examples/interact/WeatherAssistantInteractExampleSupport.java` 展示了完整过程：

1. 调用 `workflow.invoke(...)`
2. 如果 `WorkflowOutput.state == INPUT_REQUIRED`，从结果里提取交互问题
3. 逐个读取用户回答
4. 把回答写入 `InteractiveInput`
5. 用**同一个 sessionId** 再次调用 `workflow.invoke(...)`

示意代码如下：

```java
WorkflowOutput output = workflow.invoke(
        Map.of("query", "明天我要出差，帮我查天气"),
        session,
        null
);

if (WorkflowExecutionState.INPUT_REQUIRED.equals(output.getState())) {
    InteractiveInput reply = new InteractiveInput();
    reply.update("ask_city", "Shanghai");
    reply.update("ask_unit", "C");

    output = workflow.invoke(reply, session, null);
}
```

### `examples/interact` 演示了什么

这个 Java 示例不是抽象 demo，而是一条真实恢复路径：

- 新的 `user>` 请求会创建新的 `sessionId`
- `reply>` 与 `retry>` 都复用同一个 `sessionId`
- `AskCity` 与 `AskUnit` 会在同一轮返回多个交互问题
- `QueryWeather` 第一次固定失败
- 用户输入 `retry` 后，用 `new InteractiveInput("retry")` 在同一 session 恢复
- 会话结束时显式调用 `checkpointer.release(sessionId)`

这条路径同时把“等待输入”和“失败后继续执行”串在了一起。

## 恢复主线二：`WorkflowAgent` 的补问与继续执行

在 `WorkflowAgent` 场景里，恢复入口通常不再直接调用 `workflow.invoke(...)`，而是继续调用 `Runner.runAgent(...)` 或 `Runner.runAgentStreaming(...)`。

`examples/workflow_agent/WorkflowAgentExampleSupport.java` 的主线是：

1. 首次请求：

```java
Runner.runAgentStreaming(
        agent,
        Map.of("query", userInput, "conversation_id", conversationId),
        null,
        null,
        List.of(StreamMode.OUTPUT)
);
```

2. 当输出里出现 `__interaction__` 时，记住交互节点 id；
3. 用户输入 `reply>`；
4. 构造 `InteractiveInput.update(nodeId, userInput)`；
5. 再次调用 `Runner.runAgentStreaming(...)`，并继续复用同一个 `conversation_id`。

```java
InteractiveInput reply = new InteractiveInput();
reply.update(nodeId, userReply);

Runner.runAgentStreaming(
        agent,
        Map.of("query", reply, "conversation_id", conversationId),
        null,
        null,
        List.of(StreamMode.OUTPUT)
);
```

### 为什么 `conversation_id` 不能丢

Java 当前 `RunnerImpl` 会优先从输入里读取 `conversation_id` 作为 agent session id。对 `WorkflowAgent` 来说，这个值直接决定：

- 是否能找到之前的 agent session
- 是否能取回 `workflow_controller` 保存的中断任务
- 是否能把回答路由回正确的 workflow

如果不传，它会回退到 `default_session`，多轮恢复语义就不再清晰。

## 多问题并发补问

Java 当前 workflow 交互并不要求“一次只能问一个问题”。`examples/interact` 就展示了同一轮里同时补问城市和温度单位：

- workflow 会返回多个 `OutputSchema(type = "__interaction__")`
- 调用方按节点 id 收集回答
- 再用一个 `InteractiveInput` 一次性回填多个 node id

这也是为什么 `InteractiveInput.update(nodeId, value)` 比“只传一条字符串”更重要。

## 交互日志里看到 `GraphInterrupt` 要不要紧张

在 `QuestionerComponent` 等等待输入的场景里，底层图执行器当前可能打印 `GraphInterrupt` 的 `ERROR` 日志。按照示例 README 的说明，这通常是：

- 正常中断并等待用户输入
- 不是 workflow 真正失败

判断是否真的失败，应以这几个信号为准：

- 是否已经返回了 `assistant>` 的补问内容；
- 在 `reply>` 或 `retry>` 之后是否继续执行；
- 是否最终回到了完成结果。

## 当前 Java 能力边界

- `SimpleAgentInteraction` 只负责 checkpoint + `AgentInterrupt`，不会产出 `InteractionOutput`。
- `InteractiveInput` 的 raw 模式和 node-based 模式互斥，不能混用。
- `WorkflowAgent` 的流式恢复路径目前对交互回放有边界：`stream` 路径只保证把当前需要展示的交互返回出来，不应承诺“多交互问题一定完整重放”。
- 本页只讨论当前 Java 运行时已有的等待 / 恢复语义，不扩展到前端表单协议、审批中心或外部消息总线集成。
