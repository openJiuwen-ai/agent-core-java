# 知识检索

Java 版知识检索能力围绕 `com.openjiuwen.core.retrieval` 展开。它把知识库、索引、查询改写、重排和多知识库聚合拆成一组可组合的公开接口，适合回答型 Agent、工作流资源检索节点和需要把外部文档接入推理链路的场景。

如果你的重点是“把文档切块、建索引、检索出可引用内容”，主线从 `KnowledgeBase`、`SimpleKnowledgeBase`、`GraphKnowledgeBase` 开始；如果你的重点是“多轮对话里先把问题改写干净，再把结果排得更稳”，则在知识库外侧叠加 `QueryRewriter` 与 `Reranker`。

## 能力定位

- `SimpleKnowledgeBase` 是标准分块式知识库入口，负责文档写入、删除、更新、检索和统计。
- `GraphKnowledgeBase` 在普通分块检索上追加三元组抽取、图索引和图扩展检索，适合实体关系比较重要的场景。
- `QueryRewriter` 用于把多轮用户问题改写成更适合检索的 `standalone_query`，不直接替代知识库。
- `Reranker` 家族用于对召回结果二次排序，适合“召回还行，但排序不稳”的问题。
- 如果你已经在工作流里使用知识检索组件，底层仍然是这套知识库抽象，只是由组件代为装配。

## 核心类型

| 类型 | 作用 | 何时优先使用 |
| --- | --- | --- |
| `KnowledgeBase` | 知识库抽象基类，统一配置校验、解析、索引管理和关闭流程 | 需要先理解公共生命周期时 |
| `SimpleKnowledgeBase` | 标准知识库实现，支持 `vector`、`sparse`、`hybrid` 检索 | 大多数文档检索场景 |
| `GraphKnowledgeBase` | 增加 triple 索引、图检索和图扩展召回 | 关系型知识、实体链路较重要时 |
| `KnowledgeBaseConfig` | 定义 `kbId`、`indexType`、`useGraph`、分块参数 | 创建知识库前必配 |
| `RetrievalConfig` | 定义 `topK`、`scoreThreshold`、`useGraph` 等检索参数 | 检索时调召回规模和阈值 |
| `QueryRewriter` | 基于 LLM 的问题改写入口 | 多轮对话、口语化提问、需要上下文压缩时 |
| `Reranker` / `LexicalReranker` / `StandardReranker` / `ChatReranker` | 检索结果重排 | 召回后还想提高排序质量时 |

## 接入步骤

### 1. 先选知识库形态

先不要把“检索增强”一股脑塞进一个类里。Java 当前的稳定边界更清楚：

- 只需要分块检索时，选 `SimpleKnowledgeBase`。
- 需要图索引时，选 `GraphKnowledgeBase`，并把 `KnowledgeBaseConfig.useGraph` 设为 `true`。
- `GraphKnowledgeBase` 在 `useGraph = true` 时会维护额外的 triple 索引；如果没有显式注入 `Extractor`，但提供了 `llmClient`，会退回到 `LLMTripleExtractor`。

### 2. 按知识库构造器装配基础组件

知识库本身不负责替你创建向量库、分块器或解析器。`SimpleKnowledgeBase` 的完整构造器需要这些组件：

- `VectorStore`
- `Embedding`
- `Parser`
- `Chunker`
- `Indexer`
- 可选的 `BaseModelClient`
- 可选的 `Retriever`

典型装配顺序如下：

```java
KnowledgeBaseConfig kbConfig = new KnowledgeBaseConfig("doc_kb", "hybrid", false, 512, 50);

SimpleKnowledgeBase kb = new SimpleKnowledgeBase(
        kbConfig,
        vectorStore,
        embedding,
        parser,
        chunker,
        indexer,
        null,
        null
);
```

有两个实现细节值得先知道：

- `addDocuments(...)` 和 `updateDocuments(...)` 依赖 `chunker`，缺失时会直接报错。
- 当 `strictValidation = true` 且同时存在 `vectorStore` 与 `indexManager` 时，知识库会先校验两边的向量字段配置是否兼容。

### 3. 先写入文档，再做基础检索

知识库主线非常直接：

1. 用 `parseFiles(...)` 或 `parseUrls(...)` 把输入转成 `Document`
2. 调 `addDocuments(...)` 建索引
3. 调 `retrieve(...)` 拿结果
4. 必要时用 `updateDocuments(...)`、`deleteDocuments(...)` 维护内容
5. 用 `getStatistics()` 看当前索引状态

```java
List<String> docIds = kb.addDocuments(documents);
List<RetrievalResult> results = kb.retrieve("Alice", new RetrievalConfig());
Map<String, Object> stats = kb.getStatistics();
```

如果你在 URL 导入场景里混用不同来源，要注意 `KnowledgeBase.parseUrls(...)` 会先检查 `parser.supports(url)`，只有当前解析器声明支持的 URL 才会被真正解析。

### 4. 多知识库和图检索都属于主 API

Java 当前把这两类能力直接放在主 API 里，而不是藏到示例里：

- 多知识库聚合：`SimpleKnowledgeBase.retrieveMultiKb(...)`
- 带来源信息的聚合：`SimpleKnowledgeBase.retrieveMultiKbWithSource(...)`
- 图知识库聚合：`GraphKnowledgeBase.retrieveMultiGraphKb(...)`

多知识库聚合会按文本去重，并保留更高得分的结果。如果你已经按业务拆成多个知识库，这比先手工拼结果再排序更稳。

### 5. 多轮检索时，把 Query Rewriter 放在知识库前面

`QueryRewriter` 不是 `KnowledgeBase` 的一个模式开关，而是独立的改写入口：

- `rewrite(String)`：依赖上下文，适合多轮会话里把当前问题改写成独立查询
- `rewrite(String, List<RetrievalResult>)`：结合已有召回结果做进一步改写

推荐顺序是：

1. 先拿用户原始问题
2. 用 `QueryRewriter` 产出 `standalone_query`
3. 再把这个 query 交给 `KnowledgeBase.retrieve(...)`

这样职责边界很清楚，后续也更方便分别调试改写和召回。

### 6. 结果重排单独放在检索后面

Reranker 家族当前分成三条路：

- `LexicalReranker`：本地词法重排，不依赖远端模型
- `StandardReranker`：调用远端 `/rerank` 接口
- `ChatReranker`：用 chat completion 的 yes/no 概率做排序

如果你的问题是“召回得到的文档相关，但前几条顺序不理想”，优先加 reranker，而不是先重写知识库装配。

## 当前实现边界

- Java 当前公开 API 的主线非常明确：知识库、改写器、重排器分别是独立能力。
- `examples/retrieval` 目前重点覆盖 embedding、rewriter、reranker 和 filter；完整的 `KnowledgeBase` 生命周期更适合直接看测试文件，而不是假装存在一个仓库里没有的 quickstart。
- Java `VectorStore` 过滤接口当前按 `Map<String, Object>` 这类现有语义演示，没有额外公开的表达式 DSL。
- `GraphKnowledgeBase` 的图检索和 extractor 回退逻辑已经是 Java 公开实现的一部分，文档要以当前 `useGraph`、`Extractor`、`llmClient` 的真实组合关系为准。
