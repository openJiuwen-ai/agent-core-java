# 生成和优化提示词

这一页讲的是 Java 版里两条容易被混在一起的能力线：

1. 运行时 prompt 模板装配：`com.openjiuwen.core.foundation.prompt`
2. 开发期 prompt 生成 / 优化工具：`com.openjiuwen.dev_tools.prompt_builder`

如果你现在只是想把模板变量替换成实际消息并发起一次模型调用，先看 [基础功能 / 填充提示词模板](../基础功能/填充提示词模板.md)。如果你已经进入“先生成初始模板，再根据反馈或 bad case 继续优化”的阶段，再读这一页。

> 本页只覆盖 Java 当前已经公开的 `PromptTemplate`、`BasePromptBuilder`、`MetaTemplateBuilder`、`FeedbackPromptBuilder`、`BadCasePromptBuilder`。不展开 agent evolving 的训练闭环，那是 [自优化Agent](自优化Agent.md) 与 [ReactAgent强化学习](ReactAgent强化学习.md) 的主题。

## 先把两层能力分开

| 层次 | 代表类型 | 解决什么问题 | 典型输出 |
| --- | --- | --- | --- |
| 运行时模板层 | `PromptTemplate`、`assemble` | 在真正调用模型前，把变量装配成消息列表 | `PromptTemplate` 或 `List<BaseMessage>` |
| 开发期生成层 | `MetaTemplateBuilder` | 从一句自然语言需求生成结构化 prompt 草稿 | `CompletableFuture<String>` |
| 开发期优化层 | `FeedbackPromptBuilder`、`BadCasePromptBuilder` | 根据反馈或错误案例改 prompt | `CompletableFuture<String>` |

这三层在 Java 里是分开的：

- `PromptTemplate` 是运行时对象，重点是 `format(...)` 和 `toMessages()`。
- `BasePromptBuilder` 及其子类是开发工具，内部自己持有一个 `Model`，通过 `build(...)` / `streamBuild(...)` 向大模型求一个“更好的 prompt 文本”。
- builder 并不会直接替代运行时模板装配。它更像“帮你写 prompt 的 prompt”。

## 运行时 prompt 仍然是入口

Java 当前真正进入模型调用前的最后一层，还是 `PromptTemplate`：

- `PromptTemplate.content` 支持 `String` 与 `List<BaseMessage>`。
- `format(Map<String, Object>)` 返回新的 `PromptTemplate`，不会就地修改原对象。
- `toMessages()` 把模板转换成真正要送给模型的消息列表。

这意味着 builder 产出的结果，通常还会回到运行时模板层继续使用。最常见的落法有两种：

1. 直接把 builder 输出的字符串保存成新的 system / user prompt 文本。
2. 把 builder 输出转成 `PromptTemplate.builder().content(...)`，再进入后续 `format(...)` 流程。

如果把这条边界记住，就不容易把“运行时变量替换”和“开发期 prompt 生成优化”混成同一件事。

## `BasePromptBuilder` 提供了什么公共能力

所有 Java prompt builder 都继承 `BasePromptBuilder`：

- 构造时接收 `ModelRequestConfig` 与 `ModelClientConfig`
- 内部直接创建一个 `Model`
- 对外统一暴露两个方法：
  - `build(Object prompt, Object... args)`
  - `streamBuild(Object prompt, Object... args)`

这里有两个 Java 侧细节要单独记：

1. 两个方法都返回 `CompletableFuture<String>`，而不是同步字符串。
2. `streamBuild(...)` 当前会在内部消费 `model.stream(...)` 并把 chunk 拼接成完整字符串后返回；它不是把增量 chunk 继续向调用方流式透出。

## `MetaTemplateBuilder`：先生成初始 prompt

`MetaTemplateBuilder` 的职责是把一段比较模糊的任务描述，转成结构化的模板文本。当前实现里最值得关注的是四件事：

1. `build(...)` 和 `streamBuild(...)` 都支持 `String` 或可转成字符串的 `PromptTemplate` 作为输入。
2. 内置模板类型只有两类：
   - `general`
   - `plan`
3. 内置语言模板当前只提供：
   - `zh-CN`
   - `en-US`
   其他值会回退到 `zh-CN`。
4. 支持注册自定义 meta template，内部统一加前缀 `META_TEMPLATE_`。

### 最小示例

```java
import com.openjiuwen.core.foundation.llm.schema.ModelClientConfig;
import com.openjiuwen.core.foundation.llm.schema.ModelRequestConfig;
import com.openjiuwen.core.foundation.tool.schema.ToolInfo;
import com.openjiuwen.dev_tools.prompt_builder.builder.MetaTemplateBuilder;

import java.util.List;

ModelRequestConfig modelConfig = ModelRequestConfig.builder()
        .modelName("gpt-4o-mini")
        .build();

ModelClientConfig clientConfig = ModelClientConfig.builder()
        .clientProvider("OpenAI")
        .apiKey(System.getenv("OPENAI_API_KEY"))
        .apiBase("https://api.openai.com/v1")
        .verifySsl(true)
        .build();

MetaTemplateBuilder builder = new MetaTemplateBuilder(modelConfig, clientConfig);

String generatedPrompt = builder.build(
        "你是一个人名提取助手，只输出真实存在的人名",
        List.<ToolInfo>of(),
        "general",
        null,
        "zh-CN"
).join();
```

### 什么时候用自定义 meta template

当内置的 `general` / `plan` 模板不够贴近你的领域时，可以先注册自己的模板，再通过 `templateType = "other"` 调用：

```java
import com.openjiuwen.core.foundation.prompt.PromptTemplate;

builder.registerMetaTemplate(
        "ticket",
        PromptTemplate.builder()
                .content("""
## 角色
你是一个工单分类助手

## 任务
{{instruction}}

## 可用工具
{{tools}}
""")
                .build()
);

String customPrompt = builder.build(
        "根据用户报障内容输出工单分类和优先级",
        List.<ToolInfo>of(),
        "other",
        "ticket",
        "zh-CN"
).join();
```

当前兼容测试还验证了：

- `registerMetaTemplate(...)` 只接受 `String` 或 `PromptTemplate`
- `getMetaTemplate(...)` / `popMetaTemplate(...)` 可继续按老的 `META_TEMPLATE_xxx` 命名取回对象

## `FeedbackPromptBuilder`：根据反馈微调 prompt

`FeedbackPromptBuilder` 解决的是“我已经有一版 prompt，但还想根据人工反馈继续小步修改”的问题。它不是重新生成整篇 prompt，而是围绕当前 prompt 做定向优化。

### 三种模式的差异

| 模式 | 调用方式 | 适用场景 | 返回内容 |
| --- | --- | --- | --- |
| `general` | `build(prompt, feedback)` | 对整篇 prompt 做整体微调 | 完整 prompt |
| `select` | `build(prompt, feedback, "select", startPos, endPos, language)` | 只改指定片段 | 优化后的片段 |
| `insert` | `build(prompt, feedback, "insert", startPos, language)` | 在指定位置补一段新内容 | 待插入片段 |

这里最容易误判的是后两种模式：

- `select` 不会自动帮你把整篇 prompt 拼回去，它返回的是“被选中片段的优化结果”。
- `insert` 返回的是“要插入的纯文本片段”，不是插入后的完整 prompt。

### 最常用的是 `general`

```java
import com.openjiuwen.dev_tools.prompt_builder.builder.FeedbackPromptBuilder;

FeedbackPromptBuilder feedbackBuilder = new FeedbackPromptBuilder(modelConfig, clientConfig);

String optimizedPrompt = feedbackBuilder.build(
        generatedPrompt,
        "补充一条约束：不要把别号、地名和机构名识别成人名"
).join();
```

### 位置模式有什么限制

当前实现会在真正发起模型请求前先校验位置参数：

- `select` 必须同时提供 `startPos` 与 `endPos`
- `insert` 必须提供 `startPos`
- 越界或区间非法会直接抛错

另外，`FeedbackPromptBuilder` 在进入最终改写模板前，还会先调用一轮 `PROMPT_FEEDBACK_INTENT_TEMPLATE` 判断反馈是否有价值，并尝试把反馈表达压缩得更清晰。如果识别失败，会退回原始反馈文本继续执行。

## `BadCasePromptBuilder`：把错误案例转成优化反馈

`BadCasePromptBuilder` 适合的不是“抽象反馈”，而是“我已经收集了一组具体错例，希望系统总结失败模式并改 prompt”。

它的流程是两步：

1. 用 `PROMPT_BAD_CASE_ANALYZE_TEMPLATE` 把 `EvaluatedCase` 列表总结成反馈摘要
2. 再用 `PROMPT_BAD_CASE_OPTIMIZE_TEMPLATE` 生成新的 prompt

### 最小示例

```java
import com.openjiuwen.dev_tools.prompt_builder.builder.BadCasePromptBuilder;
import com.openjiuwen.dev_tools.tune.Case;
import com.openjiuwen.dev_tools.tune.EvaluatedCase;

import java.util.List;
import java.util.Map;

BadCasePromptBuilder badCaseBuilder = new BadCasePromptBuilder(modelConfig, clientConfig);

List<EvaluatedCase> badCases = List.of(
        EvaluatedCase.builder()
                .caseData(Case.builder()
                        .inputs(Map.of("query", "潘之恒，号鸾啸生，冰华生"))
                        .label(Map.of("output", "[潘之恒]"))
                        .build())
                .answer(Map.of("output", "[潘之恒, 冰华生]"))
                .reason("误把别号识别成真实人名")
                .build()
);

String optimizedByBadCases = badCaseBuilder.build(
        "你是一个专业的人名提取助手",
        badCases,
        "zh-CN"
).join();
```

### 当前 Java 实现的边界

- `cases` 不能为空
- bad case 数量上限是 `10`
- prompt 不能为空

这些校验都发生在模型调用前；兼容测试已经覆盖“空 prompt / 空案例会先失败”的行为。

## 这页与基础功能页怎么分工

最简单的分工方式是：

- [填充提示词模板](../基础功能/填充提示词模板.md)：你已经知道 prompt 长什么样，只需要填变量并执行
- 本页：你还在“写 prompt”这一步，想先生成、再优化、再用错例迭代

一个典型链路可以写成：

1. 用 `MetaTemplateBuilder` 生成初稿
2. 用 `FeedbackPromptBuilder` 或 `BadCasePromptBuilder` 改到满意
3. 把结果保存成 `PromptTemplate`
4. 运行时继续用 `PromptTemplate.format(...)` 装配变量

## 当前 Java 实现里要特别注意的点

- builder 的输入 `prompt` 虽然声明成 `Object`，但当前可靠的用法仍然是 `String` 或内容可转成字符串的 `PromptTemplate`。
- 内置模板语言只有 `zh-CN` 与 `en-US`，没有更多 locale 模板集。
- `streamBuild(...)` 只是“内部用流式模型调用，外部仍返回完整字符串”，不要把它当成 `Iterator` 或 chunk callback API。
- 本页不展开 `InstructionOptimizer`、`ExampleOptimizer`、`Trainer` 这类更完整的优化闭环；那已经进入 agent evolving 范畴。
