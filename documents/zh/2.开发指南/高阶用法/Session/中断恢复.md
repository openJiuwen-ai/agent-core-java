# 中断恢复

本页不重复解释交互事件的数据结构细节，也不单独展开 checkpointer 的全部生命周期，而是只回答一个更贴近 Session 的问题：

> Java 版执行为什么能够在一次中断或失败后，带着同一个 `sessionId` 继续往下跑？

答案是：`session.interaction`、`session.checkpointer` 和 Session 本身的 `sessionId` 边界一起工作。交互子系统负责把“现在缺什么输入”抛出来，checkpointer 负责保存当前现场，下一次调用再借由同一个 `sessionId` 把状态和输入重新放回执行链路。

## 从 Session 角度看，恢复到底在恢复什么

恢复并不是简单的“重新调用一次方法”，而是把下面几类东西带回同一个执行边界：

- 同一个 `sessionId`
- 上一次留下的 workflow / agent 状态
- 尚未完成的交互节点或 agent 中断点
- 本轮新回填的 `InteractiveInput`
- 必要时的 graph checkpoint

如果这些对象不能回到同一个会话范围，恢复语义就会退化成“重新开一轮新执行”。

## 协作关系

| 部分 | 负责什么 | 关键对象 |
| --- | --- | --- |
| Session | 给整条执行链提供统一的 `sessionId`、状态与运行时上下文 | `BaseSession`、`WorkflowSessionApi`、`AgentSessionApi` |
| 交互子系统 | 产出补问事件，或消费已经回填的交互输入 | `InteractiveInput`、`InteractionOutput`、`WorkflowInteraction`、`AgentInteraction` |
| 检查点子系统 | 保存、恢复和释放现场 | `Checkpointer`、`CheckpointerFactory` |
| 调用方循环 | 决定何时再次调用，以及把什么输入送回去 | `examples/interact`、`Runner` |

四者缺一不可。只有交互没有检查点，输入不知道接回哪里；只有检查点没有同一个 `sessionId`，状态也找不回原来的执行。

## workflow 恢复主线

Java 当前原生 workflow 的恢复主线可以概括成五步：

1. 首次执行，传入一个明确的 `sessionId`。
2. 运行到需要补问或异常失败的位置时，当前状态被保存下来。
3. 调用方从输出里取出交互问题，或者决定发起一次 `retry`。
4. 调用方构造 `InteractiveInput`，并继续使用同一个 `sessionId` 再调一次 `workflow.invoke(...)`。
5. workflow 恢复旧状态后继续执行，结束时释放当前会话的 checkpoint。

一个简化后的 Java 代码片段如下：

```java
String sessionId = UUID.randomUUID().toString().substring(0, 8);
Object nextInputs = Map.of("query", userQuery);

while (true) {
    WorkflowOutput output = workflow.invoke(
            nextInputs,
            new WorkflowSessionApi(null, sessionId, Map.of()),
            null
    );

    if (WorkflowExecutionState.INPUT_REQUIRED.equals(output.getState())) {
        InteractiveInput replies = new InteractiveInput();
        replies.update("ask_city", "Shanghai");
        replies.update("ask_unit", "C");
        nextInputs = replies;
        continue;
    }

    break;
}

checkpointer.release(sessionId);
```

这个片段里真正不能丢的是两点：

- 第二次调用仍然使用同一个 `sessionId`
- 回填内容必须封装成 `InteractiveInput`

## `examples/interact` 的真实恢复流程

`examples/interact/WeatherAssistantInteractExampleSupport.java` 给了一条非常具体的恢复路径，它不是抽象伪代码，而是当前 Java 仓库里的真实示例。

### 第一段：补问恢复

示例在 `user>` 输入后会：

1. 生成一个新的 8 位 `sessionId`
2. 用 `workflow.invoke(nextInputs, newSession(sessionId), null)` 启动 workflow
3. 当 `WorkflowOutput.state == INPUT_REQUIRED` 时，解析结果里的 `InteractionOutput`
4. 根据每个交互的 `id` 逐个读取 `reply>`
5. 用 `InteractiveInput.update(nodeId, reply)` 把回答送回 workflow

这里最关键的事实是：同一轮里可以同时存在多个待回答问题。示例里的 `AskCity` 和 `AskUnit` 就会在同一轮中断里一起返回，所以恢复时不是简单传一条字符串，而是按节点 id 回填。

### 第二段：失败后 retry

这个示例还故意让 `QueryWeather` 第一次固定失败。失败后它不会新开会话，而是：

1. 读取 `retry>`
2. 构造 `new InteractiveInput("retry")`
3. 继续用同一个 `sessionId` 再次调用 `workflow.invoke(...)`

这条链路证明 Java 当前“失败后继续执行”的会话语义，和“等待用户补问后继续执行”的语义，本质上都依赖同一个恢复边界。

### 第三段：会话结束后的清理

示例完成或退出时，会显式调用：

```java
checkpointer.release(sessionId);
```

这一步不是装饰性代码，而是在告诉运行时：“这个 session 相关的 checkpoint 已经不需要再保留了。”

## `interaction` 和 `checkpointer` 是怎么接起来的

这部分在 [人机交互](../人机交互.md) 和 [Checkpointer 检查点机制](../Checkpointer检查点机制.md) 都分别展开过，但从 Session 视角可以把它们压缩成下面两条：

### workflow 侧

- `WorkflowInteraction` 先看当前 session 里是否已经有可消费的交互输入。
- 如果没有，它会产出 `InteractionOutput` 并打断 workflow。
- checkpointer 随后保存 workflow state 和 graph checkpoint。
- 下一次再带着同一个 `sessionId` 和 `InteractiveInput` 进入时，checkpointer 会先恢复状态，再把本轮输入注入进去。

### agent 侧

- `AgentInteraction` 或 `SimpleAgentInteraction` 负责把 agent 执行打断到“等待输入”的状态。
- agent checkpointer 保存的是 agent session 相关状态。
- 下一次继续执行时，仍然靠相同的 `sessionId` 或 `conversation_id` 找回这段会话。

也就是说，无论是 workflow 节点补问还是 agent 多轮等待输入，最终都是“交互告诉你要什么，checkpointer 告诉你从哪里接着跑”。

## 为什么同一个 `sessionId` 是硬条件

Checkpointer 文档已经给出持久化键结构：

```text
sessionId:namespace:entityId:suffix
```

这意味着：

- workflow state、agent state、graph checkpoint 都挂在某个 `sessionId` 下
- 交互等待与恢复不是全局广播，而是回到某个具体会话
- 如果你改了 `sessionId`，旧状态不会自动迁移到新会话上

从调用效果看，换一个 `sessionId` 就等于“重新开一轮”，不是“接着上一轮继续”。

## 在 Runner / WorkflowAgent 场景里的对应关系

如果你不是直接调用 `workflow.invoke(...)`，而是走 `Runner` 或 `WorkflowAgent`，同样的原则仍然成立，只是入口从 `sessionId` 变成了更上层的 `conversation_id`：

- `RunnerImpl` 会优先把输入中的 `conversation_id` 当作 agent session id
- 交互恢复时要继续沿用同一个 `conversation_id`
- 结束时通常通过 `Runner.release(conversationId)` 清理整段会话

所以 Session 子目录里的“恢复”，并不是只适用于原生 workflow 示例，它也是 `Runner` 与 `WorkflowAgent` 多轮继续执行的底层前提。

## 当前边界

- `InteractiveInput` 的 raw 模式和按节点 `update(nodeId, value)` 模式互斥，不能混用。
- 多个交互节点并发等待输入时，恢复必须带节点 id，不能只传一条模糊字符串。
- Java 当前流式恢复路径对交互回放仍有实现边界，本页只讨论“如何继续执行”，不承诺完整重放之前所有流块。
- agent 侧 `postAgentExecute(...)` 当前会继续保留 agent state，因此完整结束一段会话时仍应显式 `release(...)`。
