# 状态管理

Java 版 Session 的状态管理，不是把所有运行时数据都塞进一个普通 `Map`，而是按执行职责拆成多个状态分区，并配合提交、回滚和恢复语义来工作。

如果只先记一句话，可以把它理解成：

> Session 状态 = 分区存储 + 节点级待提交更新 + checkpointer 恢复边界。

## 最先该掌握的对象

第一次进入 `session.state` 时，建议先抓住下面四类对象：

| 类型 | 作用 | 为什么先看它 |
| --- | --- | --- |
| `State` | Session 状态顶层接口 | 先知道 Session 统一暴露了哪些分区与方法。 |
| `WorkflowCommitState` | workflow 侧最重要的状态实现 | 它真正承载提交、回滚、快照与恢复。 |
| `WorkflowStateCollection` | workflow 状态分区视图 | 帮你理解全局 / 组件 / IO / workflow 各分区的职责。 |
| `AgentStateCollection` | agent 侧状态集合 | 它对应 agent 的全局状态与 agent 私有状态。 |

如果你只是普通业务开发者，通常不需要直接 new 这些类型；但理解它们的职责，会直接影响你怎么使用 `session.getState(...)`、`updateState(...)`、`updateGlobalState(...)`。

## Session 里到底有哪些状态分区

`State` 接口当前定义的关键分区常量包括：

| 分区 | 典型持有方 | 作用 |
| --- | --- | --- |
| `global_state` | workflow / agent | 整个会话共享的全局状态。 |
| `io_state` | workflow | 组件输入 / 输出的中间承接区。 |
| `comp_state` | workflow | 当前节点或组件的私有状态。 |
| `workflow_state` | workflow | 更偏 workflow 级运行控制的数据。 |
| `trace_state` | workflow / agent | trace 相关状态。 |
| `agent_state` | agent | agent 私有状态。 |

其中最需要先建立直觉的是：

- workflow 侧不是只有“全局状态”和“组件状态”两层；
- agent 侧结构更简单，主要是 `global_state` + `agent_state`。

## 业务代码最常碰到的是哪两层

对自定义 workflow 组件来说，最常使用的是 `NodeSessionApi` 暴露的两组方法：

- `updateState(...)` / `getState(...)`：组件私有状态。
- `updateGlobalState(...)` / `getGlobalState(...)`：全局共享状态。

这意味着：

- 只在当前组件内部有意义的数据，优先放组件状态；
- 需要被后续节点或整个会话共享的数据，再放全局状态。

而 `io_state`、`workflow_state` 更多是运行时和 checkpointer 参与的内部语义，不是普通业务代码最先直接操作的入口。

## workflow 状态为什么要拆成四层

`WorkflowStateCollection` 当前同时持有：

- `ioState`
- `globalState`
- `compState`
- `workflowState`
- `traceState`

这样拆的目的，是把“共享数据”“节点私有数据”“输入输出承接数据”“workflow 运行控制数据”分开。

### `global_state`

适合记录整个 workflow 都需要读取的数据，例如：

- 补问收集结果
- 某轮执行的共享上下文
- 跨节点的执行标志

### `comp_state`

适合记录当前节点自己的私有信息，例如：

- 执行次数
- 当前节点的局部缓存
- 只在本节点内部有意义的中间结果

### `io_state`

它更像工作流引擎的“输入输出承接区”：

- `getInputs(...)` / `setOutputs(...)` 会围绕它工作；
- 节点之间的 schema 解析与输出引用，也会落到这一层。

### `workflow_state`

这层更偏 workflow 级控制语义，适合运行时在整个 workflow 范围内维护补充状态，而不把它混进组件私有状态。

## agent 状态比 workflow 更简单

`AgentStateCollection` 当前主要维护三部分：

- `globalState`
- `agentState`
- `traceState`

其中普通业务最常感知到的是前两层：

- `AgentSessionApi.updateState(...)` 写的是 agent 级全局状态；
- `AgentStateCollection` 内部仍保留 agent 私有分区。

相较 workflow 的多分区结构，agent 侧状态更像“持续会话上下文 + agent 私有运行数据”。

## 为什么“更新后立刻 get 不一定能看到”

这是 Session 状态子系统最容易误解的点。

workflow 侧的 `WorkflowCommitState` 并不是每次 `update(...)` 都直接落到已提交状态里，而是先进入待提交缓冲区。也就是说：

- `updateById(...)` 先把更新挂到某个 node 的 pending updates；
- 真正进入 committed state，要等 `commit...()`；
- 如果中途 `rollback()`，这些 pending updates 会被清掉。

因此，在同一个组件执行过程中：

- 你刚调用 `updateState(...)`；
- 紧接着又 `getState(...)`；
- 看到的仍可能是提交前的旧值。

这也是为什么很多状态示例里，“本组件更新后立刻打印”并不会读到新值，而要等到提交后、下一次节点运行或后续节点读取才真正可见。

## 提交、回滚与恢复语义

`WorkflowCommitState` 是理解这部分行为的核心对象。

### `commitCmp()`

提交当前节点的：

- `comp_state`
- `io_state`

适合节点执行完成后，把当前组件的局部产物固定下来。

### `commitWorkflow()`

只提交当前节点挂在 `workflow_state` 上的更新。

### `commit()`

一次性提交：

- `io_state`
- `global_state`
- `comp_state`
- `workflow_state`

这是 workflow 侧最完整的状态落盘前语义。

### `rollback()`

`rollback()` 当前清掉的是**当前 node 的待提交更新**，而不是把整个会话历史都回滚到最初状态。因此应把它理解成“撤销本节点尚未提交的改动”，而不是数据库式的全局事务回退。

## 恢复时恢复的不只是已提交快照

`WorkflowCommitState` 除了 `getState()` / `setState()` 之外，还提供：

- `getUpdates()`
- `setUpdates()`

这意味着 Session 恢复并不只依赖“已提交 state 快照”，还会把 pending updates 一并带回去。对 checkpointer 来说，这非常关键，因为被中断的 workflow 可能正卡在某个尚未完全收束的节点边界上。

从 Session 视角看，可以把恢复理解成两层：

1. 恢复 committed state；
2. 恢复尚未提交但仍应继续参与执行的 updates。

## `createNodeState(...)` 说明了什么

`WorkflowCommitState.createNodeState(...)` 会创建一个新的节点视图，但它共享底层状态分区，而不是把整套状态深拷贝成完全独立的新对象。

这有两个直接结果：

- workflow 能按节点视角读写状态；
- 但这些节点视图仍属于同一个 Session / workflow 状态空间。

所以它更像“带 nodeId 的状态窗口”，而不是“每个节点各有一份完整状态副本”。

## 内存实现是怎么工作的

如果你想先理解最稳定、最直接的一条实现路径，建议先看：

- `InMemoryCommitState`
- `InMemoryState`

### `InMemoryCommitState`

它的特点是：

- 每个 node 的更新会先累积到 `updates`；
- `commit(nodeId)` 时才真正并入底层 `state`；
- `rollback(nodeId)` 会清掉这个 node 的待提交更新。

### `InMemoryState`

`InMemoryState.create()` 会把：

- `io_state`
- `global_state`
- `comp_state`
- `workflow_state`

都装配成基于内存的 `InMemoryCommitState`，再返回一个 `WorkflowCommitState`。

这也是 Java 当前本地开发、单元测试和示例里最容易观察状态行为的实现路线。

## Session 和 checkpointer 为什么绑得这么紧

对 Session 来说，状态管理不是孤立子系统，因为：

- `BaseSession.state()` 给运行时提供统一状态入口；
- checkpointer 需要把 workflow / agent 状态保存下来；
- 恢复时又要按同一个 `sessionId` 把状态和 pending updates 放回去。

所以“状态管理”真正讨论的不是单纯的读写 API，而是“这次执行中断后，哪些状态应该被保留并在下次继续使用”。

## 什么时候继续看 API 文档

本页适合先建立 Session 状态模型。如果你遇到下面几类需求，再继续看底层 API 文档：

- 想深入确认 `WorkflowCommitState` 的快照与 updates 结构；
- 想写自定义 checkpointer 或持久化状态适配层；
- 想区分 `io_state`、`workflow_state` 与 `global_state` 在源码里的调用点；
- 想验证某个更新为什么在当前节点里读不到。

## 当前边界与注意事项

- workflow 侧很多更新先进入 pending buffer，不应把 `update...()` 理解成“立刻写入最终状态”。
- `createNodeState(...)` 创建的是共享底层分区的节点视图，不是完全独立状态副本。
- `AgentStateCollection.updateTrace(...)` 当前仍是占位实现，不应把 agent trace state 写成完整持久化能力。
- 真正涉及恢复边界时，应结合 checkpointer 理解状态，而不是只看 `dump()` 的表面结果。
