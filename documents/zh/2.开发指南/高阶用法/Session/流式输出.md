# 流式输出

Java 版 Session 的流式输出，不只是“把 token 一块块返回出去”，而是把 `output`、`trace`、`custom` 三类执行期数据统一放进同一条 Session 流管道里，再由 workflow 或 agent 的流式入口消费。

如果只先记一条主线，可以把它理解成：

> `StreamWriterManager` 负责按 mode 装配 writer，writer 负责校验 chunk，`StreamEmitter` 负责把 chunk 推进队列，调用方再通过 `stream(...)` 或 `streamIterator()` 把它们取出来。

## 最先该掌握的对象

如果你第一次读 `session.stream`，建议先只抓住下面六个对象：

| 类型 | 作用 | 为什么先看它 |
| --- | --- | --- |
| `StreamMode` | 定义 `OUTPUT`、`TRACE`、`CUSTOM` 三种流模式 | 先决定“你想让哪类 chunk 出现在流里”。 |
| `OutputSchema` / `TraceSchema` / `CustomSchema` | 三类流式 chunk 的 schema | 先知道每种 chunk 长什么样。 |
| `StreamWriterManager` | 管理不同 mode 的 writer 与消费接口 | 它是 Session 流式输出的总入口。 |
| `StreamWriter<T>` | 校验并发出某一类 chunk | 它决定写入的数据是否合法。 |
| `StreamEmitter` | 把 chunk 推给流队列 | 它负责把“写出”真正变成“可消费”。 |
| `AsyncStreamQueue` | 线程安全阻塞队列 | 它承接生产者 / 消费者之间的流数据。 |

等你把这几层关系看懂，再继续读细分 API 文档就不会迷路。

## 从 Session 角度看，一块数据是怎么流出去的

Session 流式输出的大致路径如下：

1. 当前执行创建或持有一个 `StreamWriterManager`。
2. 调用方或运行时按 `StreamMode` 取到对应的 `StreamWriter`。
3. `StreamWriter` 把输入校验成 `OutputSchema`、`TraceSchema` 或 `CustomSchema`。
4. 校验通过后，writer 调 `StreamEmitter.emit(...)`。
5. `StreamEmitter` 把 chunk 写进 `AsyncStreamQueue`。
6. workflow / agent 外部通过 iterator 或 callback 风格接口消费这些 chunk。

也就是说，Session 并不是给每种能力各开一条独立通道，而是用“同一条队列 + 不同 schema”把执行期数据统一起来。

## 三种 stream mode

`StreamMode` 当前只有三个公开枚举值：

| Mode | 典型 chunk | 适用场景 |
| --- | --- | --- |
| `OUTPUT` | `OutputSchema` | 标准答案块、`workflow_final`、交互提示等框架标准输出。 |
| `TRACE` | `TraceSchema` | workflow / agent 执行观测、组件开始 / 结束、错误与自定义 trace 数据。 |
| `CUSTOM` | `CustomSchema` | 业务方自定义结构化流数据。 |

一个容易混淆的点是：

- `StreamWriterManager` 在**直接以 `null` mode 构造**时，会把三种 mode 都装上；
- 但 `Workflow.stream(...)` 的**公开默认行为**并不是“全部打开”，而是默认只请求 `List.of(StreamMode.OUTPUT)`。

所以文档上谈“默认流式输出”时，应以 workflow / runner 的公开入口为准，而不是只看 `StreamWriterManager` 的内部兜底行为。

## chunk 长什么样

### `OutputSchema`

`OutputSchema` 是框架标准输出 chunk，核心字段是：

- `type`
- `index`
- `payload`

它适合承载“答案 token / 段落”“最终结果”“交互提示”等标准运行时输出。这里的 `type` 是业务含义标签，而不是 Java 类型系统本身。

### `TraceSchema`

`TraceSchema` 只有两个核心字段：

- `type`
- `payload`

它不是单独的日志系统，而是 Session 流管道里的 trace chunk。只要你打开 `TRACE` mode，它就和 `OutputSchema` 一样走同一个 `StreamWriterManager`。

### `CustomSchema`

`CustomSchema` 用于承载自定义属性集合。当标准 `OutputSchema` 不够表达业务数据时，可以把额外字段塞到自定义 chunk 里。

## writer、queue、emitter 的关系

### `StreamWriter<T>`：先校验，再写出

`StreamWriter<T>` 负责两件事：

1. 接收 schema 实例或 `Map<String, Object>`；
2. 校验并转换成目标 schema 后，再交给 emitter。

因此，业务代码更应该把它理解成“**模式感知的发射前校验层**”，而不是普通的 `println(...)`。

### `StreamEmitter`：把 chunk 推到队列

`StreamEmitter` 自己不关心 chunk 的语义，它关心的是：

- 把数据送进队列；
- 在关闭时发出 `END_FRAME` 哨兵值；
- 告诉消费者“这条流结束了”。

### `AsyncStreamQueue`：真正的生产者 / 消费者边界

`AsyncStreamQueue` 是线程安全阻塞队列，承接：

- 上游 writer / emitter 的持续写入；
- 下游 iterator / callback 的阻塞消费。

它也是 Session 能同时支持“后台持续产生 chunk”和“外部逐个取 chunk”的关键。

## `StreamWriterManager` 是真正的 Session 流入口

`BaseSession.streamWriterManager()` 把流式能力收束到一个统一入口。`StreamWriterManager` 当前至少暴露四类能力：

- `getOutputWriter()` / `getTraceWriter()` / `getCustomWriter()`：按 mode 取 writer。
- `streamIterator()`：以阻塞 iterator 方式消费流。
- `streamOutput(...)`：以 callback 方式消费流。
- `collectStreamOutput()`：阻塞收集全部 chunk。

从 Session 角度看，这意味着“写流”和“读流”都围绕同一个 manager 组织，而不是各自实现一套接口。

## workflow 是怎么接上这条流管道的

从 Session 视角看，workflow 流式执行的关键不是工作流拓扑，而是：`Workflow.stream(...)` 会为当前运行准备一个带 stream modes 的 workflow session，然后把产出的 chunk 以 `Iterator<WorkflowChunk>` 暴露出去。

这里的 `WorkflowChunk` 可以理解为 Java 当前 workflow 流式返回的统一上层类型；实际落到运行时，常见 chunk 仍然是：

- `OutputSchema`
- `TraceSchema`
- `CustomSchema`

在 workflow 组件内部，最常直接接触流式写入的是 `NodeSessionApi`：

- `writeStream(...)` 写标准输出块；
- `writeCustomStream(...)` 写自定义输出块。

如果你只想在组件里发结果，而不想自己拼装底层队列，这两个 API 就是最直接的入口。

## agent 是怎么接上这条流管道的

agent 侧最常见的两个入口是：

- `AgentSessionApi.writeStream(...)`
- `AgentSessionApi.writeCustomStream(...)`

另外还保留了更底层的：

- `AgentSessionApi.writeTraceStream(...)`

在外部消费时，通常不会直接操作内部队列，而是通过：

- `AgentSessionApi.streamIterator()` / `streamOutput(...)`
- `Runner.runAgentStreaming(...)`
- `Runner.runWorkflowStreaming(...)`

把 mode 列表一路传到 Session 内部。

## trace 不是“另一条单独通道”

这是 Java 当前 Session 流子系统里最值得先搞清楚的一点：

- trace 数据的 schema 是 `TraceSchema`；
- 但 trace 的传输通路仍然是同一个 `StreamWriterManager`；
- `TraceBaseHandler` 也是从 manager 里取 `getTraceWriter()` 再把 trace 发出去。

所以如果你开启 `TRACE` mode，调用方拿到的是“同一条 Session 流里的 trace chunk”，而不是旁路日志文件或单独 socket 通道。

## 什么时候继续看 API 文档

当你只是在业务代码里消费流式输出时，理解本页就够了；当你遇到下面几类问题，再继续看底层 API 文档：

- 想自定义 mode 对应的 writer 行为；
- 想确认 `OutputSchema` / `TraceSchema` 的字段细节；
- 想看 `StreamWriterManager` 的迭代超时、关闭与收集逻辑；
- 想理解 trace chunk 为什么会在某个 workflow 节点发出。

## 当前边界与注意事项

- `Workflow.stream(...)` 的公开默认 mode 是 `OUTPUT`，不要把它写成“默认输出所有类型 chunk”。
- trace 不是独立日志通道，而是 Session 流里的 `TraceSchema`。
- `AsyncStreamQueue.close()` 会清空剩余队列项，因此不应承诺“关闭后还能继续取回所有历史 chunk”。
- 组件处于 `transform` / `collect` 这类 stream-mode 路径时，`NodeSessionApi.interact()` 当前不支持等待用户输入。
