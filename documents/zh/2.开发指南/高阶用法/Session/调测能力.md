# 调测能力

从 Session 视角看，Java 版调测能力主要回答两个问题：

1. 执行过程中的事件是怎么被捕获和分发的？
2. 这些事件又是怎么变成 trace chunk、供外部实时观察的？

如果先只记一条主线，可以把它概括成：

> `CallbackManager` 决定事件交给谁处理，`Tracer` 决定这些事件怎样变成 span 和 `TraceSchema`，而 `TraceSchema` 仍然走 Session 的同一条流输出管道。

本页只讲 Session 视角下的观测与调试入口，不把整套 logging 或 runner callback 体系全部展开。

## 最先该掌握的对象

| 类型 | 作用 | 为什么先看它 |
| --- | --- | --- |
| `CallbackManager` | 回调处理器注册与触发中心 | 先知道事件是怎样被分发的。 |
| `BaseHandler` | callback handler 抽象基类 | 先知道一个 handler 需要具备什么结构。 |
| `TriggerEvent` | 标记可被回调触发的方法 | 先理解事件发现机制。 |
| `Tracer` | span manager、trace handler 的协调中心 | 先知道 trace 为什么能自动挂进 Session。 |
| `TraceSchema` | trace 的流式 schema | 先知道外部消费到的 trace chunk 长什么样。 |
| `TracerWorkflowUtils` | workflow 侧 trace 上报工具 | 先知道 workflow 生命周期事件从哪里进入 tracer。 |

## Session 侧观测其实分成两层

### 第一层：callback 事件分发

这层解决的是：

- 某个事件发生了；
- 应该通知哪个 handler；
- 参数怎样传给 handler 方法。

### 第二层：tracer 把事件变成 span 和 trace chunk

这层解决的是：

- 如何为 agent / workflow 维护 trace span；
- 如何把开始、结束、错误、stream 输入输出等事件写成 trace 数据；
- 如何把这些 trace 数据发送给外部消费者。

把这两层分开理解后，你就不会把 callback、tracer、日志系统混成一件事。

## callback 层：事件是怎么被触发的

### `BaseHandler` 与 `@TriggerEvent`

一个 Session callback handler 通常继承 `BaseHandler`。`BaseHandler.getTriggerEvents()` 会扫描本类里所有标了 `@TriggerEvent` 的方法，并把它们视为可触发事件。

也就是说：

- 不是 handler 里的任意 public 方法都会被当成事件；
- 真正会被 `CallbackManager` 识别的，是那些显式标注了 `@TriggerEvent` 的方法。

### `CallbackManager` 做了什么

`CallbackManager` 负责：

1. 注册 handler；
2. 记录每个 handler 可响应的事件名；
3. 在 `trigger(...)` 时查找并调用目标方法；
4. 按方法签名把 `kwargs` 映射成参数。

它还有两个很实用的细节：

- 会在 snake_case 和 camelCase 之间做事件名适配；
- 如果 handler 内部抛异常，异常不会被静默吞掉，而会继续向上冒泡。

因此，Session callback 更像“带签名映射和失败传播的事件分发器”，而不是简单日志 hook。

## tracer 层：trace 怎么挂进 Session

`Tracer` 是 Session 观测链路里的中心对象。它在初始化时会做两件关键的事：

1. 持有 `SpanManager`，管理 agent 和 workflow 的 span；
2. 把 `TraceAgentHandler`、`TraceWorkflowHandler` 注册进当前 `CallbackManager`。

这意味着 trace 不是一套绕开 Session 的旁路系统，而是直接借助 callback 层把执行事件接进来。

## trace 最终为什么会出现在流式输出里

关键在 `TraceBaseHandler`。

`TraceBaseHandler` 在构造时，会从 `StreamWriterManager` 里取到：

- `getTraceWriter()`

之后把 span 格式化成：

- `type`
- `payload`

再以 `TraceSchema` 的形式写回 Session 流。

所以从运行路径看：

1. workflow / agent 事件进入 callback；
2. trace handler 更新 span；
3. `TraceBaseHandler` 把 span snapshot 写成 `TraceSchema`；
4. `TraceSchema` 进入同一个 `StreamWriterManager`；
5. 外部通过同一条流消费到 trace chunk。

这也是为什么本页强调：**trace 不是独立的日志通道，而是 Session 流管道上的一种 chunk。**

## workflow 侧最常见的自动观测入口

workflow 生命周期里，最值得先掌握的是 `TracerWorkflowUtils`。它把下面这些事件组织成统一上报入口：

- workflow 开始 / 完成
- 组件开始 / 完成
- 组件 inputs / outputs
- stream 输入 / 输出
- 交互输入
- 错误与自定义 trace 数据

换句话说，如果你看到 workflow 执行里自动出现组件开始、结束、错误或 stream 相关 trace，多半就是这一层在把节点生命周期转换成 tracer 事件。

## 业务代码最直接能用什么

### workflow 组件里：`NodeSessionApi.trace(...)`

对于自定义 workflow 组件，最直接的 Session 级调试入口是：

- `trace(Map<String, Object> data)`
- `traceError(Exception error)`

它们的作用不是直接写日志文本，而是把当前节点的自定义调试信息送进 tracer 流程，让这些数据进入同一套 Session 观测链路。

### agent 侧：更常见的是让 tracer 自动工作

agent 侧虽然也暴露了更底层的 `writeTraceStream(...)`，但大多数场景更适合让 `Tracer`、handler 和 decorator 自动工作，而不是手工拼每一条 trace chunk。

只有当你明确知道自己要输出什么 `TraceSchema`，并且希望跳过更高层 span 语义时，才需要直接写 trace stream。

## 如何让外部真正看到 trace

如果外部消费的是 streaming 接口，那么要显式把 `TRACE` mode 打开。例如：

- `Workflow.stream(..., List.of(StreamMode.TRACE))`
- `Workflow.stream(..., List.of(StreamMode.OUTPUT, StreamMode.TRACE))`
- `Runner.runAgentStreaming(..., ..., List.of(StreamMode.OUTPUT, StreamMode.TRACE), ...)`

这里需要特别注意：workflow 的公开默认流式行为仍然是 `OUTPUT`，不是自动包含 `TRACE`。如果没有显式请求 `TRACE`，你不能假设调用方一定能收到 trace chunk。

## 什么时候应该继续看底层 API 文档

本页适合先建立 Session 观测主线。只有在下面几类场景里，才建议继续钻更底层文档：

- 想自定义 handler，并明确控制它响应哪些事件；
- 想看 `Span` / `TraceWorkflowSpan` / `TraceAgentSpan` 的字段；
- 想理解嵌套 workflow、loop、stream output 为什么会带某些 trace 元数据；
- 想确认 `TracerDecorator` 在模型、工具或 workflow 包装时到底做了什么。

## 当前边界与注意事项

- 本页讲的是 Session 观测链路，不是整套 logging 系统；日志输出仍由其他层负责。
- trace 不是独立旁路，而是通过 `TraceSchema` 走同一条 Session stream。
- callback handler 抛出的异常不会被静默吞掉，所以自定义 handler 也会影响执行成败。
- `TracerDecorator` 依赖 Java 代理能力，当前更适合接口型对象包装，不应把它写成“所有对象都能自动无侵入追踪”。
