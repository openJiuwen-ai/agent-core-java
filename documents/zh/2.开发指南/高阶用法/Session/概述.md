# 概述

Java 版 Session 子系统负责把一次执行真正变成“可继续的会话”：它决定当前运行使用哪个 `sessionId`，状态写到哪里，交互问题通过什么对象抛出，流式输出和 trace 由谁发射，以及恢复时从哪里把上下文取回来。

如果只记一条主线，可以把 Session 理解成下面这件事：

> 同一个 `sessionId` 下，agent、workflow、交互、流输出、状态与检查点共享同一条执行边界。

这也是为什么 Java 版很多高阶能力最终都会回到 `com.openjiuwen.core.session` 根包，而不是各自维护一套独立的恢复协议。

## 核心类型

Session 根包里最值得先建立认知的是下面几个对象。

| 类型 | 角色 | 适合怎么理解 |
| --- | --- | --- |
| `Session` | 最小会话接口 | 给 `ContextEngine` 等只需要窄接口的调用方保留兼容入口。 |
| `BaseSession` | 执行期基础抽象 | 统一暴露配置、状态、流 writer、callback、tracer、checkpointer 和 `sessionId`。 |
| `AgentSessionApi` | agent 对外门面 | 面向业务代码，负责 agent 级环境变量、状态、流输出和交互入口。 |
| `WorkflowSessionApi` | workflow 对外门面 | 面向 workflow 调用方，携带父级 session、环境变量、callback manager 和 `sessionId`。 |
| `ProxySession` | 底层代理实现 | 自己不保存状态，只把 `BaseSession` 的访问器转发到底层 stub。 |

这几个对象不是并列重复，而是分别位于不同层级。

## `BaseSession` 是真正的运行时中心

`BaseSession` 是 Session 体系里最重要的抽象基类。它统一暴露了执行期最关键的几件事：

- `config()`：环境变量和运行配置来源。
- `state()`：当前会话状态对象。
- `streamWriterManager()`：流式输出 writer 管理器。
- `callbackManager()`：回调处理器注册与触发入口。
- `tracer()`：trace span 和 handler 的挂接点。
- `checkpointer()`：保存与恢复当前会话状态的入口。
- `sessionId()`：唯一会话标识。

从文档组织角度看，`BaseSession` 也是后续 `流式输出`、`状态管理`、`调测能力` 三页的共同起点，因为这些能力最终都会从这个抽象上取到具体实现。

## `AgentSessionApi` 与 `WorkflowSessionApi` 负责对外使用

大多数业务代码不需要直接 new 一个 `BaseSession`，而是通过对外门面进入。

### `AgentSessionApi`

`AgentSessionApi` 面向单个 agent 的执行期能力，重点是：

- 读写环境变量和全局状态。
- 发出标准输出流、自定义流和 trace 流。
- 在 agent 级调用 `interact(...)` 进入等待输入。
- 通过 `preRun()` / `postRun()` 与 checkpointer 生命周期衔接。
- 用 `createWorkflowSession()` 把当前 agent 会话继续下钻到 workflow。

换句话说，`AgentSessionApi` 主要解决“agent 外部怎么拿到一个可运行、可继续、可输出的会话门面”。

### `WorkflowSessionApi`

`WorkflowSessionApi` 面向 workflow 执行。它自己携带：

- `sessionId`
- 环境变量快照
- 父级 `BaseSession`
- 独立的 `CallbackManager`
- 当前 workflow card

其中一个关键点是：当 `WorkflowSessionApi` 带着父级 `BaseSession` 创建时，会优先继承父级环境变量。也就是说，agent 里的 workflow 子执行不是一段完全割裂的新上下文，而是“挂在当前会话树下面的子执行”。

## `ProxySession` 解决的是延迟绑定

`ProxySession` 自己不维护配置、状态或追踪器，它只是把全部访问器转发给底层 `BaseSession` stub。这个对象的价值不在业务层，而在运行时装配层：

- 有些 workflow / graph 对象在构建期就需要持有一个 session 引用；
- 但真正的底层 session 要到执行期才能确定；
- 这时用 `ProxySession` 先占位，等实际执行开始后再把 stub 填进去。

因此它更像运行时内部的“会话适配器”，而不是一个给业务侧长期直接操作的主要 API。

## Session 怎么把 agent 和 workflow 接在一起

从调用链看，Java 当前 Session 子系统大致是这样协作的：

1. 外部先拿到一个 `AgentSessionApi` 或 `WorkflowSessionApi`。
2. 运行时内部把这些门面转换成真正参与执行的 `BaseSession`。
3. workflow 组件、graph 引擎、trace、callback、checkpointer 都通过 `BaseSession` 取各自的子系统。
4. 如果 agent 内再调用 workflow，就沿用同一个会话边界继续创建子 workflow session。

这条链路解释了两个常见现象：

- 为什么很多框架内部代码签名都直接接收 `BaseSession`。
- 为什么恢复、状态、流输出这些能力虽然散落在不同子包里，最后仍然能围绕同一个 `sessionId` 收束起来。

## 子系统分工

Session 根包下的子包不是平铺罗列，而是围绕执行期会话拆成不同职责。

| 子系统 | 主要职责 | 典型类型 |
| --- | --- | --- |
| `state` | 状态读取、更新、提交、回滚与恢复 | `WorkflowStateCollection`、`WorkflowCommitState`、`AgentStateCollection` |
| `stream` | 输出块 schema、队列、writer、writer manager | `OutputSchema`、`TraceSchema`、`StreamEmitter`、`StreamWriterManager` |
| `interaction` | 交互载荷、等待输入和恢复入口 | `InteractiveInput`、`InteractionOutput`、`WorkflowInteraction`、`AgentInteraction` |
| `checkpointer` | 会话保存、恢复和释放 | `Checkpointer`、`CheckpointerFactory`、`InMemoryCheckpointer`、`PersistenceCheckpointer` |
| `callback` | 注册和触发执行期事件处理器 | `CallbackManager`、`BaseHandler` |
| `tracer` | trace span、trace handler 和 workflow/agent 追踪工具 | `Tracer`、`TraceWorkflowHandler`、`TracerDecorator` |
| `store` | 会话持久化基础存储抽象 | `Store`、`MemoryStore`、`FileStore` |

其中 `state`、`stream`、`interaction` 是最直接面向运行结果的三块，`checkpointer`、`callback`、`tracer`、`store` 则负责把这些运行结果保存、观察或持久化。

## 状态、流、交互、回调、存储之间的关系

可以用下面这条主线理解这些子系统如何配合：

1. 执行开始后，状态写入 `state`。
2. 执行中产生的输出和 trace 通过 `stream` 发出去。
3. 遇到等待用户输入时，`interaction` 产出 `InteractionOutput`。
4. 需要保存当前现场时，`checkpointer` 把状态和图执行进度持久化。
5. 整个过程中，`callback` 和 `tracer` 提供可观测性。
6. 如果状态需要跨进程或跨执行保存，再由 `store` 或底层 KV 存储承接。

所以这几个名词虽然分属不同子包，但实际都是“同一个执行期会话”的不同切面。

## 开发时怎么选入口

如果你是业务侧开发者，可以按下面的原则选：

- 需要驱动 agent 运行、写流或调用 agent 交互，优先用 `AgentSessionApi`。
- 需要直接调用 workflow、显式传入 `sessionId` 或挂接 callback，优先用 `WorkflowSessionApi`。
- 需要理解恢复、状态或 tracing 的底层行为，再往下看 `BaseSession` 和对应子包。
- `ProxySession` 更偏运行时内部细节，一般不作为普通业务代码的首选入口。

## `sessionId` 是 Session 的主键

在 Java 当前实现里，`sessionId` 决定了至少三件事：

- 状态写到哪个会话范围。
- 交互输入恢复时去哪里查旧状态。
- checkpointer 释放时清理哪一批 agent / workflow / graph 数据。

`Checkpointer` 文档已经把持久化键格式总结成：

```text
sessionId:namespace:entityId:suffix
```

这意味着一旦换了 `sessionId`，就不是“继续同一会话”，而是创建一条新的执行上下文。对恢复语义来说，这个边界非常硬。
