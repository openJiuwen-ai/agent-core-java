# 开发自定义组件

Java 版工作流真正扩展能力的核心，不是再造一套新的 workflow DSL，而是围绕 `ComponentComposable`、`ComponentExecutable` 和 `WorkflowComponent` 这组三个抽象来扩节点。

如果你只是想把现成组件接起来，优先看 [构建工作流](../工作流/构建工作流.md) 与 [使用组件](../工作流/使用组件/README.md)。只有在现成的 `Start`、`End`、`LLMComponent`、`ToolComponent`、`QuestionerComponent`、`SubWorkflowComponentImpl` 等节点都不够用时，才需要进入自定义组件。

> 这里先聚焦 workflow 组件扩展本身，不讨论 skill、sysop 工具或 agent 级插件开发。

## 什么时候应该自定义组件

最常见的三个触发点是：

1. 你需要一个仓库里还没有的业务节点，例如自定义解析、字段归一化、外部系统适配。
2. 你需要消费流式输入或产出流式输出，现成组件不匹配。
3. 你希望把“节点配置 + 执行逻辑 + 分支接入方式”封装成可重复使用的组件。

相反，如果你只是：

- 改一条 prompt
- 重排现有节点
- 改输入输出 schema

通常还不需要写自定义组件。

## 先把三组抽象分开

| 类型 | 角色 | 你该怎么理解 |
| --- | --- | --- |
| `ComponentExecutable` | 执行契约 | 定义 `invoke`、`stream`、`collect`、`transform` 四种执行模式 |
| `ComponentComposable` | 图接入契约 | 定义 `toExecutable()` 和 `addComponent(...)`，决定节点怎样进图 |
| `WorkflowComponent` | 最常用基类 | 同时具备上面两层角色，适合大多数自定义节点 |

Java 当前最常见的结论是：

- 简单组件直接继承 `WorkflowComponent`
- 复杂组件把“配置 / 图接入”和“运行态执行”拆成 `ComponentComposable + ComponentExecutable`

## `ComponentExecutable`：四种执行能力不是同一回事

`ComponentExecutable` 公开了四种基本能力：

| 方法 | 输入形态 | 输出形态 | 对应能力枚举 |
| --- | --- | --- | --- |
| `invoke(...)` | batch | batch | `INVOKE` |
| `stream(...)` | batch | stream | `STREAM` |
| `collect(...)` | stream | batch | `COLLECT` |
| `transform(...)` | stream | stream | `TRANSFORM` |

这四个方法并不会自动全部生效。真正把它们接进工作流图时，还要配合 `ComponentAbility`：

- `STREAM` 组件通常要配 `addStreamConnection(...)`
- `COLLECT` / `TRANSFORM` 组件必须把 `waitForAll` 设为 `true`

`BaseWorkflow.validateCompAbility(...)` 已经把这一点写成了硬校验：`COLLECT` 与 `TRANSFORM` 如果没有 `waitForAll = true`，会直接报错。

## `WorkflowComponent`：最常用、最直接的写法

`WorkflowComponent` 本身就：

- 继承了 `ComponentExecutable`
- 实现了 `ComponentComposable`
- 默认 `addComponent(...)` 会把当前对象自己加到 graph 里

所以只要你的图接入逻辑很普通，最省事的方式就是直接继承它。

### 最小示例：一个批处理节点

```java
import com.openjiuwen.core.context.ModelContext;
import com.openjiuwen.core.session.NodeSessionApi;
import com.openjiuwen.core.workflow.WorkflowComponent;

import java.util.Map;

public final class NormalizeAmountComponent extends WorkflowComponent {

    @Override
    @SuppressWarnings("unchecked")
    public Object invoke(Object inputs, NodeSessionApi session, ModelContext context) {
        Map<String, Object> inputMap = (Map<String, Object>) inputs;
        String rawAmount = String.valueOf(inputMap.getOrDefault("amount", ""));
        String normalized = rawAmount.replace("人民币", "").trim();

        session.trace(Map.of("raw_amount", rawAmount, "normalized_amount", normalized));
        session.updateState(Map.of("normalized_amount", normalized));

        return Map.of("amount", normalized);
    }
}
```

这个模式适合：

- 逻辑简单
- 不需要额外的 graph 拼装
- 组件实例本身就可以直接作为 executable

## `ComponentComposable + ComponentExecutable`：把构造和执行拆开

如果你的组件要持有复杂配置、初始化运行态对象，或者希望把执行器单独抽出来复用，就更适合拆成两层。

仓库里已经有很多现成例子：

- `QuestionerComponent` -> `QuestionerExecutable`
- `LLMComponent` -> `LLMExecutable`
- `KnowledgeRetrievalComponent` -> `KnowledgeRetrievalExecutable`
- `ToolComponent` -> `ToolExecutable`

这类组件的共同点是：

1. 组件类本身主要保管 config 和图接入方式
2. `toExecutable()` 每次产出真正的运行态对象
3. 运行期状态放进 executable 或 session，而不是堆在 composable 对象里

### 最小示例：拆分式组件

```java
import com.openjiuwen.core.context.ModelContext;
import com.openjiuwen.core.graph.Executable;
import com.openjiuwen.core.session.NodeSessionApi;
import com.openjiuwen.core.workflow.ComponentComposable;
import com.openjiuwen.core.workflow.ComponentExecutable;

import java.util.Map;

final class NormalizeAmountExecutable extends ComponentExecutable {
    @Override
    @SuppressWarnings("unchecked")
    public Object invoke(Object inputs, NodeSessionApi session, ModelContext context) {
        Map<String, Object> inputMap = (Map<String, Object>) inputs;
        String rawAmount = String.valueOf(inputMap.getOrDefault("amount", ""));
        return Map.of("amount", rawAmount.trim());
    }
}

public final class NormalizeAmountNode implements ComponentComposable {
    @Override
    public Executable<?, ?> toExecutable() {
        return new NormalizeAmountExecutable();
    }
}
```

如果你不实现 `toExecutable()`，而当前对象本身又不是 `Executable`，`ComponentComposable` 的默认实现会直接抛异常。

## 自定义分支组件：什么时候要重写 `addComponent(...)`

不是所有自定义组件都只有一个普通节点。有一类组件本身就带“路由”语义，例如：

- 意图识别
- 条件判断
- 某些带内置 `BranchRouter` 的业务网关节点

这时只靠默认的 `graph.addNode(...)` 不够，你还要在 `addComponent(...)` 里一起把条件边挂进去。Java 仓库里最直接的参考就是 `IntentDetectionComponentImpl`：

- `toExecutable()` 返回 `IntentDetectionExecutable`
- `addComponent(...)` 先 `graph.addNode(...)`
- 然后 `graph.addConditionalEdges(nodeId, router)`
- 组件本身再暴露 `addBranch(...)`

这类组件适合“组件本身拥有自己的分支协议”，而不是把分支完全交给工作流外部去配。

## `NodeSessionApi`：自定义组件在运行时能拿到什么

自定义组件在 `invoke` / `stream` / `collect` / `transform` 里拿到的是 `NodeSessionApi`，不是裸 `BaseSession`。它是你最应该利用好的运行时入口。

### 最常用的能力

| 方法 | 作用 |
| --- | --- |
| `trace(...)` / `traceError(...)` | 把自定义观测数据送进 Session tracer 链路 |
| `updateState(...)` / `getState(...)` | 读写当前节点作用域状态 |
| `updateGlobalState(...)` / `getGlobalState(...)` | 读写全局状态 |
| `interact(...)` / `userLatestInput(...)` | 触发人机交互或读取最近一次交互输入 |
| `writeStream(...)` / `writeCustomStream(...)` | 直接写输出流或自定义流 |
| `getEnv(...)` | 读取 workflow 运行环境参数 |

### 一个重要限制

`NodeSessionApi` 在 `collect(...)` 和 `transform(...)` 这类 stream-mode 执行路径里会禁止 `interact(...)`。也就是说：

- 批处理组件可以发起交互
- `COLLECT` / `TRANSFORM` 组件不能在处理流的时候再要求用户交互

这是 `NodeSessionApi` 当前源码里的显式限制，不是文档建议。

## 接入 workflow 的最短路径

自定义完组件后，接入工作流通常就按下面这条主线走：

### 1. 注册节点

```java
import com.openjiuwen.core.workflow.Workflow;
import com.openjiuwen.core.workflow.component.End;
import com.openjiuwen.core.workflow.component.Start;

import java.util.Map;

Workflow workflow = new Workflow();
workflow.setStartComp("start", new Start(), Map.of("amount", "${amount}"), null);
workflow.addWorkflowComp(
        "normalize",
        new NormalizeAmountComponent(),
        Map.of("amount", "${start.amount}"),
        null
);
workflow.setEndComp(
        "end",
        new End(Map.of("responseTemplate", "标准金额：{{amount}}")),
        Map.of("amount", "${normalize.amount}"),
        null
);
```

### 2. 补边

```java
workflow.addConnection("start", "normalize");
workflow.addConnection("normalize", "end");
```

### 3. 执行验证

```java
Object result = workflow.invoke(Map.of("amount", "人民币 200 元"), null, null).getResult();
```

如果你的组件涉及流式链路，就把 `addConnection(...)` 换成 `addStreamConnection(...)`，并按能力声明 `STREAM` / `COLLECT` / `TRANSFORM`。

## 做流式组件时要补上的两件事

### 1. 显式声明 `ComponentAbility`

`WorkflowComponent` 里实现了 `stream(...)`、`collect(...)` 或 `transform(...)`，不代表工作流图会自动按那种方式连。接入时仍然要在 `addWorkflowComp(...)` 里写清能力，例如：

```java
workflow.addWorkflowComp(
        "collector",
        new MyCollectorComponent(),
        true,
        Map.of("value1", "${producer.value}"),
        null,
        Map.of("value", "${producer.value}"),
        null,
        List.of(com.openjiuwen.core.workflow.component.ComponentAbility.COLLECT)
);
```

### 2. `COLLECT` / `TRANSFORM` 必须 `waitForAll = true`

这是 Java 当前的硬性规则，不满足会在 workflow 注册阶段失败。原因也很直接：这两类能力消费的是一整路流，图执行器必须先等上游流准备好。

## `config / state / IO` 这些抽象在自定义组件里怎么用

`workflow.component` 包里还有三类容易让人误会的壳类型：

| 类型 | 当前定位 | 你该怎么用 |
| --- | --- | --- |
| `ComponentConfig` | 公共配置壳，只包含 `metadata` | 需要做公共 metadata 描述时再继承 |
| `ComponentState` | 公共运行态壳，只包含 `compId` 和 `status` | 需要给外部暴露标准化状态结构时再扩展 |
| `IOConfig` | 输入输出 schema 壳 | 多数业务代码不手动 new，通常由 `Workflow` 注册方法自动组装 |

也就是说，真正写自定义组件时：

- 运行逻辑重点看 `ComponentExecutable`
- 图接入重点看 `ComponentComposable`
- 运行时上下文重点看 `NodeSessionApi`
- `ComponentConfig` / `ComponentState` / `IOConfig` 更多是公共结构或内部规格说明

## 怎么验证你的组件写对了

最实用的验证顺序通常是：

1. 先写一个最小 workflow，只放 `Start -> 自定义组件 -> End`
2. 用 `invoke(...)` 跑通 batch 路径
3. 如果涉及 stream，再补 `stream(...)` 与 `addStreamConnection(...)`
4. 如果组件需要状态或 trace，检查 `session.getState(...)` 与 trace chunk 是否符合预期

Java 仓库自己的 `WorkflowTest` 已经覆盖了三种最值得参考的扩展路径：

- 自定义 `STREAM` 节点
- 自定义 `COLLECT` 节点
- `STREAM -> TRANSFORM -> COLLECT` 的串接

## 当前 Java 实现里要特别注意的点

- `WorkflowComponent` 是最常用入口，但不是唯一入口。`QuestionerComponent`、`LLMComponent` 这类成熟组件其实走的是 composable + executable 分层模式。
- `COLLECT` 与 `TRANSFORM` 必须设置 `waitForAll = true`。
- `NodeSessionApi.interact(...)` 不支持在 `collect(...)` / `transform(...)` 里调用。
- batch schema 与 stream schema 当前不能做重名覆盖；`BaseWorkflow` 已经有重名校验。
- 这里聚焦 workflow 组件扩展，不覆盖 skill 或系统操作扩展。
