# 记忆引擎

Java 版长期记忆主线只有一个公开入口：`LongTermMemory`。它负责把消息、变量、片段记忆和摘要记忆写入底层存储，再按 `userId + scopeId + sessionId` 这组边界去检索和维护。

如果你的需求是“跨多轮、多会话记住用户偏好、变量和历史摘要”，应该从 `LongTermMemory` 开始；如果你的需求是“控制一次 LLM 调用时上下文窗口里放哪些消息”，那是 `ContextEngine` 的职责；如果你在看 `examples/context_evolver`，那是建立在扩展算法管线之上的记忆增强示例，不是 `LongTermMemory` 的主 API。

## 能力定位

- `LongTermMemory` 管理的是可持久化的长期记忆，而不是单次推理窗口。
- `scopeId` 用来区分业务域、Agent 或应用隔离边界。
- `sessionId` 主要服务于消息写入和近期消息读取，不等于长期记忆的唯一主键。
- 当前公开记忆类型集中在变量、片段记忆和摘要记忆，没有把 `context_evolver` 的算法流程包装成根包 API。

## 核心类型

| 类型 | 作用 | 何时使用 |
| --- | --- | --- |
| `LongTermMemory` | 长期记忆引擎主入口 | 所有记忆读写和检索都从这里进 |
| `MemoryEngineConfig` | 引擎级默认模型、消息长度和加密配置 | 完成 `registerStore(...)` 后立即设置 |
| `MemoryScopeConfig` | scope 级模型和 embedding 配置 | 需要按 Agent / 业务隔离模型配置时 |
| `AgentMemoryConfig` | 控制当前 Agent 写入哪些变量和记忆类型 | 每次 `addMessages(...)` 前定义策略 |
| `MemInfo` / `MemResult` | 记忆基础信息和检索结果 | 需要分页或语义检索返回值时 |

## 接入步骤

### 1. 先注册存储，再谈配置

`LongTermMemory` 采用单例模式：

```java
LongTermMemory memory = LongTermMemory.getInstance();
memory.registerStore(kvStore, vectorStore, dbStore, embeddingModel);
```

这一段有两个仓库事实需要先说清：

- `registerStore(...)` 会自动建表并执行 KV / vector / SQL migration。
- 当前实现里 `registerStore(...)` 会立刻调用 `setConfig(new MemoryEngineConfig())`，而 `setConfig(...)` 会检查 KV、Vector、DB 三类 store 是否都已注册，所以这三类存储在当前版本里都应准备好。

如果你只打算接一个轻量缓存，而没有 SQL 或向量存储，这不是“文档没展开”，而是当前实现本身就还不支持那种半装配状态。

### 2. 设置系统级配置

系统级配置用 `MemoryEngineConfig`：

```java
memory.setConfig(MemoryEngineConfig.builder()
        .defaultModelCfg(modelCfg)
        .defaultModelClientCfg(clientCfg)
        .cryptoKey(aesKey)
        .inputMsgMaxLen(8192)
        .singleTurnHistorySummaryMaxToken(128)
        .build());
```

这里最值得注意的是：

- `cryptoKey` 要么为空，要么正好是 32 字节。
- `defaultModelCfg` 和 `defaultModelClientCfg` 是 scope 未覆盖时的默认模型配置。
- `inputMsgMaxLen` 和 `singleTurnHistorySummaryMaxToken` 会影响写入与摘要行为。

### 3. 用 scope 把不同业务隔离开

长期记忆不是只按用户分桶。Java 当前把 `scopeId` 作为非常明确的隔离面：

```java
memory.setScopeConfig("support_agent", MemoryScopeConfig.builder()
        .modelCfg(modelCfg)
        .modelClientCfg(clientCfg)
        .embeddingCfg(embeddingCfg)
        .build());
```

`setScopeConfig(...)` 会把配置序列化进 KV 存储，并对 `model_client_cfg` 和 `embedding_cfg` 里的 API key 做加密；`getScopeConfig(...)` 读取时再解密回来。这意味着 scope 配置不是一段只存在内存里的临时参数，而是长期记忆系统自己维护的一部分状态。

### 4. 为当前 Agent 定义记忆策略

当前 Java 公共配置里的 `AgentMemoryConfig` 很聚焦：

- `memVariables`
- `enableLongTermMem`
- `enableFragmentMemory`
- `enableSummaryMemory`

也就是说，Java 当前公开的是“长期记忆总开关 + 片段记忆 + 摘要记忆 + 变量记忆”这组能力，而不是更细的算法型 memory pipeline 配置。

```java
AgentMemoryConfig agentMemoryConfig = AgentMemoryConfig.builder()
        .enableLongTermMem(true)
        .enableFragmentMemory(true)
        .enableSummaryMemory(true)
        .memVariables(List.of(variableParam))
        .build();
```

### 5. 在每轮交互后写入消息，并按需生成记忆

主写入入口是 `addMessages(...)`：

```java
memory.addMessages(
        messages,
        agentMemoryConfig,
        "user-1",
        "support_agent",
        "session-1"
);
```

更完整的重载还允许你传入：

- 显式 `timestamp`
- 是否立即生成记忆 `genMem`
- 生成记忆时额外回看的历史消息条数 `genMemWithHistoryMsgNum`

如果 `timestamp` 为空，当前实现会按系统默认时区生成时间戳，这一点已经在 `LongTermMemoryTest` 里有覆盖。

### 6. 读最近消息、变量和长期记忆时分清用途

写入之后，最常用的读取路径一般分成三类：

- 最近消息：`getRecentMessages(...)`
- 变量记忆：`getVariables(...)`、`updateVariables(...)`、`deleteVariables(...)`
- 长期检索：`searchUserMem(...)`、`searchUserHistorySummary(...)`

```java
List<BaseMessage> recent = memory.getRecentMessages("user-1", "support_agent", "session-1", 6);
Map<String, String> variables = memory.getVariables(List.of("city", "tone"), "user-1", "support_agent");
List<MemResult> hits = memory.searchUserMem("退款偏好", 5, "user-1", "support_agent", 0.3);
```

这一步的推荐思路是：

1. 调用前先取变量和相关长期记忆，拼进 prompt 或上下文
2. 调用后再把本轮消息回写到 `LongTermMemory`

这样 `ContextEngine` 和 `LongTermMemory` 的职责就不会混掉。

## 当前实现边界

- Java 当前公开的 `AgentMemoryConfig` 字段聚焦 `enableLongTermMem`、`enableFragmentMemory`、`enableSummaryMemory` 和 `memVariables`。
- Java 版长期记忆明确采用 `LongTermMemory` 单例 + `registerStore(...)` + `setScopeConfig(...)` 的入口形态，而不是把 context evolver 一类扩展算法管线混进根包主 API。
- 仓库里目前没有独立的 memory example，最直接的事实来源是测试和 API 文档；这一点应当被显式写出来，而不是虚构一个不存在的 quickstart。
- `scopeId` 在 Java 里是很实在的隔离边界，且 scope 配置会持久化到 KV 存储；不要把它写成纯粹的运行时标签。
