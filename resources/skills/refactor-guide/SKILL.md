# 项目重构规范与流程治理

本 skill 治理重构的核心痛点：**没测试就改、改完没验证、改一半中断、引入新 bug**。原则是"先补测试再验证，小步快走"。

## 重构前置检查（不满足就停）

重构前必须全部满足，缺一不可：

- [ ] **有覆盖率足够的测试**：核心逻辑覆盖率 > 70%。没测试 → 先补"特征测试"（记录当前行为，哪怕有 bug 也记录），再重构
- [ ] **测试当前是绿的**：`mvn test` 通过，建立"重构前是好的"基线
- [ ] **有明确的重构目标**：能一句话说清"这次重构要解决什么问题"，不是"顺手改改"
- [ ] **有回滚方案**：在独立 git 分支上做，或已备份
- [ ] **重构范围已界定**：列出要改的文件清单，范围外的"看着不爽"的代码不改

**特征测试写法**（没测试时的应急）：
```java
// 记录当前行为，不判断对错
@Test
void characterize_currentBehavior_ofCalc() {
    assertEquals(42, calc.compute(1, 2, 3));  // 即使 42 是 bug，也先记录
    assertEquals(0, calc.compute(0, 0, 0));
    assertNull(calc.compute(null, null, null));  // 当前 NPE 也记录下来
}
```

## 重构粒度分级

按风险和影响范围分 4 级，每级有不同流程要求：

| 级别 | 范围 | 例子 | 流程要求 |
|---|---|---|---|
| **L1 表面重构** | 单文件、不改签名 | 重命名变量、提取常量、调格式 | 改完跑单测即可 |
| **L2 结构重构** | 单文件、改内部结构 | 提取方法、内联方法、搬移函数 | 改完跑单测 + 集成测试 |
| **L3 接口重构** | 多文件、改签名 | 改方法签名、拆类、合并类 | 先改测试，再改实现，跑全量测试 |
| **L4 架构重构** | 跨模块、改依赖 | 换框架、拆微服务、改数据流 | 分阶段、每阶段独立可测可回滚 |

**判断级别**：如果改完要影响调用方 → 至少 L3；如果跨模块 → L4。

## 标准重构流程（5 步，小步快走）

1. **绿灯基线**：`mvn test` 通过。失败就先修 bug，别在坏代码上重构。
2. **补测试**：对要改的代码补测试，覆盖率不够就加用例。重点覆盖**要改的部分**和**会被影响的调用方**。
3. **小步重构**：每次只做一个原子动作（提取一个方法 / 重命名一个变量 / 搬移一个函数），改完立即跑测试。
4. **提交检查点**：每个原子重构后 `git commit`，commit message 写清做了什么。方便 `git bisect` 定位和 `git revert` 回滚。
5. **验证**：跑全量测试 + 集成测试 + 关键路径手动验证。L3/L4 还要跑性能基线对比。

**关键原则**：不要一次改 10 个地方再跑测试。出问题时无法定位是哪一步引入的。

## 重构动作清单

常见重构场景的标准做法：

| 场景 | 重构动作 | 注意点 |
|---|---|---|
| 方法太长 | 提取方法 | 提取后方法名表达意图；参数过多则封装成对象 |
| 重复代码 | 提取公共方法/模板方法 | 不要过度抽象，**3 次重复**再提取（rule of three） |
| 类太大 | 拆类/提取职责 | 先问"这个类有几个职责"，单一职责违反才拆 |
| 嵌套太深 | 提取方法 / 早返回 / 卫语句 | 减少嵌套层级，优先用卫语句提前 return |
| 魔法数字 | 提取常量 | 常量名表达业务含义，不是 `NUM_42` |
| 过长参数 | 封装参数对象 | 不要造"参数袋"反模式（一个类装所有参数） |
| switch 分支 | 多态替换 / 策略模式 | 分支固定用 switch，分支会扩展用策略模式 |
| 全局变量 | 依赖注入 | 减少 static，用构造注入或方法注入 |
| 复杂条件 | 提取判断方法 / 策略模式 | `if (a && b || c)` 提成 `if (shouldExecute(a, b, c))` |

## 安全重构技巧

避免"重构到一半代码挂了"的 4 种模式：

### 1. Strangler Fig（绞杀者模式）

新代码逐步替换旧代码，旧代码保留到验证完毕再删：

```
// 阶段 1：新实现并存
public Result process(Input in) {
    if (featureFlag.useNew()) {
        return newProcess(in);   // 新实现
    }
    return oldProcess(in);       // 旧实现保留
}

// 阶段 2：灰度验证后，流量切到新实现
// 阶段 3：删旧实现
```

适用：L4 架构重构、替换整个模块。

### 2. 并行实现 + 开关切换

新旧实现并存，配置开关切换，出问题秒回滚：

```java
if (config.getBoolean("use.new.parser")) {
    return newParser.parse(input);
} else {
    return oldParser.parse(input);
}
```

适用：换框架、换算法、换数据源。

### 3. 影子流量

新旧实现同时跑，对比结果，不影响线上：

```java
Result official = oldProcess(input);          // 线上用这个
Result shadow = newProcess(input);             // 影子跑，不影响返回
logCompare(official, shadow);                  // 对比，不一致告警
return official;
```

适用：核心链路重构，不能直接切。

### 4. 提交检查点

每个原子重构后 `git commit`，方便回滚和 bisect：

```bash
git commit -m "refactor: 提取 computeTax 方法 from calculate"
# 跑测试，绿
git commit -m "refactor: 重命名 price -> unitPrice"
# 跑测试，红 → git revert HEAD，回到上一步
```

适用：所有级别的重构，**必做**。

## 反模式（不要这么重构）

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| **大爆炸重构** | 改一周才跑测试，出问题无法定位 | 小步快走，每步 commit + 测试 |
| **顺手重构** | 修 bug 时顺手改无关代码，扩大变更范围 | 重构和修 bug 分开 commit，分开 PR |
| **无测试重构** | 凭"我懂这代码"直接改 | 先补特征测试，再重构 |
| **重构 + 改逻辑** | 重构和行为变更混一起，无法区分 | 重构不改行为，改逻辑单独 commit |
| **跨分支重构** | 多个分支同时重构，合并冲突地狱 | 在一个分支做完，再 cherry-pick |

## L3/L4 重构的分阶段策略

L3（接口重构）和 L4（架构重构）必须分阶段，每阶段独立可测可回滚：

### L3 接口重构示例（改方法签名）

```
阶段 1：新签名 + 旧签名并存（旧签名 delegate 到新签名）
阶段 2：所有调用方迁移到新签名
阶段 3：删旧签名
```

每阶段一个 commit，每阶段后跑全量测试。

### L4 架构重构示例（拆微服务）

```
阶段 1：新服务搭建，不接流量（独立可测）
阶段 2：Strangler Fig 接入新服务，影子流量对比
阶段 3：灰度切流量到新服务
阶段 4：下线旧服务
```

每阶段之间可能间隔数周，每阶段都要有回滚方案。

## 重构完成的验收标准

重构做完，检查：

- [ ] 全量测试通过（含集成测试）
- [ ] 没有引入新的测试失败
- [ ] 行为未变（L1/L2/L3）或行为变更已验证（L4）
- [ ] 代码更清晰（可读性提升，不是更复杂）
- [ ] 没有引入新的代码坏味道
- [ ] 性能未退化（L3/L4 跑性能基线对比）
- [ ] 已删除死代码（旧实现、无用 import）

## 使用方式

1. **前置检查**：重构前先过"前置检查"5 条，缺测试先补特征测试。
2. **判断级别**：按"粒度分级"表确定 L1-L4，选对应流程要求。
3. **执行流程**：按"标准重构流程"5 步走，小步快走，每步 commit + 测试。
4. **选动作**：按"重构动作清单"找对应场景的标准做法；需要代码示例时 Read `references/refactoring_patterns.md`。
5. **遗留代码**：没测试的旧代码 Read `references/legacy_code_patterns.md`，用接缝点 + 特征测试 + 解依赖。
6. **真实案例**：需要端到端参照时 Read `references/refactoring_cases.md`（4 个案例：Service 拆分/static 改注入/拆微服务/补测试再重构）。
7. **安全策略**：L3/L4 用 Strangler Fig / 并行实现 / 提交检查点，避免大爆炸。
8. **验收**：按"验收标准"检查重构是否真正完成。
9. **不确定不要编造**：重构手法以《重构》《修改代码的艺术》为准，本 skill 不替代正式方法论。
