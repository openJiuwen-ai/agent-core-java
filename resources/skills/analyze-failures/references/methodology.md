# PR 驱动的根因分析方法

## 证据优先级

按以下顺序建立事实，不用后一级推断覆盖前一级真实证据：

1. 实际测试输出：断言、异常、cause 链、超时或 Surefire 汇总；
2. 失败测试源码：断言意图、夹具、输入和被测入口；
3. PR patch：本次实际增加、删除和修改的行为；
4. 基线与当前源码：hunk 外上下文、接口契约和默认行为；
5. 可达调用链：变更如何传播到失败观察点；
6. 推断：只能填补小缺口，必须标注置信度，不能代替缺失证据。

## 建立最小因果链

对每个失败回答五个问题：

1. **观察到了什么？** 精确记录异常类型、断言差异或超时边界。
2. **测试要求什么？** 从测试源码确认断言针对的契约，而不是只读方法名。
3. **PR 改变了什么？** 找到具体文件、符号和行为变化，不只列“修改过该文件”。
4. **变化能否到达失败点？** 说明参数、返回值、状态、异常或异步事件经过的调用路径。
5. **反事实是否成立？** 如果恢复基线行为，现有证据是否足以解释失败会消失；如果不能，
   降低置信度。

只有“PR 行为变化 → 可达路径 → 失败现象”闭合时，才能高置信度归为开发问题。

## 改前与改后对照

重点检查这些行为变化：

- 返回值、默认值或序列化字段变化；
- 异常类型、catch 范围、错误传播或重试变化；
- 空值、边界值、白名单和校验顺序变化；
- 状态机、完成条件、流式终止条件和回调顺序变化；
- 路径规范化、符号链接、工作目录和进程环境变化；
- 时间、并发、缓存键、去重和资源生命周期变化；
- Mock、fixture、回放数据或断言本身变化。

不要只读当前源码。当前实现说明“现在是什么”，patch 和基线才说明“这次 PR 改了什么”。

## 归属判定

### 开发问题

需要同时证明：

- 失败涉及的产品行为在 PR 中发生了变化；
- 测试断言代表仍然有效的需求或兼容契约；
- 变化通过可达调用链导致当前失败。

### 测试代码问题

至少证明以下一种：

- 已确认的新契约要求更新断言，而测试仍固定旧语义；
- 测试夹具、Mock、回放数据或等待条件自身错误；
- 测试依赖未承诺的实现细节，产品行为仍符合公开契约。

不要因为“失败发生在测试代码”就归为测试问题。

### 环境问题

需要存在独立环境证据，例如不可达服务、缺失构件、容器权限、资源耗尽、错误 JDK、
时钟漂移或不稳定外部依赖。若 PR 修改了路径、启动参数或依赖解析并直接造成这些现象，
仍可能是开发问题，而不是环境问题。

### 证据不足

当 PR diff、测试意图或调用链无法确认时使用。列出最小补充证据，例如一个特定文件、
一个 revision、Surefire XML 或一段被截断的 cause 链。

## 多失败用例聚类

优先按以下签名聚类：

- 相同根因异常类型和首个项目帧；
- 相同 expected/actual 差异片段；
- 相同被修改符号或上游调用；
- 相同环境端点、缺失构件或容器错误；
- 一个初始化失败导致的后续级联错误。

不要把数量很多的级联失败误报为多个独立产品缺陷。报告中保留每个 nodeid，但为共享
原因分配同一个“共同根因组”。

## 修复建议质量

一个合格建议应说明：

- 修复哪个责任边界；
- 保留什么契约或兼容行为；
- 最小修改位置；
- 应由哪一个精确测试或 CI 证据验证；
- 可能影响的相邻边界。

不要建议弱化断言、无条件增加超时、吞掉异常、跳过测试或扩大 Mock 来掩盖失败。无法
证明实现补丁时，建议下一步取证而不是编造代码。
